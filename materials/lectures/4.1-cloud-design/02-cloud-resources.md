# 02. Облачные ресурсы для микросервисного приложения

## Карта ресурсов

Проектируя инфраструктуру, вы в конечном счёте заполняете таблицу: какая потребность каким сервисом закрывается. Для приложения из курса потребности примерно следующие: вычислительные мощности для сервисов, база данных, брокер сообщений, кэш, файловое хранилище, реестр образов.

Соответствие сервисов трёх провайдеров (Yandex Cloud, Selectel, AWS) полезно при чтении документации: одна и та же сущность в разных облаках называется по-разному, но работает похоже.

| Потребность | Yandex Cloud | Selectel | AWS |
|-------------|--------------|----------|-----|
| Виртуальные машины | Compute Cloud | Облачные серверы | EC2 |
| Управляемый Kubernetes | Managed Service for Kubernetes | Кластеры Kubernetes | EKS |
| Функции по событию | Cloud Functions | нет сервиса, фоновые задачи — отдельными воркерами | Lambda |
| Реестр контейнеров | Container Registry | Container Registry | ECR |
| PostgreSQL | Managed Service for PostgreSQL | Облачные БД для PostgreSQL | RDS |
| Redis | Managed Service for Valkey | Облачные БД для Redis | ElastiCache |
| Kafka | Managed Service for Apache Kafka | Облачные БД для Kafka | MSK |
| SQS-подобные очереди | Message Queue | нет аналога | SQS |
| Объектное хранилище | Object Storage (S3-совместимый API) | S3 | S3 |
| Балансировщики L4/L7 | Network Load Balancer, Application Load Balancer | Балансировщик нагрузки | NLB, ALB |
| Виртуальная сеть | VPC | Сети в панели управления | VPC |

Обращу внимание на две вещи. Во-первых, Object Storage у обоих российских провайдеров совместим с S3 API — то есть код, написанный под AWS S3, работает с ними без изменений, это важно для переносимости. Во-вторых, набор сервисов у Selectel уже, чем у Yandex Cloud: нет managed-очередей типа SQS, нет сервиса функций; Kafka и кэш закрываются облачными БД. И наоборот, managed RabbitMQ нет ни у кого из тройки — этот брокер везде ставится самостоятельно (отдельная VM или готовое решение из Marketplace). Это нормально: выбор всегда ограничивается двумя-тремя провайдерами, и дизайн готовится под конкретного.

## Вычислительные ресурсы

**Managed Kubernetes** — кластер из master-ноды (у провайдера) и worker-нод (ваша группа VM). Вы описываете желаемое состояние в манифестах, провайдер следит за control plane и обновлениями нод.

Для микросервисного приложения с постоянной нагрузкой и очередями это основной выбор курса: вы уже умеете собирать образы (ЛР3), оркестрация даст healthcheck, рестарты и rolling update из коробки. Serverless-варианты (Serverless Containers, App Runner) в классификации из файла 01 существуют, но в этом курсе мы их не рассматриваем: App Runner к тому же закрыт AWS для новых клиентов с апреля 2026 года.

## Данные: база, кэш, очереди

Managed Postgres — почти всегда правильный выбор для учебного и малого/среднего продакшен-проекта. PostgreSQL на VM требует от вас всего цикла администрирования: от установки и обновлений до резервного копирования с проверкой восстановления и настройки репликации при отказе. Managed-кластер делает это автоматически: мастер с репликами в разных зонах доступности, бэкапы с точкой восстановления, автоматический failover.

Redis/Valkey в managed-исполнении нужен, если вы кэшируете сессии или результаты. Если в приложении нет кэширования — не добавляйте сервис ради галочки в архитектуре, это замечание и к ДЗ7: каждый ресурс должен отвечать на реальную потребность вашего приложения.

Очередь сообщений: RabbitMQ и Kafka — разные инструменты, и в дизайн-документе надо выбрать осознанно, ссылаясь на то, что вы реализовали в ДЗ5.

По провайдерам: в Yandex Cloud и Selectel managed-исполнение есть только для Kafka, RabbitMQ разворачивается самостоятельно — на VM или готовым решением из Marketplace.

## Объектное хранилище

Всё, что приложение принимает или отдаёт как файл (загрузка от пользователя, аватары, экспорты), не должно лежать на диске VM. Причина: диск VM конечен, бэкапится вами вручную, а при пересоздании инстанса файлы исчезают. Object Storage масштабируется автоматически, данные хранятся в нескольких копиях, доступ по S3 API прямо из приложения. В отчёте ДЗ7 опишите, какие именно сущности вашего приложения уходят в объектное хранилище и почему.

## Реестр контейнеров и артефакты

Ваши образы из CI (ДЗ6, а после ДЗ8 — облачный CI/CD) должны где-то храниться. Container Registry у провайдера ближе к инфраструктуре, чем Docker Hub: быстрая загрузка образов нодами, приватные репозитории, интеграция с правами доступа облака. В Yandex Cloud и Selectel это Container Registry, в AWS — ECR.
