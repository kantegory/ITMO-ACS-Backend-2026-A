# 05. Архитектурные решения, инфраструктура как код

## Принципы, из которых складывается дизайн

Облачный технический дизайн начинается не с выбора конкретных сервисов, а следуя определённым принципам, под которые выбранные сервисы должны подходить. Для микросервисного приложения можно выделить пять ключевых принципов.

**Слабая связанность сервисов.** Синхронные вызовы между микросервисами создают каскадные отказы: если сервис оплаты медленный, зависает всё, что его вызывает. Асинхронные сценарии через очередь (ДЗ5) развязывают это: отправка события не ждёт обработки. В облаке тот же принцип отражается в выборе между «все в одном кластере на синхронных вызовах» и «очередь/топик как шина между сервисами».

**Дизайн под отказ, а не против отказа.** Традиционная on-premise логика — предотвратить отказ (один надёжный сервер, ИБП, RAID). Облачная логика — принять, что отказ будет на любой машине в любое время, и спроектировать систему так, чтобы отказ отдельного экземпляра ничего не менял: stateless-сервисы в нескольких копиях, состояние — в managed-хранилищах. Это меняет и отношение к железу: инстанс — не «сервер на годы», а расходный объект, пересоздаваемый за минуты.

**Stateless по умолчанию.** Любое состояние, живущее на диске контейнера, лишает вас возможности пересоздать инстанс без потери этого состояния. Отсюда стандартное распределение: код без состояния исполняется в подах, сессии и кэш уходят в Valkey/Redis, файлы — в Object Storage. Для вашего приложения это означает, что загрузка фото «на диск» — архитектурная ошибка, а сохранение сразу в S3-совместимое хранилище — правильное решение, и его нужно показать в дизайн-документе.

**Минимизация общей ответственности.** Может показаться, что один кластер БД на все микросервисы противоречит концепции database-per-service из ДЗ4, но это не совсем так и именно для этого мы стремимся добавить несколько READ-реплик, чтобы один медленный запрос не тормозил подготовку данных для всех сервисов. Существует и альтернативный подход — несколько маленьких managed-кластеров, что почти всегда дороже одного большого, и этот компромисс стоит зафиксировать явно: какие БД разделяем, какую экономию принимаем.

**Наблюдаемость как часть инфраструктуры.** Стек из темы 3.4 не остаётся на старой VM: в облаке добавляются собственные сервисы мониторинга (Managed Service for Prometheus в Yandex Cloud, CloudWatch в AWS), а к ним — логирование контейнеров через те же Loki/Promtail или сервисные лог-потоки провайдера. Дизайн инфраструктуры без раздела про мониторинг и логирование будет неполным, при этом стоит упомянуть о мониторинге хотя бы в разрезе использования встроенных инструментов и того же Sentry, как инструмента для отладки и локализации искажений.

## Инфраструктура как код

Terraform — стандарт, и в ДЗ7 он вам нужен не для оценки, а для воспроизводимости: инфраструктура, описанная кодом, — это и есть инженерный ответ на вопрос «как вы гарантируете, что тестовый контур и прод совпадают».

Базовые понятия: provider-блоки описывают подключение к облаку (для Yandex Cloud — провайдер `yandex`), ресурсы — сущности с аргументами, output — значения, отдаваемые наружу (IP балансировщика). Terraform хранит состояние (state) — файл с соответствием «код ↔ реальные ресурсы»; при команде `plan` видно, что изменится, перед применением. Для команды из одного человека state можно держать в git, но с ограничениями: в state попадают чувствительные значения, для серьёзного проекта state обычно хранят в удалённом бэкенде (в Yandex Cloud — Object Storage с lock'ингом).

Пример сетевого стека в HCL:

```hcl
resource "yandex_vpc_network" "app" {
  name = "app-network"
}

resource "yandex_vpc_subnet" "a" {
  name           = "subnet-a"
  zone           = "ru-central1-a"
  network_id     = yandex_vpc_network.app.id
  v4_cidr_blocks = ["10.128.0.0/24"]
}

resource "yandex_vpc_subnet" "b" {
  name           = "subnet-b"
  zone           = "ru-central1-b"
  network_id     = yandex_vpc_network.app.id
  v4_cidr_blocks = ["10.129.0.0/24"]
}

resource "yandex_vpc_security_group" "public" {
  name       = "public-traffic"
  network_id = yandex_vpc_network.app.id

  ingress {
    protocol       = "TCP"
    port           = 443
    v4_cidr_blocks = ["0.0.0.0/0"]
  }
}
```
