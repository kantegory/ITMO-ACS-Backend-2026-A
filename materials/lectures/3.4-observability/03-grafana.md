# 03. Grafana: дашборды под требования ЛР6

## Подключение источников данных

Когда Grafana и Prometheus подняты в одном docker compose, их имена в сети — просто `prometheus` и `loki`. Подключение через UI:

Administration → Data sources → Add data source. Для Prometheus указываем `http://prometheus:9090`, для Loki — `http://loki:3100`. После нажатия «Save & Test» оба источника становятся доступны во всех панелях.

Альтернатива — provisioning: положить JSON в `grafana/provisioning/datasources/` и при каждом `docker compose up` источники будут создаваться автоматически. Для лабораторной проще настраивать через UI и показать процесс скриншотами в отчёте.

## Как строить дашборд

Один дашборд на всю ЛР6, разделённый на три секции — по трём пунктам задания.

Секция «Ресурсы хоста» закрывает первый пункт. Панели CPU, RAM, диск и сеть — это прямые запросы к node_exporter из файла 02. CPU лучше всего считать через долю idle:

```promql
100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

RAM — разница между `MemTotal` и `MemAvailable`. Диск — `node_filesystem_avail_bytes` для точки монтирования `/`. Сеть — `rate()` от `receive`/`transmit` в байтах, умноженный на 8 и делённый на 1024^2 для Мбит/с.

Секция «Healthcheck» закрывает второй пункт. Здесь есть два уровня. Первый — таблица по метрике `up`: колонки `job`, `instance`, значение и время последнего изменения. Настройте на ней пороги: ноль — красный, единица — зелёный. Тогда «все ли сервисы доступны» видно без чтения чисел. Второй — поведение сервисов: запросы в секунду, доля 5xx, p95 задержки — всё это из ваших метрик через `prom-client`.

Секция «Логи» закрывает третий пункт. Панель типа «Logs» с источником Loki. Основной запрос `{container=~".+"}` показывает всё, фильтр `|= "ERROR"` — только ошибки. Включите автообновление панели (10–15 секунд), чтобы на защите график не требовал ручного обновления.

## Переменные дашборда

В шапке дашборда создайте две переменные. Первая — `$job`: query variable, источник Prometheus, метрика `up`, label `job` — получится выпадающий список всех сервисов. Вторая — `$container`: аналогично для лейбла Loki.

После этого запросы вида `rate(app_http_requests_total{job="$job"}[5m])` работают с фильтром — дашборд превращается из статичной картинки в инструмент.

## Алерты и email

Для доп. задания есть два пути, и оба дают баллы.

Первый — через Grafana Alerting. На панели с метрикой `up` создаёте alert, условие «Last of series = 0», contact point — Email. Для отправки почты Grafana требует настроенный SMTP; в docker compose это делается переменными окружения сервиса grafana:

```yaml
  grafana:
    environment:
      - GF_SMTP_ENABLED=true
      - GF_SMTP_HOST=mailhog:1025
      - GF_SMTP_FROM_ADDRESS=monitoring@example.com
      - GF_SMTP_SKIP_VERIFY=true
      - GF_SMTP_STARTTLS_POLICY=NoTLS
```

Второй — классическая схема через Alertmanager. Prometheus собирает правила, Alertmanager их маршрутизирует, email-конфигурация лежит в `alertmanager.yml`. Здесь есть routing и inhibition — чуть сложнее, но это «правильная» схема, про которую спрашивают на КР3.

Оба описаны в файлах 06 и 07, выбирайте одно и обоснуйте выбор в отчёте.

## Что показать на защите

Останавливаете контейнер: `docker stop api`. Через 15–30 секунд в таблице статуса он отображается как недоступный, `up` равен 0. Возобновляете работу — статус возвращается к нормальному. Это демонстрация healthcheck.

Создаёте нагрузку — через k6 или Postman несколько сотен запросов на один из сервисов. На графике QPS и latency рост виден в реальном времени. В логах через переменную выбираете конкретный контейнер и уровень ошибок. Если выполняли доп. задание — показываете сработавший алерт и место, куда было направлено уведомление.

## Экспорт дашборда

Dashboard menu → Export → Save to file. Приложите JSON в отчёт или на GitHub — это показывает, что дашборд воспроизводим, а не просто картинка.
