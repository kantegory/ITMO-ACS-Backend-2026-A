# 08. Kubernetes глазами человека, знакомого с docker compose

Большая часть терминологии Kubernetes — это понятия docker compose, переложенные на объекты кластера. Сравнение одного с другим помогает легче освоиться с новым инструментом.

| docker compose | Kubernetes | Чем отличается по поведению |
|----------------|------------|------------------------------|
| образ в `image:` | Container Registry + `image:` в шаблоне | образ берётся из реестра нодой; тег = версия для rollback |
| сервис compose | Deployment (+ ReplicaSet) | реплик сколько хочешь, раскидка по хостам, rolling update |
| `ports:` | Service (ClusterIP/LoadBalancer) | сетевая абстракция поверх набор pod'ов, имя в DNS |
| внутренняя сеть compose | сеть кластера (CNI) | единое пространство pod'ов на всех нодах, изоляция через namespace/NetworkPolicy |
| environment/env-file | ConfigMap + Secret | отдельные объекты, переиспользуются, не хранятся в git секретами |
| volumes/bind mount | emptyDir, PV/PVC | «том» = объект кластера, а не путь на хосте |
| `depends_on` | readinessProbe + retries | порядковых зависимостей нет, есть «станет ready — попадёт в балансировку» |
| `healthcheck:` | readiness/liveness probe | тот же смысл, разные действия: не готов / убить и перезапустить |
| `deploy.replicas` | `spec.replicas` + HPA | плюс автоматическое изменение по метрикам |
| `docker compose up -d` | `kubectl apply -f` | повторный apply идемпотентен |
| `docker compose logs` | `kubectl logs` | по pod'у; за долгим хранением — Loki/Cloud Logging (тема 3.4) |
| `docker compose ps` | `kubectl get pods` | плюс поля Ready/Restarts/Age — видна история сбоев |

## Что не имеет прямого аналога

**Namespace** — граница ресурсов, прав и именования. В compose всё приложение живёт в одном «пространстве имён»; в кластере разумная граница: namespace на приложение или на команду, отдельный для ingress-инфраструктуры, служебные под `kube-system`.

**Label selectors** — универсальный способ связывать объекты: селекторы Deployment'а, Service, NetworkPolicy, метрики Prometheus. В compose связки жёстко вшиты в структуру файла, здесь всё через произвольные пары ключ-значение на любых объектах. Выучите `kubectl get pods -l app=orders` в первый же день — это самый частый запрос в кластере.

**Реконсиляция** — в compose состояние файлов равно состоянию системы: `docker compose up` после правки и есть весь цикл. Кластер сам следит за соответствием: удалите pod руками — ReplicaSet его восстановит; поменяйте число реплик в консоли провайдера — через apply вашего манифеста всё вернётся как в git. Это меняет саму практику: манифесты становятся единственным источником истины, а ручные правки `kubectl edit` — временным экспериментом, который обречён быть затёртым.
