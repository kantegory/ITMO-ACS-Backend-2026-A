# 07. CI/CD для облачной инфраструктуры

## Что меняется после ДЗ6

В ДЗ6 автодеплой шёл на одну ВМ: сборка, ssh, `docker compose up`. В облачном Kubernetes появляются три новых вещи, и весь ДЗ8 — посвящён именно им:

1. артефакт пайплайна — не «код на сервере», а версионированный образ в реестре;
2. цель деплоя — не хост, а API кластера, у которого есть аутентификация и права;
3. деплой должен быть откатываемым, потому что одна команда применяет состояние ко всей системе сразу.

## Форма пайплайна

Скелет для GitHub Actions:

```yaml
name: deploy
on:
  push:
    branches: [main]
    paths: ['services/**']

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        service: [auth, orders, gateway]
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $REGISTRY/${{ matrix.service }}:${{ github.sha }} services/${{ matrix.service }}
      - run: docker push $REGISTRY/${{ matrix.service }}:${{ github.sha }}

  deploy:
    needs: build-and-push
    runs-on: ubuntu-latest
    steps:
      - name: Configure kubeconfig
        run: |
          # получение kubeconfig от сервисного аккаунта — см. раздел «Доступ к кластеру» ниже
      - name: Update manifests
        run: |
          sed -i "s|IMAGE_TAG|${GITHUB_SHA}|" k8s/*.yaml
          kubectl -n shop apply -f k8s/
      - name: Wait for rollout
        run: kubectl -n shop rollout status deploy/orders-service --timeout=120s
```

Разделение деплоя по сервисам — прямое следствие микросервисной архитектуры: каждый сервис собирается из своей папки в свой образ, и падение сборки одного не блокирует другие (в пределах одной стадии).

## Доступ к кластеру из пайплайна

Три способа:

**kubeconfig администратора в secret** — работает сразу, но: срок действия сертификатов в Yandex Cloud ограничен, админские права пайплайну не нужны, а ротация — ваша ручная работа.

**Сервисный аккаунт Yandex Cloud с отдельными правами** — вместо editor лучше выдать ровно то, что нужно пайплайну: `viewer` на кластер и `container-registry.pull` на реестр. `yc k8s cluster get-credentials` от имени этого аккаунта выдаёт короткий kubeconfig. Секрет в CI остаётся, зато область прав адекватна задаче.

**Токен service account Kubernetes + RBAC** — пайплайн ходит в API кластера не от вашего аккаунта вообще, а от service account namespace с правами только на деплойменты и configmap'ы этого namespace. В сочетании с external secret'ами это и есть «низкопривилегированный деплоер» — уровень, который в ДЗ8 уже не требуется.

## Конвейер поверх GitOps

Альтернатива `kubectl apply` из CI — Argo CD или Flux: в кластере крутится контроллер, который следит за git-репозиторием с манифестами и сам применяет изменения. Тогда «деплой» пайплайна сводится к коммиту нового тега образа в манифест, а доставка состояния — забота кластера. Преимущества: единая правдивая картина состояния в git, встроенный rollback = git revert, видимость дрейфа конфигурации. Для ДЗ8 достаточно обычного apply из CI.

## Где тесты

Порядок стадий: линт → unit-тесты сервиса (если есть) → сборка образа → интеграционные тесты (поднять compose с БД и очередью, прогнать сценарий из ДЗ3) → деплой.

Отдельная полезная стадия для кластера — проверка манифестов без применения: `kubectl apply --dry-run=server -f k8s/` ловит опечатки в apiVersion и валидационные ошибки до того, как половина прод-namespace улетит в Pending.

## Замечания по практике

- Обновляйте в облаке только изменённые сервисы: `paths:`-фильтры или `git diff --name-only` относительно последнего тега. Гонять сборку gateway из-за изменений в README — точно не стоит.
- Stage deploy обязан иметь `rollout status --timeout`: иначе пайплайн «успешно завершился», а половина pod'ов в CrashLoop, и узнаёте вы это от пользователей.
- Заведите откат: `kubectl rollout undo` в отдельный workflow, запускаемый вручную — простая «кнопка отката» которой всегда можно воспользоваться без необходимости залезать в kubectl.
- Пайплайн подставляет именно новые версии образов.
