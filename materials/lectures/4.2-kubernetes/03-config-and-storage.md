# 03. Конфигурация и хранение состояния

## Контейнер не знает своей конфигурации

В docker compose переменные окружения задавались в файле, благодаря чему образ мог оставаться тем же самым для разработки и продакшена. Kubernetes ту же идею доводит до ресурсов: конфигурация живёт в отдельных объектах, а деплоймент только подключает их к контейнеру.

**ConfigMap** — именованные пары «ключ → значение», передаваемые в переменные окружения или как смонтированные файлы:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: orders-env
data:
  NODE_ENV: "production"
  LOG_LEVEL: "info"
  QUEUE_URL: "amqp://rabbitmq:5672"
```

В деплойменте:

```yaml
      containers:
        - name: orders
          envFrom:
            - configMapRef:
                name: orders-env
```

**Secret** — то же по механике, но значения кодируются base64 (не шифруются — не путайте), и по умолчанию их видно всем, у кого есть право чтения в namespace. Секреты хранят строки соединения, токены, DSN Sentry:

```yaml
        - name: orders
          env:
            - name: SENTRY_DSN
              valueFrom:
                secretKeyRef:
                  name: app-secrets
                  key: sentry-dsn
```

Никогда не коммитьте Secret-манифесты со значениями в git. Если нужен декларативный секрет в репозитории — зашивают только имя и структуру, а значения добавляются через `kubectl create secret generic app-secrets --from-literal=sentry-dsn=...` отдельно или через sealed-secrets/External Secrets в более серьёзных проектах. Для ЛР7 вполне достаточно создать секреты из CLI.

## Куда пишется состояние

Диск контейнера непостоянен: pod пересоздали — всё, что он писал в `/tmp` или в sqlite-файл рядом с приложением, потеряно. Это верно для всех pod'ов, включая те, что «никогда не перезапускались» — перезапуск всё равно рано или поздно случится (сбой ноды, обновление образа, OOMKill). Отсюда правило из темы 4.1: приложение без состояния.

Если состояние на диске всё-таки нужно, в Kubernetes за ним стоят **PV/PVC**: PersistentVolumeClaim — «запрос на диск», PersistentVolume — сам диск, за которым в облаке стоит облачный диск.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: upload-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
```

В Yandex Cloud для этого работает стандартный storage class `yandex-csi` — при создании PVC облачный диск заведётся автоматически и примонтируется к pod'у.

Важное ограничение: `ReadWriteOnce` означает «один узел для записи», поэтому диск нельзя разделить между pod'ами на разных нодах. Файловые загрузки пользователя в облачном проекте почти всегда правильнее отправлять в Object Storage через S3 API, а PVC оставлять для того, что действительно должно жить на локальном диске — в первую очередь для stateful-систем ниже.

## StatefulSet

Для приложений, где имя и диск pod'а должны быть стабильны (базы данных на своих нод, брокеры очередей), существует контроллер StatefulSet: pod'ы получают предсказуемые имена `orders-0`, `orders-1`, каждый со своим PVC, запуск и обновление — по порядку.

Для вашего приложения в ЛР7 это не нужно: выносите базу и очередь в managed-сервисы (дизайн ДЗ7 именно об этом), а StatefulSet если и планируете упоминать в отчёте, то исключительно как рассмотренную и отвергнутую альтернативу с объяснением почему: эксплуатация собственного PostgreSQL в кластере — это бэкапы, failover, обновления на вас, в то же время managed-кластер БД дешевле по суммарным усилиям и, зачастую, надёжнее.
