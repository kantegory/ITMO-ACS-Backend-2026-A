# 02. Pod, Deployment, ReplicaSet, Service

## Pod

Pod — минимальная единица развёртывания Kubernetes. Это не контейнер, а «общая среда для одного или нескольких контейнеров»: они делят сеть (один IP на pod, контейнеры видят друг друга через `localhost`), тома, lifecycle. Для бэкенд-приложения из курса под почти всегда содержит один контейнер — намеренно усложнять sidecar-паттернами не нужно.

Сам по себе pod не переживает сбой: упал — его никто не пересоздаёт. Поэтому pod'ы практически всегда создаются не напрямую, а через деплоймент.

## Deployment

Deployment объявляет: какой образ, сколько реплик, какие правила обновления. Минимальный вариант для одного из ваших микросервисов:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-service
  labels:
    app: orders
spec:
  replicas: 2
  selector:
    matchLabels:
      app: orders
  template:
    metadata:
      labels:
        app: orders
    spec:
      containers:
        - name: orders
          image: registry.example/orders:v1
          ports:
            - containerPort: 3000
          readinessProbe:
            httpGet:
              path: /health        # зависимости: БД, очередь
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /healthz       # только «процесс жив»
              port: 3000
            initialDelaySeconds: 15
            periodSeconds: 20
```

Поле `selector.matchLabels` связывает деплоймент с pod'ами из шаблона: метка `app: orders` в шаблоне должна совпадать с селектором. Если не совпадает, кластер такой манифест вообще не примет — валидация отвечает ошибкой «selector does not match template labels». Типичная ошибка первого раза именно тут.

Проба readiness указывает на `/health` с проверкой зависимостей, liveness — на отдельный `/healthz`, который отвечает «жив» всегда, пока процесс не завис. Почему их нельзя сводить к одному эндпоинту — в файле 04, раздел про health-эндпоинты. Разница между самими probe'ами такая:

- **readinessProbe** отвечает на вопрос «готов ли pod принимать трафик». При неудаче pod не убивается, он просто исключается из балансировки Service. Идеальное применение — зависимость от БД: если база недоступна, pod подождёт и не будет отдавать 500.
- **livenessProbe** отвечает на вопрос «жив ли процесс». При серии неудач kubelet перезапускает контейнер. Злоупотреблять нельзя: liveness на проверку зависимостей (та же недоступная БД) убьёт pod'ы именно в тот момент, когда вам нужно их сохранить для диагностики.

## ReplicaSet

Между деплойментом и pod'ами стоит ReplicaSet — он и следит за количеством реплик. Сам его почти никогда не объявляют вручную; достаточно знать, что при `kubectl apply` деплоймент создаёт новый ReplicaSet, старый остаётся с нулевыми репликами — и поэтому откат на предыдущую версию (`kubectl rollout undo`) мгновенен: достаточно переключить селектор обратно.

## Rolling update

Стратегия обновления по умолчанию: новая версия pod'ов создаётся до удаления старых. Два параметра в `spec.strategy.rollingUpdate`:

```yaml
  strategy:
    rollingUpdate:
      maxSurge: 1        # на один pod выше desired можно разогнаться
      maxUnavailable: 0  # ниже желаемого числа не проваливаться
```

Без readinessProbe это превращается в лотерею: трафик пойдёт на новый pod до того, как приложение внутри него поднялось. С probe'ом новый pod считается готовым только после успешной проверки, и трафик переключается осознанно. Отсюда правило: `maxUnavailable: 0` всегда требует корректного readiness.

## Service

Pod'ы живут коротко и пересоздаются с новыми IP. Service — постоянная сущность поверх них: фиксированное внутреннее DNS-имя и балансировка на текущий набор pod'ов.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  selector:
    app: orders
  ports:
    - port: 80
      targetPort: 3000
```

После этого любой pod в кластере обращается к сервису по имени `orders` (или полностью — `orders.<namespace>.svc.cluster.local`), и между вашими микросервисами межсетевые вызовы описываются так же, как в docker compose, только имена берутся из Service, а не из compose-сервисов. Внутрикластерный DNS — стандартная часть кластера, настраивать его не нужно.
