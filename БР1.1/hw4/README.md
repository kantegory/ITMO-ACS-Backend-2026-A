# ДЗ4 Технический дизайн микросервисной архитектуры

## 1. Назначение работы

RentEase в ЛР1 реализован как монолитное REST API на Spring Boot. В ДЗ4 спроектирован переход к микросервисной архитектуре с правилом `database-per-service`: каждый сервис владеет своими таблицами и изменяет их только через собственный API.

Целевая архитектура должна сохранить пользовательский сценарий из ДЗ3:

`регистрация -> вход -> публикация объявления -> поиск и фильтрация -> просмотр объекта -> переписка`.

Дополнительно в архитектуре сохранены бронирования, договоры, платежи, избранное и отзывы из модели ЛР1.

## 2. Исходный монолит

В монолите используются следующие группы данных:

| Группа | Таблицы | Ответственность |
|---|---|---|
| Пользователи | `user_roles`, `users` | регистрация, вход, роли `tenant`, `landlord`, `admin` |
| Недвижимость | `properties`, `rental_conditions`, `property_photos` | объявления, условия аренды, фотографии |
| Избранное | `favorites` | сохраненные пользователем объекты |
| Бронирования | `bookings` | даты и статусы заявок на аренду |
| Сделки | `rental_contracts`, `payments` | договоры и платежи |
| Переписка | `messages` | сообщения по объекту |
| Отзывы | `reviews` | оценки участников завершенной сделки |

Контроллеры монолита (`AuthController`, `PropertyController`, `BookingController`, `ContractController`, `MessageController`, `FavoriteController`, `ReviewController`) обращаются к одной БД через Spring Data JPA. В целевой архитектуре контроллеры становятся API-слоем соответствующих сервисов, а прямые связи между таблицами разных сервисов заменяются REST-вызовами по UUID.

## 3. Целевая архитектура

Клиент обращается только к API Gateway. Gateway маршрутизирует публичные запросы, проверяет JWT, добавляет `X-Request-Id` и скрывает внутренние адреса сервисов. Внутренние endpoint'ы недоступны из внешней сети.

| Компонент | Порт в локальной среде | Владеет данными | Основные функции |
|---|---:|---|---|
| API Gateway | 8080 | нет | единая точка входа, маршрутизация, CORS, rate limit, корреляция запросов |
| Identity Service | 8081 | `identity_db` | регистрация, вход, роли, выпуск и отзыв refresh-токенов |
| Property Service | 8082 | `property_db` | объявления, условия, фотографии, избранное, поиск, проверка владельца |
| Booking Service | 8083 | `booking_db` | заявки, проверка пересечений дат, статусы бронирования |
| Contract and Billing Service | 8084 | `contract_db` | договоры, платежи, участники сделки |
| Communication Service | 8085 | `communication_db` | сообщения и диалоги по объектам |
| Review Service | 8086 | `review_db` | отзывы и оценки участников завершенных договоров |

Каждый сервис имеет собственные миграции Flyway и собственные учетные данные БД. Общая PostgreSQL-инсталляция допустима только как инфраструктурный кластер: логически это шесть отдельных баз или схем с отдельными владельцами. Сервисам запрещается подключаться к чужой БД.

Исходник схемы взаимодействия находится в [architecture.mmd](architecture.mmd). Для отчета используется также [architecture.svg](architecture.svg).

## 4. Границы сервисов

### 4.1 Identity Service

Владеет учетной записью пользователя. Хранит email, хэш пароля, телефон, ФИО, роль, статус учетной записи и refresh-токены. Пароли не передаются другим сервисам. Access JWT содержит `sub`, `role`, `iss`, `aud`, `exp` и используется сервисами только для авторизации запроса.

### 4.2 Property Service

Владеет жизненным циклом объявления: объектом недвижимости, условиями, фотографиями и активностью. В этой работе сюда же помещены `favorites`, потому что избранное является пользовательским действием над объектом и не требует отдельной бизнес-транзакции.

`landlord_id` и `user_id` в избранном являются внешними UUID-ссылками без внешнего ключа. При необходимости сервис проверяет пользователя через Identity Service, а не читает `identity_db`.

### 4.3 Booking Service

Владеет заявками на бронирование. Поля `tenant_id` и `property_id` хранятся как UUID-ссылки. При создании бронирования сервис синхронно запрашивает у Property Service активность объекта, владельца и цену, а пересечение дат проверяет локально по `booking_db`. При изменении статуса на `confirmed` он передает Contract Service снимок подтвержденной сделки.

### 4.4 Contract and Billing Service

Владеет договором и платежами. В договоре хранится снимок необходимых участников и объекта: `booking_id`, `property_id`, `tenant_id`, `landlord_id`, даты и сумма. Это позволяет истории договора оставаться доступной, даже если объявление позже станет неактивным.

### 4.5 Communication Service

Владеет сообщениями. Он не хранит копию профиля или объявления, а хранит только их UUID. Перед отправкой сообщения сервис проверяет существование получателя в Identity Service и существование активного объекта в Property Service.

### 4.6 Review Service

Владеет отзывами. Перед созданием отзыва проверяет у Contract Service, что договор завершен, автор является его участником и отзыв от этого автора еще не создавался.

## 5. Взаимодействие сервисов

### 5.1 Синхронное взаимодействие

Для операций, где ответ нужен в рамках текущего HTTP-запроса, используется внутренний REST поверх HTTP/JSON:

| Инициатор | Получатель | Причина вызова |
|---|---|---|
| Booking Service | Property Service | проверить активность объекта, владельца и цену |
| Booking Service | Contract and Billing Service | создать договор после подтверждения бронирования |
| Communication Service | Identity Service | проверить получателя и его статус |
| Communication Service | Property Service | проверить объект, к которому относится сообщение |
| Review Service | Contract and Billing Service | проверить право автора оставить отзыв |
| API Gateway | Identity Service | login, register, получение пользователя и управление токенами |

Вызовы выполняются с короткими таймаутами, ограниченным числом повторов и передачей `X-Request-Id`. Для повторяемых команд используются `Idempotency-Key` и уникальные ограничения в базе данных.

### 5.2 Асинхронное расширение

Для следующих этапов курса рекомендуется добавить брокер сообщений и transactional outbox. Booking Service может публиковать события `BookingConfirmed`, `BookingCancelled`, а Contract Service и Communication Service будут обрабатывать их независимо. На этапе ДЗ4 основным контрактом остаются синхронные REST-вызовы: это упрощает миграцию и сохраняет немедленный ответ пользователю.

### 5.3 Поток создания и подтверждения бронирования

1. Tenant отправляет `POST /api/v1/bookings` в Gateway.
2. Gateway проверяет JWT и направляет запрос в Booking Service.
3. Booking Service вызывает `GET /internal/properties/{property_id}/summary` и получает активность, владельца и цену.
4. Booking Service проверяет пересечение дат по собственной `booking_db` и создает заявку со статусом `pending`.
5. Landlord получает список заявок через Gateway и отправляет изменение статуса.
6. Booking Service проверяет владельца через Property Service.
7. При подтверждении Booking Service вызывает `POST /internal/contracts` и передает снимок сделки.
8. Contract and Billing Service идемпотентно создает договор в `contract_db`.

### 5.4 Поток создания отзыва

1. Пользователь отправляет `POST /api/v1/reviews`.
2. Review Service вызывает `GET /internal/contracts/{contract_id}/review-eligibility?author_id=...`.
3. При `eligible=true` сохраняет отзыв локально.
4. При повторной отправке возвращает `409 REVIEW_ALREADY_EXISTS`.

Полный контракт внутренних вызовов находится в [internal-openapi.yaml](internal-openapi.yaml).

## 6. Разделение базы данных

| База | Таблицы после разделения | Внешние UUID-ссылки без FK |
|---|---|---|
| `identity_db` | `user_roles`, `users`, `refresh_tokens` | нет |
| `property_db` | `properties`, `rental_conditions`, `property_photos`, `favorites` | `landlord_id`, `favorites.user_id` |
| `booking_db` | `bookings`, `booking_status_history` | `tenant_id`, `property_id` |
| `contract_db` | `rental_contracts`, `payments` | `booking_id`, `property_id`, `tenant_id`, `landlord_id` |
| `communication_db` | `messages` | `sender_id`, `receiver_id`, `property_id` |
| `review_db` | `reviews` | `contract_id`, `author_id`, `property_id` |

Внутренние связи одного сервиса сохраняются как обычные FK: например, `rental_conditions.property_id -> property_db.properties.id` и `payments.contract_id -> contract_db.rental_contracts.id`. Между базами FK не создаются, иначе сервисы снова будут связаны общей схемой и не смогут развиваться независимо.

Для каждой базы используется отдельная последовательность миграций, например:

```text
identity-service/src/main/resources/db/migration/V1__identity_schema.sql
property-service/src/main/resources/db/migration/V1__property_schema.sql
booking-service/src/main/resources/db/migration/V1__booking_schema.sql
contract-service/src/main/resources/db/migration/V1__contract_schema.sql
communication-service/src/main/resources/db/migration/V1__communication_schema.sql
review-service/src/main/resources/db/migration/V1__review_schema.sql
```

## 7. Внутренний API и ошибки

Все внутренние endpoint'ы:

- доступны только в приватной сети;
- требуют сервисный bearer-токен с `iss`, `aud` и scope;
- принимают `X-Request-Id`;
- возвращают единый объект `Error`;
- не раскрывают SQL, stack trace, пароли и токены.

Основные коды ошибок:

| HTTP | Код | Когда возвращается |
|---:|---|---|
| 400 | `INVALID_REQUEST` | отсутствует обязательное поле или неверный формат UUID/даты |
| 401 | `SERVICE_UNAUTHORIZED` | отсутствует или неверен сервисный токен |
| 403 | `SERVICE_FORBIDDEN` | у вызывающего сервиса нет нужного scope |
| 404 | `PROPERTY_NOT_FOUND`, `USER_NOT_FOUND`, `CONTRACT_NOT_FOUND` | внешняя сущность не найдена |
| 409 | `DATES_UNAVAILABLE`, `CONTRACT_ALREADY_EXISTS`, `REVIEW_ALREADY_EXISTS` | конфликт состояния или повтор идемпотентной команды |
| 422 | `BUSINESS_RULE_VIOLATION` | объект неактивен, договор не завершен, автор не участник |
| 429 | `RATE_LIMITED` | превышен лимит запросов |
| 502/503 | `DEPENDENCY_UNAVAILABLE` | зависимый сервис недоступен или истек таймаут |

Пример ответа ошибки:

```json
{
  "code": "DATES_UNAVAILABLE",
  "message": "Selected dates are already booked",
  "trace_id": "01JEXAMPLE7Y2K9K6K7J2M2Q6M",
  "details": {
    "property_id": "d4162366-8ce4-40f0-84ad-5fc289c1ee36"
  }
}
```

## 8. План перехода от монолита

1. Зафиксировать публичные контракты ДЗ2 и сценарий ДЗ3, добавить `X-Request-Id` и корреляцию логов.
2. Ввести стабильные UUID и запретить новые прямые обращения к таблицам из чужих модулей.
3. Поднять отдельные базы и выполнить независимые Flyway-миграции для Identity и Property Service.
4. Скопировать `users` и роли в `identity_db`, затем `properties`, условия, фотографии и избранное в `property_db`. На время миграции сверять количество записей и контрольные суммы.
5. Вынести Gateway и Identity Service. Сначала направить через Gateway регистрацию и вход, сохранив обратную совместимость публичных URL.
6. Вынести Property Service и перевести GET/POST объявлений на новый сервис. Старые записи сделать read-only после успешной сверки.
7. Вынести Booking Service. На переходном этапе использовать dual-read или outbox, затем оставить единственную запись в `booking_db`.
8. Вынести Contract and Billing Service, затем Communication и Review Service. Для каждого шага включать отдельные feature flags и проверять сценарий ДЗ3.
9. Переключить трафик на Gateway, включить метрики ошибок и latency по каждому dependency call.
10. После периода наблюдения удалить код доступа монолита к вынесенным таблицам и архивировать исходную общую схему.

Критерий завершения миграции: ни один сервис не имеет сетевого доступа к чужой БД, все публичные маршруты проходят через Gateway, а сценарий регистрации, входа, создания объявления, фильтрации, просмотра и переписки проходит через Postman без изменения пользовательского контракта.

## 9. Нефункциональные требования

- доступность Gateway и Identity не ниже 99.5% в учебном окружении;
- таймаут внутреннего REST-вызова 1-2 секунды, не более двух повторов для безопасных GET;
- идемпотентность создания договора и других повторяемых команд;
- BCrypt/Argon2 для паролей, короткоживущий access JWT, ротация refresh-токенов;
- TLS на внешнем контуре и mTLS либо подписанный service JWT во внутреннем контуре;
- структурированные логи с `trace_id`, метрики RPS, latency, error rate и health/readiness endpoints;
- контрактные тесты OpenAPI между Gateway и сервисами;
- резервное копирование каждой базы независимо от остальных.

## 10. Критерии приемки ДЗ4

- границы сервисов и владельцы данных определены однозначно;
- для каждой таблицы указана ровно одна база-владелец;
- между базами нет внешних ключей и прямых SQL-запросов;
- описаны как минимум два межсервисных пользовательских потока;
- внутренние endpoint'ы и схемы находятся в `internal-openapi.yaml`;
- для endpoint'ов описаны успешные ответы и ошибки;
- приведен пошаговый план перехода с контрольными точками и возможностью отката;
- отчет содержит целевую схему, разделение БД, протоколы взаимодействия и вывод.
