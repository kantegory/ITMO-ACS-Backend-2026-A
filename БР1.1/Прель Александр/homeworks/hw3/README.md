# ДЗ3: тестирование API средствами Postman

Автор: Прель Александр, БР1.1. Обновлено 2026-09-09.

## Задача

Реализовать тестирование API средствами Postman, написать тесты внутри Postman и связать их в один комплексный сценарий основного процесса: поиск ресторана и бронирование столика.

## Состав

- `restaurant-booking-dz3.postman_collection.json`: 29 последовательных запросов, 117 проверок.
- `restaurant-booking-local.postman_environment.json`: окружение с адресом локального API, без действующих токенов.
- `ДЗ3_Прель Александр_БР1.1.pdf`: актуальный отчёт по расширенному сценарию.
- `Прель Александр БР 1.1 ДЗ 3.pdf`: предыдущий отчёт о первоначальных 16 запросах.

Одна коллекция подходит для монолита ЛР1 и микросервисов ЛР2. В ЛР2 `baseUrl` указывает на Gateway; внутренние методы не нужны клиенту.

## Ход сценария

| Запросы | Действия | Что проверяется |
| --- | --- | --- |
| 1-5 | Health, регистрация, вход, чтение и изменение профиля | HTTP-коды, JWT, совпадение email, изменение имени |
| 6-11 | Кухни, фильтрация ресторанов, карточка, меню, фото, отзывы | Форматы ответов, результат поиска, ID, пагинация |
| 12-16 | Отзыв, бронь, история, чтение брони, отмена | Создание, принадлежность истории, `confirmed` -> `cancelled` |
| 17-19 | Профиль без токена, неверный пароль, повторный email | 401, 401, 409 и коды ошибок |
| 20-22 | Неверные поля брони, неизвестный ресторан, недостаточная вместимость | 422, 404, 409 |
| 23-24 | Повторная отмена и чтение состояния | 409; отмена действительно сохранена |
| 25-29 | Второй пользователь и попытки доступа к чужой брони | 403, изоляция истории, сохранение доступа владельца |

Для каждого ответа дополнительно проверяются JSON Content-Type и отсутствие поля `passwordHash`.

Email создаётся с UUID, поэтому повторный запуск не сталкивается с уже зарегистрированным пользователем. Переменные `accessToken`, `userId`, `restaurantId`, `reservationId` передают результаты от запроса к запросу. `secondaryToken` используется для проверки прав второго пользователя. Коллекция очищает идентификаторы и токены предыдущего запуска перед новой регистрацией. Токены существуют только во время выполнения и не сохраняются в исходный JSON.

Пример проверки внутри Postman:

```javascript
pm.test('Бронирование создано', () => pm.response.to.have.status(201));
pm.test('Статус confirmed', () => {
  pm.expect(pm.response.json().status).to.eql('confirmed');
});
pm.collectionVariables.set('reservationId', String(pm.response.json().reservationId));
```

## Запуск на ЛР2

Из `БР1.1/Прель Александр/labs/lab2`:

```bash
npm ci --include=dev
npm run setup
npm run build
npm start
```

В другом терминале из той же папки:

```bash
npm run test:postman
```

Команда использует Newman 6.2.2 через npx. Глобальная установка не нужна. Адрес берётся из `.env`; при необходимости: `BASE_URL=http://127.0.0.1:8084 npm run test:postman`.

Для интерфейса Postman импортируйте оба JSON-файла, выберите окружение, установите `baseUrl` равным адресу Gateway и запустите все запросы через Collection Runner в исходном порядке.

## Запуск на ЛР1

Из `labs/lab1`: `npm ci --include=dev`, `npm run build`, затем `npm start` с отдельным тестовым `DATABASE_PATH`. Пример выбора новой базы: `DATABASE_PATH=./data/hw3-new-test.sqlite PORT=8084 npm start`. Выберите имя, которое ещё не занято существующими данными, и свободный порт.

Из `homeworks/hw3`:

```bash
npx --yes newman@6.2.2 run restaurant-booking-dz3.postman_collection.json \
  -e restaurant-booking-local.postman_environment.json \
  --env-var baseUrl=http://127.0.0.1:8084 --reporters cli
```

## Данные и интерпретация результата

Каждый прогон создаёт двух пользователей, отзыв и одно отменённое бронирование. Запускайте коллекцию на отдельной учебной базе. Она не очищает существующие данные. При остановке сценария до отмены может остаться активная бронь; перед повтором отмените свою тестовую бронь либо подготовьте новую тестовую базу.

Ожидаемый результат полного прогона: 29 requests, 117 assertions, 0 failed. Проверки ожидаемых ответов 401/403/404/409/422 тоже должны быть зелёными: это проверка правильного отказа, а не ошибка теста.

Фактические результаты сохранены в [ЛР2 / TEST_RESULTS.md](../../labs/lab2/TEST_RESULTS.md). Дополнительные сценарии отказов сервисов и одновременного бронирования выполняются через `npm test` в ЛР2; они не входят в 117 Postman-проверок.

## Вывод

Postman проверяет полный пользовательский процесс и основные ошибочные действия. Использование одного внешнего контракта позволяет повторить сценарий после перехода от монолита к микросервисам и выявить нарушения совместимости.
