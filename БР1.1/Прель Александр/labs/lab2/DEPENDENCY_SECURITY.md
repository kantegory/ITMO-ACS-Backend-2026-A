# Проверка и обновление зависимостей

Дата проверки: 10.09.2026.

Область проверки: монолит `БР1.1/Прель Александр/labs/lab1` и рабочий микросервисный код `labs/lab2`, используемый ЛР2, ДЗ5 и Docker-образами ЛР3. Оба lockfile обновлены отдельно и проверены чистой установкой.

## Зачем понадобилось обновление

Начальный `npm audit --json` в Lab 1 и Lab 2 сообщил об одинаковых 14 затронутых пакетах: 2 low, 4 moderate, 7 high, 1 critical. Это количество пакетов в отчёте, а не 14 независимых способов атаковать API. Часть записей описывала одну цепочку вложенных зависимостей установки SQLite.

Например, приложение напрямую использует `sqlite3`, тот устанавливает инструменты сборки и `tar`. Уязвимость вложенного пакета может попасть в проект, даже если разработчик не добавлял его самостоятельно. Наш API не принимает tar-архивы: наличие пакета не доказывает доступность этой атаки через HTTP, но оставлять известные дефекты в установочной цепочке тоже нежелательно.

Старые `cacache`, `make-fetch-happen`, `http-proxy-agent`, `@tootallnate/once` и `ip-address` больше не входят в получившийся lockfile. Остальные сопутствующие изменения относятся к деревьям обновлённых пакетов. AMQP-библиотека, TypeScript, JWT, bcrypt и бизнес-код не обновлялись.

В `package.json` подняты минимальные версии трёх прямых зависимостей: sqlite3, TypeORM и Morgan. Для Express добавлено узкое правило:

```json
"overrides": {
  "express": {
    "qs": "6.16.0"
  }
}
```

Оно нужно, потому что Express 4.22.2 ограничивает qs диапазоном `~6.15.1`, не включающим исправленную 6.16.0. Правило действует только внутри дерева Express. При будущем обновлении Express его нужно пересмотреть; не следует переносить этот override на любые версии автоматически.

Lockfile пересчитан через `npm install --package-lock-only --ignore-scripts --no-audit --no-fund`, затем адресно обновлены `body-parser` и `brace-expansion` командой `npm update body-parser brace-expansion --package-lock-only --ignore-scripts --no-audit --no-fund`. Эти команды описывают сделанное обновление, а не требуются для обычного запуска. Для повторения установки используйте только `npm ci`.

## Найденная несовместимость Linux

На macOS arm64 готовый sqlite3 6.0.1 загрузился и прошёл тесты. Первая Linux-сборка тоже завершилась без ошибок, но запуск контейнеров упал:

```text
ERR_DLOPEN_FAILED: GLIBC_2.38 not found
```

Готовый Linux arm64 addon требовал более новую glibc, чем Debian bookworm в закреплённом Node.js-образе. TypeScript проверяет код, но не проверяет ABI нативных библиотек. Первый Compose-прогон остановился на подготовке окружения: восемь сценариев не смогли начаться. Рабочий стенд в этот момент продолжал использовать прежние контейнеры.

Минимальное исправление в пяти Dockerfile:

```dockerfile
RUN npm_config_build_from_source=true npm ci --include=dev --no-audit --no-fund
```

SQLite теперь собирается в build-стадии под тот же базовый Linux, что используется в runtime. Python/make/g++ уже были в build-стадии; дополнительные системные программы на Mac не устанавливались. Базовые образы Node.js и RabbitMQ не менялись. В финальную стадию после `USER node` добавлена проверка:

```dockerfile
RUN node -e "require('sqlite3')"
```

npm 11.9.0 предупреждает о неизвестном env config `build-from-source`; это параметр, который читает установщик нативного модуля. При обновлении npm его поддержку нужно перепроверить. Текущая версия npm закреплена вместе с образом Node.js.

## Воспроизведение

На проверенном Mac: Node.js 24.14.0, npm 11.9.0, Docker Desktop с Compose 5.5.1. Docker Desktop должен быть запущен.

```bash
cd "БР1.1/Прель Александр/labs/lab2"
npm ci --include=dev
npm run typecheck
npm test
npm run test:messaging
npm audit
npm audit --omit=dev

cd "../lab3"
npm run setup
npm run config:check
npm run build
npm test
npm start
npm run status
npm run test:postman
npm run test:smoke
```

`setup` сохраняет существующую `.env.compose`. `npm test` в lab3 создаёт одноразовый Compose-проект и удаляет только его ресурсы. Postman и smoke проверяют основной локальный тестовый стенд и добавляют в него тестовые записи. Команды установки/аудита и первая Docker-сборка требуют доступа к реестрам; это не публикация приложения. Не выполняйте `npm audit fix`, `down --volumes` или глобальную очистку Docker для обычного запуска.

## Границы результата

Ноль в npm audit означает отсутствие известных этому реестру advisories для проверенного графа на дату запроса, а не доказанную безопасность программы. Аудит не проверяет полноценно Linux-пакеты образа, встроенный движок SQLite, RabbitMQ, системный Node.js/npm, отдельно загружаемый Newman или ошибки бизнес-логики. Сканирование образов на CVE и pentest не выполнялись.

Установщик по-прежнему предупреждает об устаревших `prebuild-install` и `glob`. Репозиторий `node-sqlite3` объявлен неподдерживаемым и архивирован: переход на sqlite3 6 устранил текущие npm advisories, но не решает долгосрочное сопровождение. Замена драйвера или базы требует отдельного этапа с проверкой миграции данных. [README sqlite3](https://github.com/TryGhost/node-sqlite3/tree/v6.0.1), [состояние репозитория](https://github.com/TryGhost/node-sqlite3).

Lab 1 также обновлён: все TypeORM-колонки получили явные типы, поэтому `npm run dev` и `npm run seed` теперь работают через `tsx`; добавлен ESLint и локальная Newman-команда. На отдельной базе и на копии существующей базы проверены `npm start`, seed, dev и весь сценарий 29/117. Схема и записи копии существующей базы не изменились. Полный и production audit Lab 1 показывают 0 известных уязвимостей. Исходная база и `.env` сохранены.

Newman 6.2.2 остаётся актуальной опубликованной версией, но одна его вложенная библиотека обращается к устаревшему `fs.F_OK`. Скрипты Lab 1, Lab 2 и Lab 3 передают дочернему процессу `--disable-warning=DEP0176`: скрывается только это известное нефатальное предупреждение, а не весь stderr или все предупреждения Node.js. Сам Newman не добавлен в lockfile приложения и по-прежнему запускается через `npx`.

Старые PDF-отчёты описывают результаты своих этапов и в рамках этого обновления не пересоздаются.
