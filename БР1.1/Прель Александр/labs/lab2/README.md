## Локальный запуск на macOS

Требуется Node.js 22+ и npm. Проверено на Node.js 24.14.0 и npm 11.9.0, macOS arm64.

```bash
cd "БР1.1/Прель Александр/labs/lab2"
npm ci --include=dev
npm run setup
npm run typecheck
npm run build
npm start
```

`setup` создаёт `.env` с правами 0600, случайными JWT_SECRET и SERVICE_KEY, свежим каталогом данных и четырьмя свободными портами в диапазоне 8080-8179. Существующий `.env` сохраняется. Конфигурация перечислена в `.env.example`. Если порт занят уже после настройки, измените соответствующий `*_PORT` в `.env`, затем повторите запуск; чужие процессы останавливать не нужно.

`npm start` запускает четыре дочерних процесса и выводит их адреса. По умолчанию:

| Процесс | Адрес | Назначение |
| --- | --- | --- |
| Gateway | `http://127.0.0.1:8080` | Единый адрес API для клиента |
| Accounts | `http://127.0.0.1:8081` | Пользователи и проверка JWT |
| Catalog | `http://127.0.0.1:8082` | Рестораны, столики, отзывы, меню |
| Bookings | `http://127.0.0.1:8083` | Бронирования |

Проверка из другого терминала:

```bash
curl http://127.0.0.1:8080/health
curl http://127.0.0.1:8080/ready
curl http://127.0.0.1:8080/restaurants
```

`/health` проверяет Gateway, `/ready` проверяет три сервиса. На `/` ожидается JSON с `NOT_FOUND`: это backend без страницы сайта.

Остановка всего стека: `Ctrl-C` в терминале `npm start`. Повторный запуск: `npm start` из этой папки. После изменения TypeScript сначала выполните `npm run build`. Команда запуска использует скомпилированный JavaScript и метаданные декораторов `tsc`.

## Раздельный запуск

Чтобы наблюдать отказ одного сервиса, запускайте по одной команде в четырёх терминалах из `lab2`:

```bash
npm run start:accounts
npm run start:catalog
npm run start:bookings
npm run start:gateway
```

Супервизор `npm start` при неожиданном выходе одного дочернего процесса останавливает остальные свои процессы и возвращает ненулевой код. Это не production-оркестратор и не механизм автоматического восстановления. Раздельный запуск позволяет останавливать и возвращать один сервис вручную; автоматические тесты делают именно это.

## Проверки

```bash
npm run typecheck
npm test
npm run test:postman
```

`npm test` сначала собирает проект. Затем создаёт временные базы и свободные порты, поднимает реальные процессы, выполняет HTTP-запросы, проверяет параллельность и отказы, останавливает только собственные процессы и удаляет только собственный временный каталог. Работающий локальный стек и его данные этот прогон не использует.

## Карта кода

```text
src/
  accounts/       User, auth, профиль, проверка JWT, своя БД
  catalog/        ресторанные entities, каталог, отзывы, seed, своя БД
  bookings/       Reservation, HTTP-клиент каталога, защита от пересечений, своя БД
  gateway/        маршрутизация публичного API, /ready
  shared/         ошибки, HTTP-клиент, middleware, валидация, запуск
scripts/
  setup.cjs      создание локальной конфигурации
  start.cjs      управление четырьмя дочерними процессами
  postman.cjs    запуск коллекции ДЗ3
tests/
  integration.test.cjs
```

Начать чтение удобно с `src/gateway/index.ts`, затем `src/bookings/routes.ts`. В обработчике создания брони видны три шага: получить пользователя по HTTP, получить столики по HTTP, сохранить бронь в своей БД. Подробное объяснение границ и снимков данных есть в ДЗ4.

## Что сохранено и что изменилось

Использованы те же Express, TypeORM, SQLite, bcrypt и JWT, что в ЛР1. Версии прежних зависимостей сохранены; для ДЗ5 добавлены amqplib, его типы и транзитивные пакеты. Общая установка npm в `lab2` используется всеми процессами; общих бизнес-сущностей и общей БД у них нет.

Полный перечень публичных полей и методов остаётся в [ДЗ2 OpenAPI](../../homeworks/hw2/dz2.yaml). В ЛР2 добавлены `/ready`, ответы 503/504 и фиксирование имён в истории. Даты бронирований проверяются на существование в календаре. Соседние интервалы разрешены, пересекающиеся активные брони одного столика запрещены триггером SQLite.

Начальный каталог содержит 3 ресторана, 4 кухни, 7 столиков, меню и ссылки на фотографии. Accounts и Bookings начинают с пустых таблиц. Пользователи, отзывы и брони создаются через API; зависимости между seed разных БД отсутствуют. Прежние данные ЛР1 не читаются и не переносятся автоматически. Подготовлен [план отдельного переноса](../../homeworks/hw4/README.md).

Учебные ограничения: `synchronize: true`, локальная сеть, общий сервисный ключ и отсутствие idempotency-key. Сохранённые названия в брони и отзывах являются снимками на момент создания. Фоновый обмен событиями доступен в режиме ДЗ5; контейнеризация самих сервисов, развёртывание и CI/CD остаются следующими этапами.
