# Итоговый отчет: монолит -> микросервисная архитектура

## 1. Что изменилось по сравнению с монолитом

До этого проект был монолитом: один бекенд, одна кодовая база, одна база данных и единая точка исполнения. В таком варианте все модули (авторизация, пользователи, рестораны, бронирования, отзывы) живут в одном приложении и зависят от одной общей схемы данных.

После разбиения проект стал микросервисной системой, где:

- `auth-service` отвечает только за регистрацию, логин и JWT;
- `users-service` отвечает только за данные пользователя;
- `restaurants-service` отвечает за рестораны, меню, фото и кухни;
- `reservations-service` отвечает за бронирования;
- `reviews-service` отвечает за отзывы;
- `http-logger` служит для логирования HTTP событий;
- каждый сервис имеет свою собственную PostgreSQL базу данных;
- все сервисы находятся в одной Docker-сети и общаются через RabbitMQ;
- HTTP-запросы и события идут не напрямую между сервисами, а через шину сообщений.

### Основные отличия

1. Монолит:
   - один процесс
   - одна БД
   - связанный код
   - тяжело масштабировать отдельные части
   - сложнее деплоить и обновлять

2. Микросервисы:
   - независимые процессы
   - отдельные базы данных по доменам
   - изоляция ответственности
   - проще развивать каждую часть отдельно
   - легче масштабировать и гибче поддерживать

### Что именно было вынесено

- `auth` был вынесен в отдельный сервис, чтобы авторизация и JWT не зависели от остальных модулей;
- `users` стал отдельным сервисом для профилей и пользовательских данных;
- `restaurants` стал независимым сервисом, который хранит данные о ресторанах, меню и фотографиях;
- `reservations` стал отдельным сервисом с жесткой привязкой к пользователю и ресторану;
- `reviews` стал отдельным сервисом для обработки отзывов;
- логирование HTTP запросов вынесено в отдельный `http-logger`.

Это соответствует принципу domain-driven decomposition: каждый сервис отвечает за свой домен и хранит данные только для него.

## 2. Dockerfile: что это и за что отвечает каждая строка

Каждый микросервис имеет свой Dockerfile. Рассмотрим пример из `auth-service`:

```Dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3001
CMD ["npm", "run", "dev"]
```

### Разбор по строкам

#### `FROM node:20-alpine`

Это базовый образ. Он берет готовый контейнер с Node.js 20 и Alpine Linux. Alpine используется для маленького размера образа и быстрой сборки.

#### `WORKDIR /app`

Устанавливает рабочую директорию внутри контейнера. Все дальнейшие команды выполняются в `/app`.

#### `COPY package*.json ./`

Копирует в контейнер файлы `package.json` и `package-lock.json` (если есть). Это нужно, чтобы сначала установить зависимости, а не копировать весь проект целиком.

#### `RUN npm install`

Устанавливает зависимости проекта внутри контейнера. Из-за этого сервис получает все пакеты, которые нужны для запуска (Express, PostgreSQL client, JWT, RabbitMQ client и т.д.).

#### `COPY . .`

Копирует весь исходный код сервиса в контейнер: `src`, конфиги, JSON-описания API и прочие файлы.

#### `EXPOSE 3001`

Указывает, что сервис слушает порт 3001. Это документирование порта для удобства и внутренней структуры Docker, но сам порт реально пробрасывается через `docker-compose.yml`.

#### `CMD ["npm", "run", "dev"]`

Запускает приложение при старте контейнера. В этом проекте используется режим разработки (`npm run dev`), то есть приложение стартует через ts-node-dev/Node dev-сервер и автоматически реагирует на изменения в коде.

### Почему нужны Dockerfile у каждого сервиса

- каждый сервис имеет собственные зависимости;
- у каждого можно отдельно задавать порт и окружение;
- можно собирать и запускать их независимо;
- это дает возможность запускать весь стек целиком через один `docker-compose.yml`.

## 3. Docker Compose: что делает каждая строка

Ниже рассмотрен общий файл `docker-compose.yml`.

```yaml
version: "3.8"
services:
  rabbitmq:
    image: rabbitmq:3-management
    container_name: rbmq
    ports:
      - "5672:5672"
      - "15672:15672"
    environment:
      RABBITMQ_DEFAULT_USER: guest
      RABBITMQ_DEFAULT_PASS: guest
    networks:
      - app_net
```

### Разбор по блокам

#### `version: '3.8'`

Версия синтаксиса Compose. Определяет формат файла и совместимость.

#### `services:`

Начинает описание всех контейнеров в проекте.

#### `rabbitmq:`

Создает контейнер с RabbitMQ.

#### `image: rabbitmq:3-management`

Загружает готовый Docker-образ RabbitMQ с веб-интерфейсом управления.

#### `container_name: rbmq`

Назначает контейнеру фиксированное имя, чтобы удобно обращаться к нему по имени внутри сети.

#### `ports:`

Пробрасывает порты хоста на контейнер:

- `5672` — порт AMQP для общения сервисов;
- `15672` — порт веб-интерфейса RabbitMQ UI.

#### `environment:`

Содержит переменные окружения:

- логин: `guest`
- пароль: `guest`

#### `networks:`

Подключает контейнер к общей сети `app_net`.

---

### Блок базы данных

```yaml
auth-db:
  image: postgres:16-alpine
  restart: unless-stopped
  environment:
    POSTGRES_DB: auth_db
    POSTGRES_USER: app
    POSTGRES_PASSWORD: app
  ports:
    - "5433:5432"
  volumes:
    - auth-db-data:/var/lib/postgresql/data
  networks:
    - app_net
```

Что делает:

- поднимает PostgreSQL отдельный для auth сервиса;
- задает имя БД `auth_db`;
- создает пользователя `app` с паролем `app`;
- пробрасывает порт 5433 на хост, чтобы можно было подключиться снаружи;
- сохраняет данные в локальном docker volume `auth-db-data`;
- монтирует контейнер в сеть `app_net`.

Такое же правило повторяется для всех сервисов:

- `users-db` — 5434
- `restaurants-db` — 5435
- `reservations-db` — 5436
- `reviews-db` — 5437

Это важно: каждая часть приложения хранит свои данные отдельно.

---

### Блок auth-service

```yaml
auth-service:
  build: ./auth-service
  working_dir: /app
  volumes:
    - ./auth-service:/app
  command: npm run dev
  depends_on:
    - auth-db
    - rabbitmq
  ports:
    - "3001:3001"
  environment:
    - JWT_SECRET=secret
    - RABBITMQ_URL=amqp://guest:guest@rabbitmq:5672
    - DB_HOST=auth-db
    - DB_PORT=5432
    - DB_USER=app
    - DB_PASSWORD=app
    - DB_NAME=auth_db
  networks:
    - app_net
```

#### Что здесь происходит

- `build: ./auth-service` — собирает контейнер по Dockerfile из папки сервиса;
- `working_dir: /app` — рабочая директория внутри контейнера;
- `volumes` — монтирует локальную папку сервиса в контейнер, чтобы изменения в коде применялись быстро;
- `command: npm run dev` — запускает dev-режим;
- `depends_on` — сервис ждёт, пока поднимутся база и RabbitMQ;
- `ports` — пробрасывает 3001 порт на хост;
- `environment` — передает переменные окружения:
  - `JWT_SECRET` для подписи токена;
  - `RABBITMQ_URL` для соединения с RabbitMQ;
  - `DB_HOST=auth-db` — имя контейнера БД;
  - `DB_PORT=5432` — внутренний порт PostgreSQL внутри сети;
  - `DB_USER`, `DB_PASSWORD`, `DB_NAME` — параметры подключения.

То же правило используется и для остальных сервисов.

---

### Блок `http-logger`

```yaml
http-logger:
  build: ./http-logger
  working_dir: /app
  command: node index.js
  depends_on:
    - rabbitmq
  environment:
    - RABBITMQ_URL=amqp://guest:guest@rabbitmq:5672
  networks:
    - app_net
```

Здесь сервис получает сообщения из RabbitMQ и логирует их в консоль. Он не имеет своей БД, потому что его задача — только слушать обмен `http.requests` и сохранять/выводить события.

---

### Блок `volumes` и `networks`

```yaml
volumes:
  auth-db-data:
  users-db-data:
  restaurants-db-data:
  reservations-db-data:
  reviews-db-data:

networks:
  app_net:
    driver: bridge
```

- `volumes` — локальные тома для долговременного хранения данных PostgreSQL;
- `networks` — одна общая виртуальная сеть для всех контейнеров;
- `driver: bridge` — стандартная сетка Docker, которая позволяет контейнерам общаться по именам.

Именно благодаря общей сети серверам достаточно писать `auth-db`, `rabbitmq`, `restaurants-service` и т.д., а не использовать IP-адреса.

## 4. Как устроено взаимодействие между микросервисами

В проекте взаимодействие строится по двум принципам:

1. HTTP — для обычных запросов и синхронных вызовов;
2. RabbitMQ — для событий и асинхронной коммуникации.

### Пример синхронного взаимодействия

Когда пользователь оформляет бронь, `reservations-service` может потребовать информацию о ресторане из `restaurants-service` или данные пользователя из `users-service`.

Поэтому в архитектуре есть внутренние маршруты вида:

- `/internal/users/:id`
- `/internal/restaurants/:id`
- `/internal/reservations/validate`

Это внутренние endpoints, которые используются между сервисами, но не предназначены для внешнего клиента.

### Пример асинхронного взаимодействия

Когда пользователь успешно зарегистрировался, `auth-service` публикует событие:

```json
{
  "event": "user.registered",
  "data": {
    "id": 123,
    "email": "user@example.com"
  }
}
```

Это событие попадает в exchange `app.events` и может быть обработано другими сервисами, например `reviews-service`, который подписан на события и может реагировать на них.

Когда любой сервис получает HTTP-запрос, он публикует его в exchange `http.requests`.

В свою очередь `http-logger` читает это и пишет JSON-сообщение в лог.

Таким образом:

- внешние HTTP-вызовы идут в сервисы;
- сервисы публикуют события в RabbitMQ;
- логгер и другие подписчики читают сообщения;
- система становится менее связанной и более устойчивой к изменениям.

## 5. Как работает RabbitMQ в этом проекте

RabbitMQ — это брокер сообщений. Он принимает сообщения от производителей и отправляет их подписчикам.

В проекте используется два основных обменника:

### `http.requests`

Это fanout exchange.

- каждый сервис, получив запрос, публикует JSON в него;
- `http-logger` подписан на этот exchange;
- он получает все HTTP-события и логирует их.

Fanout означает: сообщение отправляется всем подписчикам, которые подписаны на этот exchange.

### `app.events`

Это topic exchange.

- сервисы публикуют события по типам, например `user.registered` или `reservation.created`;
- подписчики подписаны на темы и получают только те события, которые им нужны.

Пример:

```javascript
ch.publish("app.events", "user.registered", Buffer.from(msg));
```

Здесь:

- exchange: `app.events`
- routing key: `user.registered`
- подписчик может использовать `#` или конкретный ключ для получения нужных событий.

### Почему RabbitMQ полезен

- декомпозирует зависимость между сервисами;
- уменьшает плотную связанность;
- позволяет вести логирование и события независимо;
- позволяет расширять функциональность без переписывания всего приложения.

### Важный момент

RabbitMQ не заменяет HTTP. Он дополняет архитектуру:

- HTTP — для синхронных пользовательских вызовов;
- RabbitMQ — для асинхронных событий и интеграций.

## 6. Что такое `index.ts` и чем он отличается от `index.js`

### `index.ts`

Это TypeScript-файл. Он используется в сервисах `auth-service`, `users-service`, `restaurants-service`, `reservations-service`, `reviews-service`.

Плюсы TypeScript:

- типизация данных;
- меньше ошибок на этапе разработки;
- автодополнение и поддержка IDE;
- безопаснее для крупных проектов;
- простое сопровождение сложной логики.

Пример:

```ts
const PORT = process.env.PORT ? parseInt(process.env.PORT) : 3001;
const pool = new Pool({
  host: process.env.DB_HOST || "localhost",
  port: Number(process.env.DB_PORT || 5433),
  user: process.env.DB_USER || "app",
  password: process.env.DB_PASSWORD || "app",
  database: process.env.DB_NAME || "auth_db",
});
```

Здесь TS помогает контролировать типы и значения, например `number`, `string`, `Request`, `Response` и т.д.

### `index.js`

Это обычный JavaScript-файл. Он используется в `http-logger`.

Плюсы JavaScript:

- проще, короче и легче для маленьких утилитарных сервисов;
- не требуется компиляция TypeScript;
- проще для простого логирования и демонстраций.

Пример из `http-logger/index.js`:

```js
const amqp = require("amqplib");
const RABBITMQ_URL =
  process.env.RABBITMQ_URL || "amqp://guest:guest@rabbitmq:5672";
```

Здесь логика максимально проста: подключиться к RabbitMQ, подписаться на exchange и выводить сообщения в консоль.

### Основное различие

- `index.ts` — это типизированный, более безопасный код для бизнес-логики сервисов;
- `index.js` — это простой, быстрый код для маленькой служебной утилиты.

### Также важно

TypeScript в конечном итоге компилируется в JavaScript, поэтому в продакшене оба варианта в итоге становятся обычным Node.js-кодом. Но TS дает преимущества на этапе разработки.

---

## 7. Итог

В результате монолит была разбита на несколько независимых сервисов. Каждый сервис:

- имеет свою ответственность;
- хранит свои данные в отдельной БД;
- общается через HTTP и RabbitMQ;
- запускается через Docker;
- работает в общей сети и при этом не зависит напрямую от остальных.

Это уже соответствует базовым принципам микросервисной архитектуры: слабая связанность, высокая автономность и масштабируемость.

Стек проекта можно запустить одной командой:

```bash
docker compose up -d --build
```

После этого сервисы будут работать на отдельных портах, а RabbitMQ будет обеспечивать обмен событиями между ними.
