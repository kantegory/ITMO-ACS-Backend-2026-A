## 1. Цель

Ограничить CPU и RAM контейнеров, прогнать нагрузку без автоскейла, зафиксировать просадку latency и по ней решить, когда включать HPA.

## 2. Ограничение ресурсов

Без лимитов сервис занимает всю машину, и точку насыщения не видно. CPU и RAM режутся заранее.

В Compose (`docker-compose.yml`):

```yaml
deploy:
  resources:
    limits:
      cpus: "0.25"
      memory: 256M
```

В kind для gateway, catalog и employer:

```text
requests: cpu 50m, memory 64Mi
limits:   cpu 100m, memory 128Mi
replicas: 1
HPA: отключен
```

## 3. Нагрузка без HPA

Сценарий `load/stress.js` поднимает arrival rate примерно до 180 RPS на vacancies и skills.

```powershell
$env:BASE_URL = "http://localhost:8080"
k6 run load/stress.js
```

Фрагмент результата (полный лог: `artifacts/k6-stress-no-hpa.log`):

```text
  █ THRESHOLDS

    http_req_duration
    ✓ 'p(95)<800' p(95)=491.96ms
    ✓ 'p(99)<2000' p(99)=736.7ms

    http_req_failed
    ✓ 'rate<0.05' rate=0.00%

  █ TOTAL RESULTS

    http_req_duration..............: avg=53.99ms med=1.55ms max=1.19s p(90)=131.88ms p(95)=491.96ms
    http_req_failed................: 0.00%
    dropped_iterations.............: 103
```

После прогона `kubectl top`:

```text
catalog    71m / limit 100m
employer   97m / limit 100m
gateway    57m / limit 100m
```

Ошибок HTTP еще нет, но хвост latency уже плохой: p95 около 492 ms при единицах миллисекунд на легкой нагрузке. Employer почти упирается в limit CPU, k6 дропает итерации. Одной реплики с узким limit мало - пора подключать автоскейлинг.

## 4. Включение HPA

```powershell
.\scripts\k8s-metrics-server.ps1
kubectl apply -f k8s/30-hpa.yaml
k6 run load/stress.js
```

HPA для gateway, catalog и employer: целевой CPU 60%, от 1 до 4 реплик.

Фрагмент (`artifacts/k6-stress-with-hpa.log`):

```text
  █ THRESHOLDS

    http_req_duration
    ✓ 'p(95)<800' p(95)=2.53ms
    ✓ 'p(99)<2000' p(99)=53.24ms

    http_req_failed
    ✓ 'rate<0.05' rate=0.00%

  █ TOTAL RESULTS

    http_req_duration..............: avg=4.74ms med=1.53ms max=1.09s p(90)=1.78ms p(95)=2.53ms
    dropped_iterations.............: 41
```

После нагрузки HPA поднял реплики:

```text
catalog    4 replicas, cpu ~78%/60%
employer   4 replicas, cpu ~114%/60%
gateway    3 replicas, cpu ~73%/60%
```

## 5. Сравнение

| | без HPA (1 реплика) | с HPA |
|--|---------------------|-------|
| p95 | 491.96 ms | 2.53 ms |
| p99 | 736.7 ms | 53.24 ms |
| dropped iterations | 103 | 41 |
| реплики | 1 / 1 / 1 | до 4 / 4 / 3 |

Базовые сценарии health, catalog и vacancies и их логи лежат в `artifacts/k6-*.log`.

## 6. Вывод

Сначала режем ресурсы в compose и k8s limits, гоняем stress без автоскейла и смотрим рост p95 и dropped iterations. Когда CPU упирается в limit и latency уезжает (у нас около сотен RPS при limit 100m), включаем HPA. После масштабирования p95 упал с примерно 492 ms до 2.5 ms при той же нагрузке.
