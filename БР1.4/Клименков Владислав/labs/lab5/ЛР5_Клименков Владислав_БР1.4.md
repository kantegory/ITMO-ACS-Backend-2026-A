## 1. Цель работы и постановка задач

Цель работы — перевести настройку удалённого сервера и развёртывание
приложения RecipeHub на **Ansible**, то есть описать состояние сервера
декларативно (Infrastructure as Code) вместо набора императивных bash-скриптов,
и при этом **не сломать уже работающий автодеплой** из GitHub Actions.

К моменту начала работы приложение было полностью готово и работало в
production на VPS, а развёртывание выполнялось скриптами
`deploy/scripts/setup-server.sh` (первичная настройка) и
`deploy/scripts/deploy.sh` (обновление). Автодеплой по пушу в `main` был
реализован в рамках предыдущего домашнего задания: GitHub Actions заходил на
сервер по SSH и запускал `deploy.sh`.

Задачи работы:

1. **Настройка сервера.** Описать установку и настройку всего, что нужно для
   работы приложения: базовые пакеты, swap, Docker Engine и compose-plugin,
   файрвол UFW, nginx в режиме обратного прокси.
2. **Развёртывание приложения.** Описать получение кода, генерацию
   `services/*/.env` из шаблонов, сборку и запуск стека, проверку
   работоспособности.
3. **Сохранение автодеплоя.** Перевести CI на Ansible так, чтобы пуш в `main`
   по-прежнему приводил к автоматическому развёртыванию актуальной версии.
4. **Сохранение привычных команд.** Команды из `deploy/README.md`
   (`setup-server.sh`, `deploy.sh`) должны продолжать работать — они
   превращаются в тонкие обёртки над playbook-ами.
5. **Идемпотентность.** Повторный прогон не должен ничего менять, если сервер
   уже находится в описанном состоянии.

Дополнительное требование, вытекающее из эксплуатации: сервер — это небольшой
VPS (2 vCPU, 2 ГБ RAM), поэтому решение не должно быть тяжёлым, а деплой не
должен требовать много ресурсов и не должен допускать параллельных сборок.

## 2. Исходное состояние проекта

### 2.1. Что уже было

RecipeHub — микросервисное приложение на Node.js + TypeScript:

| Сервис | Каталог | Порт | Назначение |
| --- | --- | --- | --- |
| `api-gateway` | `services/api-gateway` | 3000 | JWT-аутентификация, маршрутизация, Swagger UI |
| `user` | `services/user` | 3001 | пользователи, подписки, авторизация |
| `recipe` | `services/recipe` | 3002 | рецепты, шаги, комментарии, оценки, избранное |

Инфраструктура уже была вынесена в каталог `deploy/`:

- `docker-compose.yml` — базовый стек из шести контейнеров (3 сервиса,
  2 PostgreSQL, RabbitMQ);
- `deploy/docker-compose.prod.yml` — прод-оверрайд: порты привязаны к
  `127.0.0.1`, ротация логов, `restart: unless-stopped`;
- `deploy/nginx/recipe-hub.conf` — конфиг nginx как обратного прокси;
- `deploy/scripts/setup-server.sh` — императивный скрипт первичной настройки;
- `deploy/scripts/deploy.sh` — императивный скрипт обновления;
- `.github/workflows/deploy.yml` — CI: пуш в `main` → SSH → `deploy.sh`.

### 2.2. Чем был плох императивный подход

Скрипты работали, но у них были системные недостатки:

1. **Нет описания желаемого состояния.** Скрипт отвечает на вопрос «что
   сделать», а не «каким должен быть сервер». Проверить, соответствует ли
   сервер конфигурации, можно только прочитав весь скрипт.
2. **Идемпотентность достигалась вручную.** Каждый шаг требовал собственных
   проверок (`if ! command -v ...`, `if [ ! -f ... ]`, `grep -q ...`). Любая
   новая правка легко ломала повторный запуск.
3. **Дублирование.** Конфиг nginx лежал отдельным файлом и копировался
   скриптом; обновление конфига означало «не забыть скопировать и
   перезагрузить nginx».
4. **Нет частичного применения.** Нельзя было применить только часть
   настроек (например, только nginx) без запуска всего скрипта.
5. **Нет «сухого прогона».** Нельзя было посмотреть, что изменится, не меняя
   сервер.
6. **Много «магии» в shell.** Ошибки вроде `set -o pipefail` под dash
   обнаруживаются только в момент запуска на конкретном сервере.

## 3. Обоснование выбора Ansible и проектные решения

### 3.1. Почему Ansible

- **Агентless.** На сервер не нужно ставить агента: Ansible работает по SSH.
  Для VPS с 2 ГБ RAM это важно.
- **Декларативность и идемпотентность.** Модули (`apt`, `template`, `copy`,
  `systemd`, `ufw` и т. д.) сами приводят систему к нужному состоянию и
  сообщают `ok`/`changed`.
- **YAML и роли.** Конфигурация читается как документация, роли дают
  переиспользование и теги для частичного применения.
- **`--check --diff`.** Встроенный «dry run» с показом diff-ов.
- **Уже есть SSH-доступ и CI.** Ansible не требует менять способ доставки:
  он использует тот же SSH-ключ, что и раньше.
- **Не оверхед.** В отличие от Kubernetes/Terraform, Ansible не требует
  дополнительной инфраструктуры и подходит для одного VPS.

Рассматривались альтернативы:

| Вариант | Почему не выбран |
| --- | --- |
| Оставить bash-скрипты | не решает главную проблему — отсутствие описания состояния |
| Terraform | управляет облачными ресурсами, а не конфигурацией уже существующего сервера |
| Kubernetes / Docker Swarm | избыточно для одного VPS с 2 ГБ RAM |
| Puppet / Chef | требуют агента и более тяжёлые в освоении |
| `community.docker.docker_compose_v2` | лишняя коллекция и хуже переносит долгую сборку на слабом VPS (см. 3.3) |

### 3.2. Ключевые проектные решения

| Решение | Обоснование |
| --- | --- |
| Два playbook-а: `site.yml` и `deploy.yml` | `site.yml` описывает **хост целиком** (для нового сервера), `deploy.yml` — только **приложение** (для частых обновлений и CI). CI не должен переустанавливать пакеты и трогать файрвол на каждый пуш |
| Роль `app` используется обоими playbook-ами | логика деплоя описана один раз; нет расхождений между «первым» и «последующими» деплоями |
| Инвентарь берёт хост из переменных окружения | IP-адрес и пользователь не попадают в git; в CI используются те же имена, что и в GitHub Secrets (`SSH_HOST`, `SSH_USER`, `SSH_KEY`) |
| `ansible.builtin.command` вместо `community.docker.docker_compose_v2` | не тянем ещё одну коллекцию; `docker compose up -d --build` — стабильная точка входа, одинаково работающая на слабом VPS |
| nginx-конфиг стал шаблоном роли (`recipe-hub.conf.j2`) | одна копия правды; параметры (`server_name`, upstream, `client_max_body_size`) вынесены в `group_vars`; старая копия `deploy/nginx/recipe-hub.conf` удалена |
| Скрипты оставлены тонкими обёртками | пользовательские команды из README не меняются; вся логика — в playbook-ах |
| Ansible Vault сознательно не добавлялся | секреты уже не хранятся в git (`.env` генерируются из `.env.example`), а Vault усложнил бы работу без реальной необходимости; при переходе на настоящие секреты его можно добавить |
| `become: true` на уровне play | все задачи выполняются от root (сервер настроен на root-доступ), но при необходимости playbook без изменений заработает и с sudo-пользователем |

## 4. Архитектура решения

### 4.1. Схема управления

```text
    ноутбук разработчика (WSL)            GitHub Actions (ubuntu-latest)
              │                                      │
              │  ansible-playbook site.yml           │  ansible-playbook deploy.yml
              │  (полная настройка)                  │  (только приложение)
              │                                      │
              └──────────────┬───────────────────────┘
                             │ SSH (ключ)
                             ▼
                    ┌──────────────────┐
                    │  VPS recipehub   │
                    │  Ubuntu 24.04    │
                    │  139.100.225.216 │
                    └────────┬─────────┘
                             │
              ┌──────────────┴───────────────┐
              │                              │
        site.yml (редко)               deploy.yml (каждый пуш в main)
        common → docker                app: git → .env → compose → health
        → firewall → nginx → app
              │
              ▼
   ┌──────────────────────────────────────────┐
   │ nginx :80  (только он смотрит наружу)    │
   │   └─ 127.0.0.1:3000 api-gateway          │
   │        ├─ user-service :3001             │
   │        └─ recipe-service :3002           │
   │  PostgreSQL ×2, RabbitMQ — внутри сети   │
   └──────────────────────────────────────────┘
```

### 4.2. Путь запроса и пути деплоя

- **Запрос пользователя:** интернет → nginx `:80` → `127.0.0.1:3000`
  (api-gateway) → docker-сеть → нужный сервис. `/api/internal/*` блокируется
  на nginx (`403`).
- **Первый деплой нового сервера:** `setup-server.sh` → `site.yml` → все роли
  по порядку.
- **Обычное обновление:** пуш в `main` → GitHub Actions → `deploy.yml` →
  роль `app` → `git` → `docker compose up -d --build` → health-check.

## 5. Структура Ansible-каталога

```text
deploy/
├── docker-compose.prod.yml          # прод-оверрайд (не менялся)
├── README.md                        # runbook: быстрый старт, Ansible, TLS, секреты
├── AGENTS.md                        # заметки по инфраструктуре для агентов/разработчиков
├── ansible/
│   ├── ansible.cfg                  # инвентарь по умолчанию, пути к ролям/коллекциям
│   ├── requirements.yml             # зависимости: community.general
│   ├── inventory/
│   │   └── prod.yml                 # хост recipe-hub; SSH_HOST/SSH_USER/SSH_KEY из env
│   ├── group_vars/
│   │   └── all.yml                  # единая точка переменных
│   ├── site.yml                     # полная настройка хоста + деплой
│   ├── deploy.yml                   # только роль app (вызывается из CI)
│   └── roles/
│       ├── common/                  # пакеты, часовой пояс, swap
│       │   └── tasks/main.yml
│       ├── docker/                  # Docker Engine, compose-plugin, daemon.json
│       │   ├── defaults/main.yml
│       │   ├── handlers/main.yml
│       │   ├── tasks/main.yml
│       │   └── templates/daemon.json.j2
│       ├── firewall/                # UFW
│       │   └── tasks/main.yml
│       ├── nginx/                   # обратный прокси
│       │   ├── handlers/main.yml
│       │   ├── tasks/main.yml
│       │   └── templates/recipe-hub.conf.j2
│       └── app/                     # код, .env, стек, health-check
│           └── tasks/main.yml
└── scripts/
    ├── setup-server.sh              # бутстрап Ansible + site.yml
    └── deploy.sh                    # обёртка над deploy.yml
```

Принцип разделения: **`site.yml` — «каким должен быть сервер», `deploy.yml` —
«какая версия приложения должна работать»**. Это позволяет применять
инфраструктурные изменения редко и осознанно, а деплой делать часто и безопасно.

## 6. Конфигурация: `ansible.cfg`, инвентарь, `group_vars`

### 6.1. `ansible.cfg`

```ini
[defaults]
inventory = inventory/prod.yml
roles_path = roles
collections_path = ~/.ansible/collections:/usr/share/ansible/collections

host_key_checking = True
interpreter_python = auto_silent
retry_files_enabled = False
nocows = True

[ssh_connection]
pipelining = True
```

Что здесь важно:

- `inventory` и `roles_path` заданы относительно **текущего каталога**, поэтому
  playbook-и запускаются из `deploy/ansible` (это задокументировано в README и
  в `AGENTS.md`). Обёртки сами делают `cd`.
- `host_key_checking = True` — SSH-ключ хоста проверяется. В CI `known_hosts`
  заранее наполняется через `ssh-keyscan` (см. раздел 10), локально хост
  попадает туда при первом обычном `ssh`.
- `pipelining = True` — меньше round-trip-ов, что заметно на слабом канале и
  слабом VPS.
- `retry_files_enabled = False` — в репозитории не появляются `.retry`-файлы.

### 6.2. Инвентарь `inventory/prod.yml`

```yaml
all:
  hosts:
    recipe-hub:
      ansible_host: "{{ lookup('env', 'SSH_HOST') }}"
      ansible_user: "{{ lookup('env', 'SSH_USER') | default('root', true) }}"
      ansible_ssh_private_key_file: >-
        {{ lookup('env', 'SSH_KEY')
           | default(lookup('env', 'HOME') ~ '/.ssh/id_ed25519', true) }}
```

- Имя хоста в инвентаре — логическое (`recipe-hub`), реальный адрес берётся из
  `SSH_HOST`.
- Пользователь по умолчанию — `root`, как настроено на сервере.
- Ключ по умолчанию — `~/.ssh/id_ed25519`, но можно переопределить через
  `SSH_KEY`.
- **IP-адрес не хранится в git.** Это осознанное решение: репозиторий
  публичный, а инфраструктурные адреса не должны быть в истории.

Запуск с ноутбука:

```bash
cd deploy/ansible
export SSH_HOST=139.100.225.216 SSH_USER=root
ansible-playbook deploy.yml
```

### 6.3. `group_vars/all.yml` — единая точка переменных

```yaml
# --- Приложение ---
app_dir: "{{ lookup('env', 'APP_DIR') | default('/opt/recipe-hub', true) }}"
repo_url: "{{ lookup('env', 'REPO_URL') | default('https://github.com/KlimVladMaks/recipe-hub.git', true) }}"
branch: "{{ lookup('env', 'BRANCH') | default('main', true) }}"

services:
  - api-gateway
  - user
  - recipe

compose_flags: "-f docker-compose.yml -f deploy/docker-compose.prod.yml"

health_url: "http://127.0.0.1:3000/api/api-gateway-health"
health_retries: 60
health_delay: 3

# --- Хост ---
timezone: Etc/UTC

swap_file: /swapfile
swap_size_mb: 2048

# --- nginx ---
nginx_server_name: "_"
nginx_client_max_body_size: "20m"
nginx_gateway_upstream: "127.0.0.1:3000"
```

Почему так:

- `app_dir`, `repo_url`, `branch` читаются из env — это позволяет использовать
  один и тот же playbook и в CI, и локально, и в обёртках, не дублируя
  значения. **Приоритет:** extra vars (`-e`) > `group_vars` > `defaults` роли.
- `services` — список сервисов, у которых есть `.env.example`; роль `app`
  проходит по нему циклом.
- `compose_flags` — прод-стек всегда запускается как
  `docker compose -f docker-compose.yml -f deploy/docker-compose.prod.yml`,
  ровно как раньше в `deploy.sh`.
- `health_url` — health-эндпоинт шлюза; `health_retries`/`health_delay` дают
  до 180 секунд ожидания (`60 × 3 с`) — с запасом для сборки на 2 vCPU.
- `timezone: Etc/UTC` — на сервере и в логах CI используется UTC, поэтому
  playbook не должен менять часовой пояс уже работающего сервера. Значение
  остаётся настраиваемым.

### 6.4. `requirements.yml`

```yaml
---
collections:
  - name: community.general
    version: ">=9.0.0"
```

Коллекция нужна для двух модулей:

- `community.general.ufw` — управление файрволом;
- `community.general.timezone` — часовой пояс.

`ansible-core` в `requirements.yml` не входит: он ставится отдельно (apt,
pip или venv). Минимальная поддерживаемая версия — **2.16**: в `setup-server.sh`
она проверяется программно, а CI ставит `ansible-core>=2.16,<2.19`.

## 7. Playbook-и

### 7.1. `site.yml` — полное состояние сервера

```yaml
---
- name: Настройка VPS и развёртывание RecipeHub
  hosts: all
  become: true

  pre_tasks:
    - name: Проверить, что целевая ОС — Ubuntu 22.04+
      ansible.builtin.assert:
        that:
          - ansible_distribution == 'Ubuntu'
          - ansible_distribution_major_version | int >= 22
        fail_msg: >-
          Поддерживаются только Ubuntu 22.04 / 24.04, обнаружено
          {{ ansible_distribution }} {{ ansible_distribution_version }}
        quiet: true
      tags: always

  roles:
    - { role: common, tags: [common] }
    - { role: docker, tags: [docker] }
    - { role: firewall, tags: [firewall] }
    - { role: nginx, tags: [nginx] }
    - { role: app, tags: [app] }
```

Особенности:

- **Порядок ролей не случаен.** `common` ставит базовые пакеты (в том числе
  `ufw` и `git`), `docker` — Docker, `firewall` — правила UFW, `nginx` —
  прокси, и только затем `app` запускает стек, который уже за прокси.
- **`assert` в `pre_tasks`** не даёт применить playbook к неподдерживаемой ОС.
  `quiet: true` убирает лишний вывод об успехе.
- **Теги** позволяют применять только нужную часть:
  `ansible-playbook site.yml --tags nginx`. Тег `always` у проверки ОС
  гарантирует, что она выполняется при любом наборе тегов.
- **Первый прогон** настраивает весь сервер; **повторный** ничего не меняет,
  кроме задачи сборки в роли `app`.

### 7.2. `deploy.yml` — только приложение

```yaml
---
- name: Обновление развёрнутого RecipeHub
  hosts: all
  become: true
  # Роли app факты не нужны — пропускаем сбор фактов, чтобы деплой был быстрее.
  gather_facts: false

  roles:
    - { role: app, tags: [app] }
```

- Ровно этот playbook вызывает GitHub Actions.
- `gather_facts: false` — небольшой, но приятный выигрыш: роль `app` не
  использует факты, а сбор фактов на каждом деплое — лишние секунды.
- Playbook **не ставит пакеты и не трогает конфиг хоста**. Это важное
  свойство: обычный деплой не может случайно изменить файрвол или nginx.

## 8. Роли

### 8.1. Роль `common`

Задачи: базовые пакеты, часовой пояс, swap.

| Задача | Модуль | Что делает |
| --- | --- | --- |
| Обновить кэш apt | `apt` | `update_cache: true`, `cache_valid_time: 3600` |
| Установить базовые пакеты | `apt` | `ca-certificates`, `curl`, `gnupg`, `git`, `lsb-release`, `ufw`, `install_recommends: false` |
| Установить часовой пояс | `community.general.timezone` | приводит TZ к `{{ timezone }}` |
| Создать swap-файл | `shell` | `fallocate` с fallback на `dd`, `chmod 600`, `mkswap`, `creates` |
| Проверить подключённые swap | `command` | `swapon --show=NAME --noheadings`, `changed_when: false`, `check_mode: false` |
| Подключить swap-файл | `command` | `swapon`, только если файла нет в выводе |
| Прописать swap в fstab | `lineinfile` | строка `{{ swap_file }} none swap sw 0 0` |

Ключевые решения:

```yaml
- name: Создать swap-файл
  ansible.builtin.shell: |
    set -euo pipefail
    if ! fallocate -l {{ swap_size_mb }}M {{ swap_file }} 2>/dev/null; then
        dd if=/dev/zero of={{ swap_file }} bs=1M count={{ swap_size_mb }} status=none
    fi
    chmod 600 {{ swap_file }}
    mkswap {{ swap_file }} >/dev/null
  args:
    creates: "{{ swap_file }}"
    # /bin/sh на Ubuntu — это dash, а ему `set -o pipefail` незнаком.
    executable: /bin/bash
  tags: [swap]
```

- `creates` делает задачу идемпотентной: если файл уже есть, она просто
  пропускается.
- `fallocate` быстрый, но на некоторых ФС недоступен — поэтому fallback на
  `dd`.
- **`executable: /bin/bash`** — важный нюанс: `ansible.builtin.shell` по
  умолчанию запускает `/bin/sh`, а на Ubuntu это `dash`, который не знает
  `set -o pipefail`. Этот баг был пойман на тестовом контейнере (см. раздел 13).
- Проверка `swapon --show` выполняется с `check_mode: false`, чтобы в
  `--check`-режиме она всё-таки прочитала реальное состояние, а не была
  пропущена.
- Тег `swap` позволяет пропустить управление swap на серверах, где оно
  настроено иначе: `--skip-tags swap`.

### 8.2. Роль `docker`

Задачи:

| Задача | Модуль | Что делает |
| --- | --- | --- |
| Создать `/etc/apt/keyrings` | `file` | каталог `0755` |
| Скачать GPG-ключ Docker | `get_url` | `https://download.docker.com/linux/ubuntu/gpg` → `docker.asc`, `0644` |
| Подключить репозиторий | `apt_repository` | строка `deb [arch=… signed-by=…] … {{ release }} stable`, файл `docker`, `update_cache` |
| Установить пакеты | `apt` | `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin` |
| Настроить ротацию логов | `template` | `/etc/docker/daemon.json` из шаблона + `notify` |
| Включить Docker | `systemd` | `enabled: true`, `state: started` |

Архитектура в репозитории определяется автоматически:

```yaml
repo: >-
  deb [arch={{ ansible_architecture
               | replace('x86_64', 'amd64')
               | replace('aarch64', 'arm64') }}
  signed-by=/etc/apt/keyrings/docker.asc]
  https://download.docker.com/linux/ubuntu {{ ansible_distribution_release }} stable
```

Шаблон `templates/daemon.json.j2`:

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "{{ docker_log_max_size }}",
    "max-file": "{{ docker_log_max_file }}"
  }
}
```

со значениями по умолчанию из `defaults/main.yml`: `10m` и `3`. Это защита
40-гигабайтного диска VPS от переполнения логами.

**Handler:**

```yaml
- name: Перезапустить Docker
  ansible.builtin.systemd:
    name: docker
    state: restarted
```

Handler вызывается только если файл `daemon.json` реально изменился. На уже
настроенном сервере содержимое шаблона побайтово совпадает с существующим
файлом, поэтому Docker не перезапускается и контейнеры не «моргают». Это
специально проверялось сравнением сгенерированного файла с текущим на сервере.

### 8.3. Роль `firewall`

```yaml
- name: Разрешить SSH
  community.general.ufw:
    rule: allow
    port: "{{ item }}"
    proto: tcp
  loop:
    - "22"
    - "80"
    - "443"

- name: Политика по умолчанию для входящих — запретить
  community.general.ufw:
    direction: incoming
    policy: deny

- name: Политика по умолчанию для исходящих — разрешить
  community.general.ufw:
    direction: outgoing
    policy: allow

- name: Включить UFW
  community.general.ufw:
    state: enabled
```

Критически важен **порядок**: сначала разрешаются порты (в первую очередь
SSH), и только потом файрвол включается и задаются политики `deny` по
умолчанию. Если сделать наоборот, можно потерять доступ к серверу.

Модуль `ufw` при `state: enabled` включает файрвол неинтерактивно
(`ufw --force enable`), поэтому playbook можно запускать из CI и по SSH без
подтверждений.

### 8.4. Роль `nginx`

| Задача | Модуль | Что делает |
| --- | --- | --- |
| Установить nginx | `apt` | `state: present` |
| Разложить конфиг | `template` | `sites-available/recipe-hub`, `notify` |
| Включить сайт | `file` | symlink в `sites-enabled` |
| Убрать дефолтный сайт | `file` | `state: absent` |
| Включить nginx | `systemd` | `enabled`, `started` |

Конфиг вынесен в шаблон
`roles/nginx/templates/recipe-hub.conf.j2`; параметры берутся из
`group_vars/all.yml`. Смысловая часть конфига (обратный прокси) не менялась —
изменился только способ доставки и добавлена параметризация:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name {{ nginx_server_name }};

    access_log /var/log/nginx/recipe-hub.access.log;
    error_log  /var/log/nginx/recipe-hub.error.log;

    # запрет внутренних service-to-service маршрутов извне
    location /api/internal/ {
        return 403;
    }

    location / {
        proxy_pass http://{{ nginx_gateway_upstream }};
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        "upgrade";
        proxy_connect_timeout 60s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;
    }

    client_max_body_size {{ nginx_client_max_body_size }};
}
```

В конце шаблона осталась закомментированная TLS-заготовка с инструкцией по
certbot — как и в прежнем конфиге.

**Handler** перезагружает nginx только после успешной проверки конфига:

```yaml
- name: Проверить и перезагрузить nginx
  ansible.builtin.shell: |
    set -euo pipefail
    nginx -t
    systemctl reload nginx
  args:
    executable: /bin/bash
  changed_when: true
```

Почему shell, а не модуль: нужно выполнить два действия подряд и **не**
перезагружать nginx, если `nginx -t` нашёл ошибку. Простая `systemd`-задача
этого не гарантирует. `reload` вместо `restart` не рвёт текущие соединения.

### 8.5. Роль `app`

Самая важная роль: именно она выполняется на каждом деплое.

| Задача | Модуль | Что делает |
| --- | --- | --- |
| Получить код | `git` | clone при отсутствии, fetch + checkout при наличии; `version: {{ branch }}`, `accept_hostkey: true` |
| Проверить `.env.example` | `stat` | цикл по `services`, регистрация результатов |
| Создать `.env` | `copy` | `remote_src: true`, `force: false`, `mode: 0600` |
| Собрать и запустить стек | `command` | `docker compose {{ compose_flags }} up -d --build` в `{{ app_dir }}` |
| Дождаться готовности API | `uri` | `until: status == 200`, 60 попыток по 3 с |
| Показать результат | `debug` | адрес health-эндпоинта и подсказка по логам; пропускается в `--check` |

Фрагменты:

```yaml
- name: Получить код приложения (клонировать или обновить)
  ansible.builtin.git:
    repo: "{{ repo_url }}"
    dest: "{{ app_dir }}"
    version: "{{ branch }}"
    update: true
    accept_hostkey: true
```

Модуль `git` заменяет `git clone`/`git pull --ff-only`: при отсутствии каталога
он клонирует репозиторий, при наличии — делает fetch и приводит рабочее дерево
к указанной ветке. `.env` при этом не затрагивается, потому что он в
`.gitignore`.

```yaml
- name: Создать services/*/.env из .env.example (если ещё нет)
  ansible.builtin.copy:
    src: "{{ app_dir }}/services/{{ item.item }}/.env.example"
    dest: "{{ app_dir }}/services/{{ item.item }}/.env"
    remote_src: true
    force: false
    mode: "0600"
  loop: "{{ app_env_examples.results }}"
  loop_control:
    label: "{{ item.item }}"
  when: item.stat.exists
```

- `force: false` — **существующий `.env` никогда не перезаписывается**. Это
  принципиально: на сервере в `.env` могут быть изменённые секреты, и деплой
  не должен их затирать.
- `mode: "0600"` — права на чтение/запись только для владельца (root).
- `stat` перед `copy` нужен, чтобы аккуратно пропустить отсутствующий
  `.env.example` и не падать.

```yaml
- name: Собрать и запустить стек
  ansible.builtin.command:
    cmd: docker compose {{ compose_flags }} up -d --build
    chdir: "{{ app_dir }}"
  changed_when: true
```

- `chdir` гарантирует, что compose найдёт `docker-compose.yml` и
  `deploy/docker-compose.prod.yml`.
- **Задача всегда `changed`.** Это осознанно и описано в README: пересборка
  образов — и есть деплой, даже если код не изменился. Остальные задачи
  остаются идемпотентными, поэтому на повторном прогоне меняется только эта.

```yaml
- name: Дождаться готовности API
  ansible.builtin.uri:
    url: "{{ health_url }}"
    status_code: 200
  register: app_health
  until: app_health.status | default(0) == 200
  retries: "{{ health_retries }}"
  delay: "{{ health_delay }}"
  changed_when: false
```

- `default(0)` нужен, потому что при ошибке соединения поле `status` может
  отсутствовать; без него выражение `until` упало бы с ошибкой шаблонизации.
- Задача повторяется до 60 раз с паузой 3 секунды. Если API так и не поднялся,
  playbook **падает** — CI не покажет «успех» при нерабочем приложении.

## 9. Скрипты-обёртки

### 9.1. `deploy/scripts/setup-server.sh`

Задача скрипта — **только подготовить Ansible** и запустить `site.yml`. Вся
настройка сервера уже описана в ролях.

Алгоритм:

1. Проверка, что скрипт запущен от root.
2. Определение каталога репозитория:
   - если скрипт лежит внутри клонированного репозитория — используется он;
   - иначе (сценарий `curl … | bash`) репозиторий клонируется в `APP_DIR`
     (по умолчанию `/opt/recipe-hub`), потому что playbook-у нужны файлы из
     репозитория.
3. Проверка версии `ansible-playbook` (нужна `>= 2.16`):
   - если версия подходит — используется она;
   - иначе ставится `ansible-core` из apt;
   - если apt дал слишком старую версию (например, на Ubuntu 22.04) — создаётся
     venv `/opt/ansible-venv` и ставится свежий `ansible-core`;
   - если ни то, ни другое не удалось — понятная ошибка.
4. Установка коллекций: `ansible-galaxy collection install -r requirements.yml`.
5. Запуск `site.yml` с локальным подключением:
   `ansible-playbook -i localhost, -c local site.yml`.

Проверка версии реализована через `sort -V`, без внешних зависимостей:

```bash
version_ge() {
    [ -n "$1" ] || return 1
    [ "$(printf '%s\n%s\n' "$2" "$1" | sort -V | head -1)" = "$2" ]
}
```

Параметры (`REPO_URL`, `BRANCH`, `APP_DIR`) можно переопределить переменными
окружения — они экспортируются и подхватываются `group_vars`.

### 9.2. `deploy/scripts/deploy.sh`

Тонкая обёртка над `deploy.yml`:

1. проверяет, что репозиторий и `deploy.yml` на месте;
2. если `ansible-playbook` нет в `PATH`, но есть venv из `setup-server.sh` —
   добавляет его в `PATH`;
3. запускает `ansible-playbook -i localhost, -c local deploy.yml`.

Команда `bash /opt/recipe-hub/deploy/scripts/deploy.sh` работает как раньше и
проверена на реальном сервере.

## 10. Автоматический деплой в GitHub Actions

### 10.1. Workflow целиком

`.github/workflows/deploy.yml`:

```yaml
name: Deploy to VPS

on:
  push:
    branches: [main]
  workflow_dispatch:

concurrency:
  group: deploy-production
  cancel-in-progress: false

jobs:
  deploy:
    name: Pull, rebuild and restart on VPS
    runs-on: ubuntu-latest
    timeout-minutes: 30

    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Prepare SSH key and known_hosts
        run: |
          set -euo pipefail
          mkdir -p ~/.ssh
          printf '%s\n' "${{ secrets.SSH_PRIVATE_KEY }}" > ~/.ssh/deploy_key
          chmod 600 ~/.ssh/deploy_key
          ssh-keyscan -H "${{ secrets.SSH_HOST }}" >> ~/.ssh/known_hosts 2>/dev/null

      - name: Install Ansible
        run: |
          set -euo pipefail
          python3 -m venv "$RUNNER_TEMP/ansible-venv"
          "$RUNNER_TEMP/ansible-venv/bin/pip" install --quiet --upgrade pip
          "$RUNNER_TEMP/ansible-venv/bin/pip" install --quiet 'ansible-core>=2.16,<2.19'
          echo "$RUNNER_TEMP/ansible-venv/bin" >> "$GITHUB_PATH"
          "$RUNNER_TEMP/ansible-venv/bin/ansible-galaxy" collection install \
            -r deploy/ansible/requirements.yml

      - name: Run Ansible deploy playbook on VPS
        run: |
          set -euo pipefail
          export SSH_HOST="${{ secrets.SSH_HOST }}"
          export SSH_USER="${{ secrets.SSH_USER }}"
          export SSH_KEY="$HOME/.ssh/deploy_key"
          cd deploy/ansible
          ansible-playbook deploy.yml

      - name: Smoke test through nginx
        run: |
          set -euo pipefail
          curl -fsS "http://${{ secrets.SSH_HOST }}/api/api-gateway-health"
```

### 10.2. Что и почему изменилось по сравнению с ДЗ6

| Было (ДЗ6) | Стало (ЛР5) | Почему |
| --- | --- | --- |
| SSH → `bash deploy/scripts/deploy.sh` | `actions/checkout` → установка Ansible → `ansible-playbook deploy.yml` | деплой стал декларативным; CI применяет playbook напрямую |
| репозиторий на runner не нужен | нужен checkout | playbook и роли лежат в репозитории |
| ключ и `known_hosts` | осталось без изменений | контракт с сервером сохранён |
| `concurrency: deploy-production` | осталось | на 2 vCPU нельзя допускать параллельных сборок |
| smoke-test `curl` | осталось | финальная проверка «снаружи» |

Дополнительные решения:

- **Ansible ставится в venv** (`$RUNNER_TEMP`), а не через `pip install --user`:
  это не зависит от политики PEP 668 на образе runner-а и даёт
  воспроизводимую версию.
- **Версия ограничена `>=2.16,<2.19`** — та же, что проверяется в
  `setup-server.sh`; протестировано на 2.18.19.
- **`SSH_KEY` передаётся через переменную окружения** в shell-шаге, а не
  жёстко прописанным путём: инвентарь читает `SSH_KEY` через `lookup('env')`.
- **`ssh-keyscan -H`** заранее добавляет ключ хоста в `known_hosts`, поэтому
  `host_key_checking = True` не мешает CI.
- **`site.yml` из CI не запускается.** Он меняет пакеты, файрвол и nginx — это
  нужно только при первичной настройке или осознанном изменении
  инфраструктуры. Обычный пуш не должен иметь таких прав.

### 10.3. Секреты репозитория

| Secret | Назначение |
| --- | --- |
| `SSH_HOST` | IP/домен VPS |
| `SSH_USER` | пользователь для деплоя (`root`) |
| `SSH_PRIVATE_KEY` | приватный CI-ключ (ed25519) |

Используется **отдельный** CI-ключ, а не личный: его можно отозвать, удалив
строку из `~/.ssh/authorized_keys`, не затрагивая личный доступ. Имена
секретов совпадают с именами переменных, которые читает инвентарь, — это
упрощает отладку.

## 11. Безопасность и работа с секретами

1. **Секреты не в git.** В репозитории только `services/*/.env.example` с
   демонстрационными значениями. На сервере роль `app` создаёт `.env` из
   шаблона **только если файла ещё нет** (`force: false`) и с правами `0600`.
2. **IP-адрес не в git.** Инвентарь читает `SSH_HOST` из окружения.
3. **CI-ключ отдельный.** Приватный ключ хранится только в GitHub Secrets.
4. **Наружу открыт только nginx.** В `docker-compose.prod.yml` порты БД,
   RabbitMQ и самого шлюза привязаны к `127.0.0.1`; UFW разрешает только
   `22`, `80`, `443`.
5. **Внутренние маршруты закрыты.** `/api/internal/*` возвращает `403` на
   nginx; сервисы общаются друг с другом напрямую по docker-сети.
6. **Проверка конфига nginx перед reload.** Битый конфиг не уронит живой
   nginx: handler выполняет `nginx -t` и только затем `systemctl reload`.
7. **Порядок в файрволе.** Порты открываются до включения UFW — нельзя
   случайно отрезать себе SSH.
8. **`host_key_checking = True`.** Не отключаем проверку ключа хоста; в CI
   `known_hosts` готовится заранее.
9. **Принцип минимальных изменений в CI.** Деплой применяет только роль
   `app`; инфраструктурные роли доступны только при ручном запуске `site.yml`.

Отдельно про Ansible Vault: он **сознательно не использовался**. Сейчас
секретов в репозитории нет, а `.env` живут только на сервере. Если появится
необходимость хранить в git зашифрованные значения (например, пароли
мониторинга), Vault добавляется без переделки структуры: `group_vars` уже
вынесены в отдельный файл.

## 13. Идемпотентность

Идемпотентность — ключевое свойство решения. Она обеспечивается так:

| Механизм | Где используется |
| --- | --- |
| Декларативные модули (`apt`, `template`, `copy`, `file`, `systemd`, `lineinfile`) | сами сравнивают состояние и меняют только при необходимости |
| `creates` | создание swap-файла |
| `force: false` | `.env` не перезаписывается |
| `notify` + handlers | рестарт Docker / reload nginx только при реальном изменении файла |
| Сравнение состояния перед действием | `swapon --show` перед `swapon`; `stat` перед `copy` |
| `changed_when: false` | задачи проверки состояния не считаются изменениями |
| `--check --diff` | предпросмотр без применения |

Проверка на реальном сервере:

```text
Прогон 1: ok=30 changed=6
Прогон 2: ok=29 changed=1   # только пересборка стека
```

Почему задача сборки всегда `changed`: `docker compose up -d --build` — это
и есть деплой; пересборка образов выполняется при каждом запуске. Если бы
задача рапортовала `ok`, вывод playbook-а скрывал бы факт выполнения работы.
При этом все остальные задачи на повторном прогоне дают `ok`, поэтому
«шумный» `changed` ровно один и его причина понятна.

Для демонстрации идемпотентности без пересборки:

```bash
ansible-playbook -i localhost, -c local site.yml \
  --tags common,docker,firewall,nginx
# → changed=0
```

### 15.6. Частые проблемы

| Симптом | Причина и решение |
| --- | --- |
| `Не найден ansible-playbook` | не выполнен `setup-server.sh`; поставить Ansible вручную: `apt install ansible-core` + `ansible-galaxy collection install -r deploy/ansible/requirements.yml` |
| `couldn't resolve module/action 'community.general.ufw'` | не установлена коллекция |
| `no hosts matched` / пустой инвентарь | не задан `SSH_HOST` или playbook запущен не из `deploy/ansible` |
| `Permission denied (publickey)` | не указан ключ: `export SSH_KEY=~/.ssh/<ключ>` |
| API не ответил за 3 минуты | смотреть логи стека; обычно нехватка RAM/swap |

## 16. Ограничения и направления развития

1. **Ansible Vault не используется.** Пока секретов в git нет, это
   осознанно. При появлении секретов в репозитории — добавить Vault и
   `ansible-vault`-пароль в CI.
2. **Нет отдельной роли мониторинга.** Следующий логичный шаг — роль
   `monitoring` (node-exporter/Prometheus/Grafana) с портами на `127.0.0.1` и
   доступом через SSH-туннель. Структура ролей к этому готова.
3. **Версия `community.general` не ограничена сверху.** Сейчас ставится
   13.5.0 и работает с `ansible-core 2.16`. Если будущая мажорная версия
   потребует более свежий core, стоит добавить верхнюю границу в
   `requirements.yml`.
4. **Нет тестового job в CI.** CI не запускает E2E-тесты перед деплоем
   (так было и до работы); тесты прогоняются локально/вручную. При желании
   тестовый шаг добавляется в тот же workflow перед деплоем.
5. **Один хост.** Инвентарь рассчитан на один сервер; при масштабировании
   добавляются группы хостов и роли с ролями БД/брокера.
6. **`become: true` рассчитан на root.** Playbook без изменений заработает и с
   sudo-пользователем, но это не проверялось на реальном сервере.
