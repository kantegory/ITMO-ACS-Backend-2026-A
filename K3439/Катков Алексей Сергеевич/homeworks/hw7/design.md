# Облачная инфраструктура сервиса рецептов

## Задача

Спроектировать облачное развёртывание сервиса рецептов. Описать ресурсы, сетевую связность, отказоустойчивость и способ доставки обновлений.

## Ход работы

### Компоненты

Приложение состоит из четырёх сервисов. API Gateway принимает запросы, передаёт их сервисам и возвращает ответы. Auth хранит пользователей и подписки, Recipe - рецепты и состав блюд, Social - комментарии, лайки и закладки. При создании рецепта Recipe публикует событие `recipe.created` в topic exchange `recipe.events`. Social получает события из отдельной очереди. У каждого сервиса собственная база PostgreSQL.

### Схема связей

```text
Клиент → HTTPS → балансировщик → Ingress → API Gateway
                                               ├→ Auth → PostgreSQL / auth
                                               ├→ Recipe → PostgreSQL / recipe
                                               └→ Social → PostgreSQL / social
                                                      └→ Recipe (проверка рецепта)
                                  Recipe → RabbitMQ → Social (recipe.created)
```

### Ресурсы и сеть

| Ресурс | Учебный стенд | Целевая конфигурация |
| --- | --- | --- |
| Kubernetes | k3s на облачной Linux-ВМ, 4 vCPU, 8 ГБ RAM и SSD от 40 ГБ | Managed Service for Kubernetes, региональный кластер, три рабочие ноды в разных зонах |
| Входящий трафик | Ingress k3s, TLS на входе, доступ с адресов участников | L7-балансировщик и TLS, публичный DNS, внутренние Service типа ClusterIP |
| PostgreSQL 16 | Три экземпляра StatefulSet с отдельными базами и PVC | Managed Service for PostgreSQL, три логические базы с разными ролями, хосты в трёх зонах |
| RabbitMQ | StatefulSet с одной репликой и PVC | Три узла в разных зонах, quorum queue после миграции очереди |
| Доставка образов | Артефакт GitHub Actions с SHA коммита и контрольной суммой архива, при необходимости GHCR | GHCR, доставка образов по digest, отдельные права на публикацию и чтение |

Учебная ВМ может находиться у любого облачного провайдера. Целевой профиль описан на примере Yandex Cloud. В целевом профиле рабочие узлы и БД размещаются в приватных подсетях VPC, по одной на зону. Внешний балансировщик принимает TCP 443. Доступ к управляющему API ограничен администратором и CI. PostgreSQL принимает TCP 5432 от рабочих узлов, RabbitMQ принимает TCP 5672 от Recipe и Social. Внешний доступ к внутренним сервисам закрыт. Для загрузки образов и обновлений рабочим узлам нужен выход в интернет через NAT или выделенный маршрут.

### Размещение и восстановление

Gateway, Auth, Recipe и Social запускаются как Deployment. Для целевой конфигурации каждой службе нужны минимум две реплики, распределение по зонам, readiness-проба и PodDisruptionBudget с `minAvailable: 1`. Региональный кластер устраняет зависимость control plane от одной зоны. При отказе пода Service направляет запросы в готовые реплики. При отказе зоны должна оставаться ёмкость для базовой нагрузки на оставшихся узлах.

HPA использует CPU относительно requests. Начальные requests для приложений составляют 100m CPU и 128 MiB памяти, стартовый лимит - 500m и 256 MiB. Для Gateway и Recipe планируется диапазон от 2 до 6 реплик с целью CPU 60%. Нагрузочный прогон должен подтвердить ресурсный профиль и запас подключений к PostgreSQL. Увеличение числа реплик не решает проблему медленного запроса к БД.

Для БД предусмотрены ежедневные резервные копии, журнал восстановления и пробное восстановление в отдельный экземпляр. Целевые RPO 15 минут и RTO 60 минут измеряются на учении. PVC учебного стенда переживают перезапуск подов. Отказ единственной ВМ потребует восстановления из внешней копии.

Миграции схемы должны выполняться один раз на выпуск перед раскаткой реплик. Для первого запуска существующего приложения синхронизацию схемы можно провести на одной реплике каждого сервиса. Для последующих выпусков нужно отключить автоматическую синхронизацию и применять версионированные миграции.

Один durable exchange и одна очередь используются в учебном стенде. Для перехода на quorum queue нужно развернуть новую очередь и переключить потребителя после обработки старого backlog. Для гарантии уведомлений о записанных рецептах в целевом профиле потребуется transactional outbox и подтверждение публикации. Сейчас запись в БД и отправка события выполняются последовательно.

### Доставка и наблюдаемость

При обновлении ветки GitHub Actions собирает четыре образа и выполняет интеграционную проверку. Учебный стенд получает образы из артефакта с контрольной суммой SHA-256. В целевом профиле образы хранятся в GHCR, а учётные данные Kubernetes доступны заданию деплоя через GitHub Environment. Обновление проверяется через `kubectl rollout status` и HTTP-запрос через входной маршрут. Предыдущие образы сохраняются для отката. Изменения схемы БД должны быть совместимы с откатом приложения.

Prometheus собирает метрики узлов, подов и HTTP-проверок. Grafana отображает CPU, RAM, диск, сеть, доступность сервисов и динамику HPA. Loki принимает логи контейнеров. Предварительные цели для чтения рецептов составляют не менее 30 запросов/с при p95 до 250 мс, p99 до 600 мс и доле ошибок ниже 1%.

## Вывод

Приложение можно развернуть на одной облачной ВМ для защиты. Для отказоустойчивости целевой профиль распределяет вычисление и состояние по зонам и предусматривает восстановление данных и откат релиза.
