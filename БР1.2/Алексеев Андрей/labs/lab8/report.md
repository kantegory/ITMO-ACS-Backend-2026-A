# Задача

Провести нагрузочное испытание в Kubernetes, включить HPA и обосновать лимиты ресурсов.

# Исходные данные

Один узел K3s на VPS, auth-service и PostgreSQL, закрытый NodePort для тестовых запросов. Сценарий — `infra/semester2/auth/load.js`, показатели CPU поступают из Metrics Server.

# Ход работы

Metrics Server передаёт данные CPU в HPA. Цель HPA — 60% запрошенного CPU, 1–2 реплики. Измеряем RPS, p95/p99 и ошибки входа через k6. В Grafana сверяем CPU процесса, JVM heap, частоту запросов и число pod. Pod использует requests CPU 120m/RAM 320Mi и limits CPU 400m/RAM 640Mi.

JVM настроена с heap 160 MiB, metaspace 144 MiB, ограниченным code cache и пулом из восьми соединений. Суммарные запросы двух реплик оставляют запас под базу и компоненты кластера. Всплески выше лимита обнаруживаются по latency и сравнению с CPU usage.

# Проверка результата

Событие Kubernetes SuccessfulRescale зафиксировало размер 2 с причиной «CPU выше цели». Два pod стали готовы принимать трафик. Пробы получают до 5 секунд на ответ. Увеличены requests с 90m/256Mi до 120m/320Mi и limits с 350m/448Mi до 400m/640Mi. Используется Recreate для планового выпуска на одном узле, чтобы старый и новый JVM-процесс не конкурировали при rollout.

| Профиль | Запросы | RPS | p95, мс | p99, мс | Ошибки |
| --- | ---: | ---: | ---: | ---: | ---: |
| Локальный smoke | 29 | 0.94 | 107 | 117 | 0.0% |
| Kubernetes baseline при старте второй реплики | 8 | 0.10 | 12001 | 12001 | 50.0% |
| Kubernetes scale | 164 | 1.23 | 4561 | 8344 | 0.0% |
| Kubernetes baseline после прогрева | 52 | 0.80 | 1258 | 2728 | 0.0% |

При 4 виртуальных пользователях все 164 запроса завершились без ошибок, но p95 составил 4,56 с при цели в 1 с. После прогрева при 1 виртуальном пользователе p95 снизился до 1,26 с. Обе реплики делят ресурсы одного физического узла.

Prometheus в Kubernetes вернул p95 около 4,27 с для окна 5 минут и метрики heap. k6 фиксировал время от клиента до HTTP-ответа, поэтому его p95 отличается от оценки по серверной гистограмме.

# Вывод

Результат автоскейлинга оценивается по фактическим репликам и их готовности. Пороговые значения задержки учитывают мощность ВМ и стоимость BCrypt.
