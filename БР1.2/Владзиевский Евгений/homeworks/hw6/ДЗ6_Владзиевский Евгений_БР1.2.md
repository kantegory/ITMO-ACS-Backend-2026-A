## 1. Цель работы

Настроить автоматическое развёртывание бэкенд-приложения на удалённый сервер
с триггером на обновление кода в репозитории на определённой ветке.

Исходная точка — ЛР4: приложение уже развёрнуто вручную на сервере
`192.168.1.245` (Docker Compose + nginx в режиме обратного прокси), процедура
развёртывания оформлена скриптами `server-setup.sh` и `deploy.sh`. Задача
ДЗ6 — выполнять те же шаги автоматически силами CI-системы.

В качестве CI выбран **GitHub Actions**: репозиторий курса и форк с работами
уже живут на GitHub, отдельная CI-система не требуется.

## 2. Выбор схемы CI/CD

Ключевое ограничение: сервер `192.168.1.245` находится **в локальной сети** и
не имеет публичного IP. Облачный раннер GitHub (`ubuntu-latest`) физически не
может открыть SSH-соединение к такому адресу, поэтому классическая схема
«cloud runner → ssh → сервер» не работает.

Рассмотренные варианты:

| Вариант | Как работает | Почему не выбран / выбран |
|---|---|---|
| Cloud runner + SSH | Раннер GitHub подключается по SSH к серверу | Нужен публичный IP или проброс портов на роутере — у сервера их нет |
| Cloud runner + VPN-туннель (Tailscale, Cloudflare Tunnel) | Раннер входит в приватную сеть через сторонний сервис | Добавляет внешнюю зависимость и отдельный аккаунт ради учебной задачи |
| **Self-hosted runner на сервере** | Раннер установлен на самом сервере и сам опрашивает GitHub по исходящему HTTPS | **Выбран.** Входящий доступ и белый IP не нужны, деплой выполняется локально — без SSH и без хранения приватных ключей в секретах |

Дополнительный плюс self-hosted runner'а: в секретах репозитория не нужно
хранить ни SSH-ключ, ни пароль сервера — раннер уже находится внутри
периметра, а права ограничены пользователем `ubuntu`.

Итоговая схема:

```
  git push в ветку lab-4
          │
          ▼
  GitHub (репозиторий lk2322/ITMO-ACS-Backend-2026-A)
          │  задание на выполнение workflow
          │  (раннер забирает его сам, исходящее HTTPS-соединение)
          ▼
  ┌──────────────────── 192.168.1.245 ────────────────────┐
  │  actions.runner (systemd-служба)                      │
  │        │                                              │
  │        ├─ rsync исходников  → /opt/rental-app         │
  │        ├─ docker compose build / up -d                │
  │        ├─ обновление конфига nginx + reload           │
  │        └─ smoke-тест http://127.0.0.1/health          │
  └───────────────────────────────────────────────────────┘
```

## 3. Установка self-hosted runner

Раннер установлен в `/opt/actions-runner` и зарегистрирован в репозитории
`lk2322/ITMO-ACS-Backend-2026-A` с меткой `rental-server`:

```bash
# токен регистрации получается через GitHub API (живёт 1 час)
TOKEN=$(gh api -X POST \
  repos/lk2322/ITMO-ACS-Backend-2026-A/actions/runners/registration-token \
  --jq '.token')

sudo mkdir -p /opt/actions-runner && sudo chown ubuntu:ubuntu /opt/actions-runner
cd /opt/actions-runner
VER=2.338.2
URL=https://github.com/actions/runner/releases/download
curl -fsSL -o runner.tar.gz \
  "$URL/v$VER/actions-runner-linux-x64-$VER.tar.gz"
tar xzf runner.tar.gz && rm runner.tar.gz
sudo ./bin/installdependencies.sh

./config.sh --unattended --replace \
  --url https://github.com/lk2322/ITMO-ACS-Backend-2026-A \
  --token "$TOKEN" \
  --name rental-server \
  --labels rental-server \
  --work _work

# регистрация как systemd-службы: раннер поднимается после перезагрузки
sudo ./svc.sh install ubuntu
sudo ./svc.sh start
```

Состояние службы:

```
● actions.runner.lk2322-ITMO-ACS-Backend-2026-A.rental-server.service
     Loaded: loaded (/etc/systemd/system/actions.runner...service; enabled)
     Active: active (running)
```

Раннер в API репозитория:

```json
{"name":"rental-server","status":"online","busy":false,
 "labels":["self-hosted","Linux","X64","rental-server"]}
```

Раннер работает от пользователя `ubuntu`, который состоит в группе `docker`
и имеет право на `sudo` — этого достаточно для управления Docker Compose и
перезагрузки nginx.

## 4. Workflow автодеплоя

Файл [`.github/workflows/deploy.yml`](../../../../.github/workflows/deploy.yml).

### 4.1 Триггеры

```yaml
on:
  push:
    branches: [lab-4]
    paths:
      - 'БР1.2/Владзиевский Евгений/labs/lab2/**'
      - 'БР1.2/Владзиевский Евгений/labs/lab4/deploy/**'
      - '.github/workflows/deploy.yml'
  workflow_dispatch:
```

- `push` в ветку `lab-4` — основной триггер, как того требует задание;
- фильтр `paths` не запускает деплой, когда меняются только отчёты и чужие
  каталоги в общем репозитории курса;
- `workflow_dispatch` даёт возможность развернуть текущее состояние ветки
  вручную из интерфейса GitHub.

Параллельные деплои запрещены, чтобы два пайплайна не перезаписывали каталог
приложения одновременно:

```yaml
concurrency:
  group: deploy-rental-app
  cancel-in-progress: false
```

### 4.2 Шаги пайплайна

| Шаг | Действие |
|---|---|
| `actions/checkout@v4` | Получение кода ветки на раннер |
| Проверка окружения | Версии `docker`, `docker compose`, `nginx` |
| Синхронизация исходников | `rsync -a --delete` каталога `lab2` в `/opt/rental-app`, с исключением `.git` и `.env` |
| Копирование конфигурации | `docker-compose.prod.yml` и `.env.example` из `lab4/deploy` |
| Генерация секретов | При первом запуске создаётся `.env` со случайными `openssl rand` значениями; существующий файл не трогается |
| Сборка образов | `docker compose build` |
| Запуск стека | `docker compose up -d --remove-orphans` |
| Обновление nginx | Копирование конфига, `nginx -t`, `systemctl reload nginx` |
| Smoke-тест | Опрос `http://127.0.0.1/health` до 30 раз с паузой 5 с, затем проверка `401` на запрос без токена |
| Состояние контейнеров | `docker compose ps` (выполняется всегда, даже при ошибке) |
| Логи при ошибке | `docker compose logs --tail 50` (только при `failure()`) |

Важные детали:

- **Идемпотентность.** Повторный запуск пайплайна не ломает развёрнутое
  приложение: `.env` сохраняется, тома с данными БД не пересоздаются,
  `docker compose up -d` перезапускает только изменившиеся контейнеры.
- **Smoke-тест с ожиданием.** Сразу после `up -d` приложение ещё не готово:
  поднимаются базы, Kafka, выполняются миграции GORM. Поэтому проверка
  `/health` повторяется с интервалом, а не выполняется один раз.
- **Проверка не только 200.** Кроме `/health` пайплайн убеждается, что
  защищённый эндпоинт отвечает `401` без токена — это проверяет, что через
  прокси работает не заглушка, а реальная цепочка с авторизацией.
- **Диагностика при падении.** Шаг с логами выполняется только при ошибке,
  чтобы в обычном прогоне не раздувать вывод.

## 6. Проверка автодеплоя

Чтобы убедиться, что пайплайн действительно доставляет изменения, а не просто
перезапускает то, что уже лежит на сервере, в конфигурацию nginx было внесено
проверяемое снаружи изменение — сжатие JSON-ответов:

```nginx
gzip on;
gzip_proxied any;
gzip_min_length 256;
gzip_types application/json text/plain;
```

### Порядок проверки

1. **До изменения** — запрос с внешней машины, сжатия нет:

   ```console
   $ curl -H "Accept-Encoding: gzip" -D - -o /dev/null \
          -X POST http://192.168.1.245/api/v1/auth/login ...
   HTTP/1.1 200 OK
   Content-Type: application/json; charset=utf-8
   ```

   Заголовка `Content-Encoding` в ответе нет.

2. **Коммит и push** изменения `rental-api.conf` в ветку `lab-4`.
   На сервер вручную не заходили — только `git push`.

3. **Пайплайн отработал автоматически**: запуск занял 16 секунд, все шаги
   успешны, `nginx -t` прошёл, конфигурация перезагружена.

4. **После изменения** — тот же запрос с внешней машины:

   ```console
   $ curl -H "Accept-Encoding: gzip" -D - -o /dev/null \
          -X POST http://192.168.1.245/api/v1/auth/login ...
   HTTP/1.1 200 OK
   Content-Type: application/json; charset=utf-8
   Transfer-Encoding: chunked
   Content-Encoding: gzip
   ```

Появился заголовок `Content-Encoding: gzip` — изменение, существовавшее только
в git, доехало до рабочего сервера без единой ручной команды.

### Замечание про статусы ответов

При проверке выяснилось, что ответ `201 Created` на регистрацию пользователя
не сжимается. Это не ошибка конфигурации: модуль `ngx_http_gzip` обрабатывает
только ограниченный набор статусов (`200`, `403`, `404`, `301`, `302`, `304`
и ряд других), и `201` в него не входит. Поэтому проверка выполнялась на
эндпоинте `/api/v1/auth/login`, возвращающем `200`.

### Сводка запусков

| Запуск | Триггер | Что доставлено | Длительность | Результат |
|---|---|---|---|---|
| 1 | push `ci(hw6): добавить автодеплой...` | сам workflow, полный прогон деплоя | 32 с | success |
| 2 | push `feat(lab4): включить gzip...` | изменение конфигурации nginx | 16 с | success |
| — | push `docs(hw6): добавить отчёт...` | — | — | не запущен |

Последняя строка — тоже часть проверки: коммит с отчётом меняет только
каталог `homeworks/hw6`, который не входит в фильтр `paths`, поэтому деплой
не запустился и работающее приложение не трогалось.

## 7. Заключение

Настроен автодеплой бэкенд-приложения на удалённый сервер средствами GitHub
Actions с триггером на push в ветку `lab-4`. Пайплайн выполняет полный цикл
развёртывания из ЛР4: синхронизацию исходников, сборку образов, запуск стека
Docker Compose, обновление конфигурации nginx и smoke-тест приложения через
обратный прокси.

Работоспособность подтверждена двумя автоматическими запусками, второй из
которых доставил на сервер проверяемое снаружи изменение конфигурации.

### Принятые решения

- **Self-hosted runner вместо SSH-деплоя с облачного раннера.** Сервер
  находится в локальной сети без публичного IP, поэтому облачный раннер до
  него не достучится. Раннер на самом сервере решает это без VPN и проброса
  портов, а заодно избавляет от хранения SSH-ключа в секретах репозитория.
- **Фильтр `paths` в триггере.** Репозиторий общий для всего потока, деплой
  запускается только при изменении кода приложения, конфигурации
  развёртывания или самого workflow.
- **Smoke-тест с ожиданием готовности** вместо одиночной проверки: после
  `up -d` сервисам нужно время на старт БД, Kafka и миграции.
- **Сохранение `.env` между запусками.** Секреты генерируются один раз;
  иначе каждый деплой менял бы пароли БД и инвалидировал выданные JWT.

### Что можно улучшить

- **Тесты до деплоя.** Сейчас пайплайн сразу разворачивает код; логичный
  следующий шаг — job с `go vet` и `go test ./...` для каждого сервиса, и
  деплой только при успешных тестах.
- **Откат при неудаче.** Сейчас при падении smoke-теста пайплайн просто
  завершается с ошибкой, а на сервере остаётся новая версия. Можно сохранять
  предыдущие теги образов и откатываться на них.
- **Окружения GitHub.** Для разделения stage и prod удобно завести
  `environment` с required reviewers на production-деплой.
