## 1. Контекст и цель

Приложение — «Сервис для аренды недвижимости»: шесть Go-сервисов
(API Gateway, auth, property, booking, payment, messaging), пять баз
PostgreSQL по схеме «база на сервис» и Kafka для асинхронного
взаимодействия через Transactional Outbox.

Текущее состояние (ЛР4–ЛР6): всё работает на одной виртуальной машине под
Docker Compose, за nginx в режиме обратного прокси, с мониторингом на
Prometheus, Loki и Grafana и автодеплоем через GitHub Actions.

Цель ДЗ7 — спроектировать облачную инфраструктуру, в которой это
приложение разворачивается как управляемая, масштабируемая и
отказоустойчивая система, и которая станет основой для ЛР7 (развёртывание
в Kubernetes) и ЛР8 (нагрузочное тестирование и автоскейлинг).

## 2. Требования к инфраструктуре

### 2.1 Функциональные

- развёртывание шести сервисов независимо друг от друга;
- изоляция данных: у каждого сервиса собственная БД;
- асинхронная шина сообщений, переживающая перезапуск сервисов;
- хранение пользовательских файлов (фотографии объектов);
- единая внешняя точка входа с маршрутизацией по путям API.

### 2.2 Нефункциональные

| Характеристика | Целевое значение | Обоснование |
|---|---|---|
| Доступность | 99.5 % в месяц (≈3.6 ч простоя) | учебный сервис, не финансовая система |
| Время отклика | p95 < 300 мс на чтение каталога | интерактивный поиск жилья |
| Пропускная способность | 100 RPS в пике | оценка: ~10 000 активных пользователей, 1 запрос в 100 с |
| RPO (допустимая потеря данных) | 15 минут | бронирования и платежи важнее профилей |
| RTO (время восстановления) | 30 минут | ручной откат релиза укладывается в это окно |
| Развёртывание | без простоя | rolling update с проверками готовности |

Из этих цифр следуют конкретные решения: p95 < 300 мс требует
горизонтального масштабирования API Gateway и каталога, RPO 15 минут —
регулярных снапшотов БД, «без простоя» — readiness-проб и стратегии
RollingUpdate с `maxUnavailable: 0`.

## 3. Выбор модели развёртывания

| Модель | Плюсы | Минусы | Решение |
|---|---|---|---|
| IaaS: ВМ + Docker Compose (как в ЛР4) | просто, дёшево, понятно | нет самовосстановления, масштабирование вручную, деплой с простоем | текущее состояние, не целевое |
| PaaS: контейнерные сервисы (Cloud Run, App Runner) | минимум эксплуатации | слабый контроль над сетью и стейтом, Kafka всё равно нужна отдельно | не подходит для стейтфул-части |
| **Kubernetes (managed)** | декларативность, самовосстановление, HPA, rolling update, единый способ описывать всё | выше порог входа, нужен контроль за ресурсами | **выбрано** |
| Kubernetes self-hosted | полный контроль | обслуживание control plane на себе | только для учебного стенда |

Выбран Kubernetes: приложение уже разбито на независимые сервисы, у
каждого свой жизненный цикл, и именно этот сценарий Kubernetes закрывает
штатно — декларативное описание, автоматический перезапуск упавших
подов, горизонтальное масштабирование по нагрузке и обновление без
простоя.

В целевом облаке это **managed Kubernetes** (Yandex Managed Service for
Kubernetes, VK Cloud Kubernetes, GKE/EKS — по месту размещения): облако
берёт на себя control plane, обновления и резервное копирование etcd.

## 4. Целевая архитектура

```
                          Интернет
                             │
                   ┌─────────▼──────────┐
                   │  Cloud Load Balancer│  публичный IP, TLS
                   └─────────┬──────────┘
                             │
                   ┌─────────▼──────────┐
                   │   Ingress Controller│  маршрутизация по путям
                   └─────────┬──────────┘
                             │
      ┌──────────────────────▼───────────────────────────────┐
      │              Kubernetes namespace: rental            │
      │                                                       │
      │   ┌───────────────┐   внутренние ClusterIP-сервисы    │
      │   │  api-gateway  │   (DNS-имена внутри кластера)     │
      │   │   2+ реплик   │                                   │
      │   └───┬───┬───┬───┘                                   │
      │       │   │   │                                       │
      │   ┌───▼┐ ┌▼──┐ ┌▼────┐ ┌────────┐ ┌───────────┐      │
      │   │auth│ │pro│ │book │ │payment │ │ messaging │      │
      │   └─┬──┘ └─┬─┘ └──┬──┘ └───┬────┘ └─────┬─────┘      │
      │     │      │      │        │            │            │
      └─────┼──────┼──────┼────────┼────────────┼────────────┘
            │      │      │        │            │
      ┌─────▼──────▼──────▼────────▼────────────▼─────────────┐
      │   Managed PostgreSQL (5 БД)    Managed Kafka          │
      │   Object Storage (фото)        Managed Monitoring      │
      └────────────────────────────────────────────────────────┘
```

Принципы:

- **Stateless-сервисы в кластере, состояние — вне его.** Go-сервисы не
  хранят ничего локально, поэтому их поды можно свободно убивать,
  пересоздавать и масштабировать. БД, Kafka и файлы вынесены в управляемые
  сервисы облака.
- **Один namespace на окружение.** `rental` для production, `rental-stage`
  для стенда: одинаковые манифесты, разные значения переменных.
- **Конфигурация отдельно от образов.** Адреса сервисов и параметры — в
  ConfigMap, пароли и ключи — в Secret; образ один и тот же для всех
  окружений.
- **Единственная публичная точка входа.** Снаружи доступен только Ingress;
  микросервисы и базы живут во внутренней сети кластера.

## 5. Облачные ресурсы

| Компонент | Облачный ресурс | Параметры | Почему так |
|---|---|---|---|
| Оркестрация | Managed Kubernetes | 3 узла по 4 vCPU / 8 ГБ | три узла переживают потерю одного |
| Точка входа | Network Load Balancer + Ingress Controller | публичный IP, TLS-терминация | LB держит внешний адрес, Ingress знает о сервисах |
| Базы данных | Managed PostgreSQL | 5 БД, 2 vCPU / 8 ГБ, HA-пара | бэкапы, репликация и обновления — на стороне облака |
| Шина сообщений | Managed Kafka | 3 брокера, replication factor 3 | потеря брокера не теряет события |
| Файлы | Object Storage (S3-совместимое) | bucket с политикой доступа | фотографии не должны лежать на диске пода |
| Образы | Container Registry | приватный репозиторий | кластер тянет образы по внутренней сети |
| Секреты | Managed KMS / Secret Manager | ключи шифрования | секреты не хранятся в git |
| Мониторинг | Managed Prometheus + Grafana либо собственный стек из ЛР6 | retention 15 дней | метрики переживают пересоздание кластера |

### 5.1 Почему managed, а не всё в кластере

PostgreSQL и Kafka можно развернуть в Kubernetes операторами, но тогда
на команду ложатся резервное копирование, восстановление на точку во
времени, обновления версий и работа с дисками. Для учебного и небольшого
production-проекта управляемые сервисы дешевле по трудозатратам, а их
SLA выше того, что реально обеспечить самостоятельно.

Исключение — объектное хранилище: его замена в кластере (MinIO) имеет
смысл только при требовании держать данные внутри периметра.

## 6. Сетевая связность

### 6.1 Уровни сети

1. **Внешний.** Публичный IP на балансировщике, TLS-сертификат, порт 443;
   порт 80 редиректит на 443.
2. **Ingress.** Маршрутизация по путям: `/api/v1/*` → api-gateway,
   `/grafana/*` → мониторинг. Единственный ресурс, видящий внешний трафик.
3. **Внутрикластерный.** Сервисы общаются по DNS-именам
   (`http://auth-service:8081`), адреса подов не фиксированы и меняются
   при пересоздании — обращение всегда через ClusterIP-сервис.
4. **К управляемым сервисам.** БД и Kafka доступны только из подсети
   кластера, публичных адресов у них нет.

### 6.2 Разграничение трафика

Планируются NetworkPolicy по принципу «запрещено всё, что не разрешено»:

| Источник | Назначение | Разрешено |
|---|---|---|
| Ingress Controller | api-gateway:8080 | да |
| api-gateway | все микросервисы | да |
| booking-service | payment-service, property-service | да |
| любой сервис | своя БД | да |
| любой сервис | чужая БД | **нет** |
| микросервисы | Ingress Controller | нет |

Это защищает инвариант «база только у своего сервиса» на сетевом уровне,
а не только договорённостью в коде.

## 7. Хранение данных

| Данные | Где | Долговечность |
|---|---|---|
| Профили, объекты, аренды, платежи, сообщения | Managed PostgreSQL, по БД на сервис | автоматические бэкапы, PITR |
| События Kafka | Managed Kafka, replication factor 3 | retention 7 дней |
| Фотографии объектов | Object Storage | репликация внутри региона |
| Метрики и логи | Prometheus (15 дней), Loki (7 дней) | на отдельном диске |

### 7.1 Резервное копирование

- **PostgreSQL:** ежедневный полный бэкап + непрерывный WAL, что даёт
  восстановление на точку во времени. RPO 15 минут из требований
  обеспечивается именно WAL-архивом, а не суточным снапшотом.
- **Object Storage:** версионирование объектов, удаление — мягкое.
- **Манифесты и конфигурация:** git, то есть восстановление кластера —
  это `kubectl apply -k` из репозитория.

Состояние, которое намеренно не резервируется: поды, образы (пересобираются
из git) и метрики (теряются без ущерба для бизнес-данных).

## 8. Отказоустойчивость

| Отказ | Что происходит | Механизм |
|---|---|---|
| Падение процесса в поде | kubelet перезапускает контейнер | liveness-проба на `/health` |
| Под завис, но жив | трафик на него не идёт, под перезапускается | readiness- и liveness-пробы |
| Потеря узла | поды переезжают на другие узлы | 3 узла, реплики на разных узлах |
| Выкладка сломанной версии | старые поды не снимаются, пока новые не готовы | RollingUpdate + `maxUnavailable: 0` |
| Отказ primary PostgreSQL | переключение на реплику | HA-конфигурация managed-сервиса |
| Недоступность payment-service | бронирование не подтверждается, событие остаётся в outbox | Transactional Outbox из ДЗ5 |
| Перегрузка | добавляются реплики | HPA по CPU |

### 8.1 Чего дизайн не покрывает

- **Отказ целого региона.** Мультирегиональное развёртывание удваивает
  стоимость и требует репликации БД между регионами; для целевых 99.5 %
  это избыточно.
- **Логические ошибки данных.** От неверной миграции защищает только
  бэкап и проверка миграций на стенде.

Это сознательные ограничения, а не упущения: они зафиксированы, чтобы
ожидания по доступности были честными.

## 9. Масштабирование

### 9.1 Горизонтальное

HPA по CPU с целевой утилизацией 70 %:

| Сервис | min | max | Почему |
|---|---|---|---|
| api-gateway | 2 | 6 | весь внешний трафик проходит через него |
| property-service | 2 | 6 | поиск по каталогу — самый частый сценарий |
| auth-service | 2 | 4 | bcrypt при входе нагружает CPU |
| booking, payment, messaging | 1 | 3 | операции реже и завязаны на БД |

Базы данных горизонтально не масштабируются: при росте нагрузки на чтение
добавляются read-реплики, запись остаётся на primary.

### 9.2 Вертикальное: requests и limits

`requests` определяют, куда планировщик поставит под, `limits` защищают
соседей от «шумного» пода. Для Go-сервисов выбран старт с
`requests: 20m CPU / 32Mi` и `limits: 500m / 192Mi` — Go-бинарник в простое
занимает единицы мегабайт, а пик приходится на обработку запроса.
Точные значения уточняются по результатам нагрузочного тестирования в ЛР8.

## 10. Безопасность

- **Секреты** — в Secret, зашифрованные провайдером KMS; в git лежит только
  пример файла. Пароли генерируются при развёртывании, а не хранятся в
  репозитории.
- **Доступ снаружи** — только через Ingress по TLS; базы и Kafka не имеют
  публичных адресов.
- **Сеть внутри кластера** — NetworkPolicy, запрещающие обращения
  «не своих» сервисов к чужим базам.
- **Образы** — приватный registry, сборка в CI, запуск от непривилегированного
  пользователя; `latest` в production не используется, тег привязан к
  коммиту.
- **RBAC** — у CI-сервисного аккаунта права только на обновление
  Deployment в своём namespace, не на весь кластер.

## 11. Наблюдаемость

Стек из ЛР6 переносится в кластер и дополняется:

| Слой | Инструмент | Что даёт |
|---|---|---|
| Метрики инфраструктуры | node-exporter, kube-state-metrics | ресурсы узлов, состояние подов |
| Метрики приложения | Prometheus client в сервисах | RPS, задержки, коды ответов |
| Логи | Promtail + Loki | единый поиск по логам всех подов |
| Доступность | blackbox-exporter | healthcheck каждого сервиса |
| Алерты | Alertmanager | уведомления о недоступности и перегрузке |

Ключевая разница с ЛР6: в кластере поды эфемерны, поэтому логи нельзя
хранить в контейнере — их сразу отправляют в Loki, а метрики собираются
по меткам пода, а не по именам контейнеров.

## 12. Учебный стенд и отличия от целевого дизайна

ЛР7 реализует этот дизайн на одной виртуальной машине под **k3s** —
облегчённом дистрибутиве Kubernetes. Сущности Kubernetes те же самые
(Deployment, StatefulSet, Service, Ingress, ConfigMap, Secret, PVC, HPA),
поэтому манифесты переносимы в managed-кластер почти без правок.

| Элемент дизайна | В облаке | В учебном стенде (ЛР7) |
|---|---|---|
| Кластер | managed Kubernetes, 3 узла | k3s, один узел |
| Балансировщик | Cloud Load Balancer | klipper-lb (ServiceLB) k3s |
| Ingress Controller | nginx-ingress / ALB | Traefik из комплекта k3s |
| PostgreSQL | Managed PostgreSQL, HA | StatefulSet + PVC |
| Kafka | Managed Kafka, 3 брокера | StatefulSet, один брокер |
| Файлы | Object Storage | PVC на локальном диске |
| Registry | приватный registry | образы импортируются в containerd узла |
| Хранилище томов | сетевые диски | local-path provisioner |

Следствия ограничений стенда, которые важно понимать:

- один узел — отказ узла означает отказ всей системы, поэтому реальная
  доступность стенда ниже целевых 99.5 %;
- `local-path` привязывает том к узлу: под с PVC не может переехать;
- один брокер Kafka — потеря брокера означает недоступность шины, хотя
  события не теряются благодаря outbox в БД.

---

## 13. Заключение

Спроектирована облачная инфраструктура для микросервисного приложения:
выбран Kubernetes как модель развёртывания, определены облачные ресурсы
(managed Kubernetes, PostgreSQL, Kafka, Object Storage, Load Balancer,
Container Registry), описана сетевая связность с единственной публичной
точкой входа и изоляцией баз, спроектированы отказоустойчивость
(пробы, реплики, rolling update, HA БД, бэкапы с RPO 15 минут) и
масштабирование (HPA по CPU, requests/limits).

Дизайн доведён до уровня, на котором его можно реализовать: в ЛР7 он
воплощается в манифестах Kubernetes на кластере k3s, в ЛР8 проверяется
нагрузочным тестированием и настройкой HPA. Отличия учебного стенда от
целевого облака перечислены явно — с указанием, что именно они ухудшают.
