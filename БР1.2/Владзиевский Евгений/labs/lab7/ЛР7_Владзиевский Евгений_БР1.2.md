## 1. Цель работы

Настроить развёртывание и оркестрацию микросервисного приложения в
Kubernetes согласно техническому дизайну из ДЗ7.

До этой работы приложение работало на одной ВМ под Docker Compose за
nginx (ЛР4), настройка сервера была автоматизирована Ansible (ЛР5), а
мониторинг собран на Prometheus, Loki и Grafana (ЛР6). В ЛР7 оркестрацию
берёт на себя Kubernetes: Compose и nginx из схемы уходят, их место
занимают манифесты, контроллеры и Ingress.

---

## 2. Кластер Kubernetes

В качестве дистрибутива выбран **k3s** — сертифицированный CNCF
дистрибутив Kubernetes, упакованный в один бинарник. Причины выбора для
учебного стенда:

- control plane, kubelet, containerd и CoreDNS в одном процессе — на ВМ с
  4 ГБ памяти полноценный kubeadm-кластер оставил бы мало места
  приложению;
- в комплекте идут Ingress-контроллер Traefik, балансировщик ServiceLB и
  storage-класс `local-path` — то есть базовая инфраструктура, которая в
  облаке предоставляется как managed-сервисы;
- API полностью совместим с «большим» Kubernetes, поэтому манифесты
  переносимы в managed-кластер.

Установка:

```bash
curl -sfL https://get.k3s.io | sudo INSTALL_K3S_EXEC="--write-kubeconfig-mode 644" sh -
```

Состояние кластера:

```
NAME                STATUS   ROLES                  VERSION        CONTAINER-RUNTIME
copy-of-vm-ubuntu   Ready    control-plane,master   v1.37.2+k3s1   containerd://2.3.7-k3s1
```

Системные компоненты: CoreDNS, Traefik, ServiceLB, local-path-provisioner,
metrics-server (последний понадобится для HPA в ЛР8).

Перед установкой были остановлены стек Docker Compose и nginx на хосте:
порты 80 и 443 нужны Ingress-контроллеру, а держать два экземпляра
приложения на одной ВМ бессмысленно.

## 3. Образы приложения

В учебном стенде нет внешнего registry, поэтому образы собираются прямо
на узле и импортируются в containerd кластера:

```bash
for svc in api-gateway auth-service property-service \
           booking-service payment-service messaging-service; do
    sudo docker build -t "rental/${svc}:latest" "/opt/rental-app/${svc}"
    sudo docker save "rental/${svc}:latest" | sudo k3s ctr images import -
done
```

В манифестах указан `imagePullPolicy: IfNotPresent` — иначе kubelet пошёл
бы за образом в Docker Hub и не нашёл бы его.

В целевом дизайне (ДЗ7) этот шаг заменяется приватным Container Registry,
куда образы кладёт CI, а теги привязываются к коммиту вместо `latest`.

## 4. Манифесты: что и почему

### 4.1 Базы данных — StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: auth-db
spec:
  serviceName: auth-db
  replicas: 1
  template:
    spec:
      containers:
        - name: postgres
          image: postgres:16-alpine
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: rental-secrets
                  key: AUTH_DB_PASSWORD
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          readinessProbe:
            exec:
              command: ["pg_isready", "-U", "auth", "-d", "auth_db"]
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
```

Почему StatefulSet, а не Deployment: у базы есть состояние, стабильное
сетевое имя и собственный том. `volumeClaimTemplates` создаёт PVC,
который переживает пересоздание пода, а Deployment пришлось бы
дополнять отдельным PVC вручную и он не гарантировал бы порядок
запуска.

`PGDATA` указывает на подкаталог тома: PostgreSQL отказывается
инициализировать базу в каталоге, где уже есть `lost+found`, а именно он
появляется в корне смонтированного тома.

Сервис для БД — **headless** (`clusterIP: None`): балансировать нечего,
реплика одна, а обращение идёт по стабильному DNS-имени.

### 4.2 Микросервисы — Deployment

```yaml
spec:
  replicas: 1
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    spec:
      containers:
        - name: auth-service
          image: rental/auth-service:latest
          imagePullPolicy: IfNotPresent
          startupProbe:
            httpGet: { path: /health, port: 8081 }
            failureThreshold: 30
            periodSeconds: 5
          readinessProbe:
            httpGet: { path: /health, port: 8081 }
          livenessProbe:
            httpGet: { path: /health, port: 8081 }
          resources:
            requests: { cpu: 20m, memory: 32Mi }
            limits:   { cpu: 500m, memory: 192Mi }
```

Решения:

- **Три пробы, а не одна.** `startupProbe` даёт сервису до 150 секунд на
  старт (миграции GORM и подключение к Kafka), и только после её успеха
  начинают работать остальные. Без неё `livenessProbe` убивала бы под,
  не дождавшись инициализации. `readinessProbe` убирает под из
  балансировки, пока он не готов, `livenessProbe` перезапускает зависший.
- **`maxUnavailable: 0`** — во время выката старый под снимается только
  после того, как новый прошёл readiness. Это и есть обновление без
  простоя из требований ДЗ7.
- **requests и limits у всех контейнеров.** `requests` нужны планировщику
  и HPA, `limits` не дают одному поду съесть память узла. Значения
  выбраны по фактическому потреблению из ЛР6: Go-сервисы занимали 5–19 МБ.

### 4.3 API Gateway — две реплики

Шлюз — единственный компонент, который видит внешний трафик, поэтому у
него `replicas: 2`: перезапуск одной реплики не прерывает обслуживание,
а Service распределяет запросы между ними.

## 5. Конфигурация и секреты

Конфигурация разделена на две части:

- **ConfigMap `rental-config`** — адреса сервисов внутри кластера, порты,
  параметры загрузки файлов. Ничего чувствительного;
- **Secret `rental-secrets`** — `JWT_SECRET`, `SERVICE_TOKEN` и пароли
  пяти баз.

Секрет не хранится в репозитории: в git лежит только `secret.example.yaml`,
а реальные значения создаёт скрипт развёртывания:

```bash
kubectl -n rental create secret generic rental-secrets \
    --from-literal=JWT_SECRET="$(openssl rand -hex 32)" \
    --from-literal=AUTH_DB_PASSWORD="$(openssl rand -hex 16)" \
    ...
```

Скрипт проверяет наличие секрета и не пересоздаёт его: иначе при каждом
развёртывании менялись бы пароли БД, а уже выданные JWT становились бы
невалидными.

Сервисы получают значения через `valueFrom` — пароли не попадают ни в
манифест, ни в образ, ни в вывод `kubectl describe deployment`.

## 6. Точка входа

Роль nginx из ЛР4 перешла к Ingress-контроллеру Traefik:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: rental-ingress
spec:
  ingressClassName: traefik
  rules:
    - http:
        paths:
          - path: /grafana
            pathType: Prefix
            backend:
              service:
                name: grafana-external
                port: { number: 3000 }
          - path: /
            pathType: Prefix
            backend:
              service:
                name: api-gateway
                port: { number: 8080 }
```

Grafana из ЛР6 осталась работать в Docker на узле — переносить мониторинг
в тот же кластер, за которым он следит, неправильно: при отказе кластера
пропадёт и наблюдаемость. Чтобы она осталась доступной по единому адресу,
создан сервис без селектора и EndpointSlice с адресом узла:

```yaml
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: grafana-external-1
  labels:
    kubernetes.io/service-name: grafana-external
addressType: IPv4
endpoints:
  - addresses: ["192.168.1.245"]
ports:
  - port: 3000
```

## 7. Развёртывание

```bash
/opt/rental-k8s/scripts/build-images.sh /opt/rental-app   # сборка и импорт образов
/opt/rental-k8s/scripts/deploy.sh                          # секреты + kubectl apply -k
```

`deploy.sh` создаёт секрет (один раз), применяет kustomization, ждёт
готовности всех StatefulSet и Deployment через `kubectl rollout status` и

### 8.5 Самовосстановление

Проверка: под API Gateway удаляется, запросы снаружи продолжают идти.

```console
$ kubectl -n rental delete pod api-gateway-6954796f59-78ggd
  после удаления: health=502
  после удаления: health=200
  после удаления: health=200
  ... (остальные 8 проверок — 200)

$ kubectl -n rental get pods -l app=api-gateway
api-gateway-6954796f59-f5qnf   1/1     Running   0     2m36s
api-gateway-6954796f59-mh762   1/1     Running   0     20s
```

Deployment сразу создал новый под взамен удалённого. Но **первый запрос
после удаления вернул 502** — честный результат, который стоит объяснить:
Ingress-контроллер успевает отправить запрос в под, который уже получил
сигнал на завершение, но ещё не исключён из списка эндпоинтов. Удаление
пода и обновление эндпоинтов происходят асинхронно.

Лечится это `preStop`-хуком с небольшой паузой: под перестаёт
обслуживаться балансировщиком раньше, чем закрывает соединения.
В текущих манифестах хук не добавлен — это зафиксированная недоработка,
а не «всё идеально».

### 8.7 Проблемы, обнаруженные при переносе

Перенос рабочего Compose-стека в Kubernetes выявил три проблемы, которых
в Compose не существовало.

**Kafka не стартовала в кластере.** Контейнер завершался с кодом 1 сразу
после строки `port is deprecated. Please use KAFKA_ADVERTISED_LISTENERS
instead`. Причина — механизм service links: Kubernetes добавляет в каждый
под переменные окружения для всех сервисов namespace, в том числе
`KAFKA_PORT=tcp://10.43.129.44:9092`. Entrypoint образов Confluent читает
`KAFKA_PORT` как устаревшую настройку порта брокера, не может разобрать
значение в виде URL и прекращает работу. В Docker Compose такой
переменной не возникает, поэтому проблема проявилась только в кластере.
Решение — отключить подстановку:

```yaml
spec:
  enableServiceLinks: false
```

**Ingress отдавал 502 на `/grafana/`.** Сервис `grafana-external` создан
намеренно без селектора: его эндпоинт задаётся вручную и указывает на
адрес узла, где в Docker работает Grafana. Однако `kubectl get endpoints`
показал, что сервис выбрал полтора десятка подов приложения. Причина —
директива `commonLabels` в kustomize: она дописывает метку не только в
`metadata.labels`, но и в `spec.selector` сервисов, и selector-less сервис
перестал быть таковым. Решение — использовать секцию `labels` с явным
запретом трогать селекторы:

```yaml
labels:
  - pairs:
      app.kubernetes.io/part-of: rental-app
    includeSelectors: false
```

**Права на тома у Kafka и ZooKeeper.** Образы Confluent работают под
пользователем с uid 1000, а том, созданный `local-path`, принадлежит root.
Решение — `securityContext` с `fsGroup: 1000`, после чего kubelet
передаёт каталог тома группе контейнера.

Все три случая — пример того, что перенос в Kubernetes не сводится к
переписыванию compose-файла в манифесты: окружение пода, права на тома и
инструменты шаблонизации вносят свои особенности.

## 9. Сравнение с Docker Compose

| Аспект | Docker Compose (ЛР4) | Kubernetes (ЛР7) |
|---|---|---|
| Описание | один `docker-compose.prod.yml` | манифесты по типам ресурсов + kustomization |
| Упавший контейнер | `restart: unless-stopped` поднимает процесс | kubelet перезапускает под по liveness-пробе |
| «Живой, но не отвечает» | не отслеживается | readiness-проба убирает под из балансировки |
| Обновление | `up -d` пересоздаёт контейнер, короткий простой | RollingUpdate с `maxUnavailable: 0` — без простоя |
| Масштабирование | `--scale`, вручную, без балансировки | `replicas`, Service балансирует, в ЛР8 — HPA |
| Секреты | `.env` на диске | Secret, подставляется через `valueFrom` |
| Точка входа | nginx на хосте | Ingress + контроллер в кластере |
| Диски | docker volumes | PVC через storage-класс |
| Ограничения ресурсов | не заданы | requests/limits у каждого контейнера |

Compose проще и быстрее для одной машины; Kubernetes даёт
самовосстановление, обновление без простоя и предсказуемое распределение
ресурсов — то, что требуется по дизайну из ДЗ7.

## 10. Заключение

Микросервисное приложение развёрнуто в Kubernetes согласно техническому
дизайну из ДЗ7. В кластере k3s работают 14 подов: шесть микросервисов
(API Gateway в двух репликах), пять баз PostgreSQL, Kafka и ZooKeeper —
все с постоянными томами, пробами готовности и ограничениями ресурсов.
Внешний доступ идёт через Ingress-контроллер Traefik, который заменил
собой nginx из ЛР4.

Работоспособность подтверждена сквозным сценарием снаружи: регистрация,
вход, авторизованные запросы, корректный 401 без токена, публикация
события в Kafka через Transactional Outbox и доступность Grafana по
тому же адресу.

### Что дал переход на Kubernetes

- **Самовосстановление.** Удалённый под шлюза заменяется новым
  автоматически, трафик продолжает обслуживаться второй репликой.
- **Обновление без простоя.** `RollingUpdate` с `maxUnavailable: 0` и
  readiness-пробы: старый под снимается только после готовности нового.
- **Декларативность.** Состояние системы описано манифестами в git;
  `kubectl apply -k` приводит кластер к этому состоянию, `kubectl diff`
  показывает расхождения.
- **Управление ресурсами.** `requests`/`limits` у каждого контейнера
  вместо неограниченного потребления в Compose; это же основа для HPA.

### Ограничения текущего стенда

- **Один узел.** Отказ ВМ означает отказ всей системы; реплики шлюза
  защищают только от падения процесса, не от падения узла.
- **`local-path` привязывает том к узлу** — под с PVC не может переехать
  на другой узел, что в многоузловом кластере стало бы проблемой.
- **Образы без registry и с тегом `latest`.** Для production нужен
  приватный registry и теги по коммиту — иначе невозможно понять, какая
  версия запущена, и откатиться.
- **Нет `preStop`-хука**, из-за чего при удалении пода один запрос может
  получить 502 (показано в разделе 8.5).
- **Kafka в одном экземпляре** — в целевом дизайне это managed-сервис с
  тремя брокерами.
