## 1. Цель работы

Настроить сервис мониторинга микросервисов средствами Grafana и реализовать
дашборд, покрывающий три группы задач:

1. общее потребление CPU, disk, RAM, Network на ВМ;
2. healthcheck для всех микросервисов — все ли сервисы доступны;
3. просмотр логов со всех контейнеров, запущенных на ВМ.

Объект мониторинга — сервер `192.168.1.245` из ЛР4–ЛР5, на котором работает
стек из 13 контейнеров: API Gateway, пять микросервисов, пять баз
PostgreSQL, Kafka и ZooKeeper.

## 2. Архитектура мониторинга

Метрики и логи — это два разных потока данных, поэтому стек состоит из двух
подсистем с общим интерфейсом в Grafana.

| Компонент | Версия | Назначение |
|---|---|---|
| Prometheus | v3.1.0 | хранение метрик, опрос экспортеров, retention 15 дней |
| node-exporter | v1.9.1 | метрики хоста: CPU, память, диски, сетевые интерфейсы |
| cAdvisor | v0.52.1 | метрики по каждому контейнеру |
| blackbox-exporter | v0.26.0 | активные HTTP-проверки `/health` микросервисов |
| Loki | 3.4.2 | хранение логов, retention 7 дней |
| Promtail | 3.4.2 | сбор логов docker-контейнеров и отправка в Loki |
| Grafana | 11.6.0 | дашборды, единый интерфейс к Prometheus и Loki |

```
            ┌──────────── ВМ 192.168.1.245 ────────────────────────────┐
            │                                                          │
 метрики ВМ │  node-exporter ─┐                                        │
контейнеров │  cAdvisor ──────┼─► Prometheus ─┐                        │
доступность │  blackbox ──────┘               │                        │
            │        ▲ /health                ├─► Grafana ◄── nginx ───┼── /grafana/
            │        │                        │     ▲                  │
            │  микросервисы (13 контейнеров)  │     │                  │
            │        │ stdout                 │     │                  │
     логи   │        └─► Promtail ─► Loki ────┘─────┘                  │
            └──────────────────────────────────────────────────────────┘
```

Стек мониторинга запускается отдельным compose-проектом и подключается к
сети приложения `rental-app_default` — иначе blackbox-exporter не смог бы
обращаться к микросервисам по их именам в docker-сети.

Наружу стек не публикует ни одного порта. Grafana слушает только
`127.0.0.1:3000` и доступна через тот же nginx, что и API, по пути
`/grafana/` — точка входа в систему остаётся одна.

## 3. Сбор метрик виртуальной машины

За метрики хоста отвечает node-exporter. Ему пробрасываются `/proc`, `/sys`
и корень файловой системы в режиме только для чтения:

```yaml
  node-exporter:
    image: prom/node-exporter:v1.9.1
    command:
      - '--path.procfs=/host/proc'
      - '--path.sysfs=/host/sys'
      - '--path.rootfs=/rootfs'
      - '--collector.filesystem.mount-points-exclude=^/(sys|proc|dev|host|etc)($$|/)'
    volumes:
      - /proc:/host/proc:ro
      - /sys:/host/sys:ro
      - /:/rootfs:ro
    pid: host
```

Используемые запросы PromQL:

| Показатель | Запрос |
|---|---|
| Загрузка CPU, % | `100 - (avg(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` |
| Память, % | `(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100` |
| Диск `/`, % | `(1 - node_filesystem_avail_bytes{mountpoint="/"} / node_filesystem_size_bytes{mountpoint="/"}) * 100` |
| Сеть | `rate(node_network_receive_bytes_total{device!~"lo\|veth.*\|br-.*\|docker.*"}[5m])` |
| Диск I/O | `rate(node_disk_read_bytes_total{device!~"loop.*"}[5m])` |

Два решения, о которых стоит сказать отдельно:

- для памяти берётся `MemAvailable`, а не `MemFree`: Linux отдаёт свободную
  память под кэш страниц, и `MemFree` показывал бы почти ноль на нормально
  работающей системе;
- виртуальные интерфейсы (`veth`, `docker0`, `br-*`) исключены из сетевых
  графиков — иначе трафик между контейнерами учитывался бы дважды и
  маскировал реальный внешний трафик.

Метрики по контейнерам собирает cAdvisor — он даёт разбивку CPU и памяти
по каждому из 13 контейнеров приложения.

## 4. Healthcheck микросервисов

У каждого сервиса есть эндпоинт `/health`, отдающий `{"status":"ok"}`.
Проверки выполняет blackbox-exporter: Prometheus просит его сходить по
адресу, а тот возвращает метрику `probe_success` (1 или 0).

Модуль проверки:

```yaml
modules:
  http_health:
    prober: http
    timeout: 5s
    http:
      method: GET
      valid_status_codes: [200]
      preferred_ip_protocol: ip4
      fail_if_body_not_matches_regexp:
        - '"status"\s*:\s*"ok"'
```

Проверяется не только код 200, но и содержимое ответа: сервис, отдающий
200 с телом об ошибке, считается недоступным.

Задание в Prometheus с перенаправлением цели на blackbox:

```yaml
  - job_name: blackbox-health
    metrics_path: /probe
    params:
      module: [http_health]
    static_configs:
      - targets:
          - http://api-gateway:8080/health
          - http://auth-service:8081/health
          - http://property-service:8082/health
          - http://booking-service:8083/health
          - http://payment-service:8084/health
          - http://messaging-service:8085/health
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: blackbox-exporter:9115
      - source_labels: [__param_target]
        regex: 'http://([^:]+):.*'
        target_label: service
        replacement: '$1'
```

Последнее правило `relabel_configs` вытаскивает из URL короткое имя сервиса
в метку `service` — на дашборде плитки подписаны `auth-service`, а не
полным адресом.

Отдельное задание `blackbox-public` проверяет приложение снаружи, через
nginx (`http://192.168.1.245/health`). Это разделение важно: если внутренний
healthcheck зелёный, а внешний красный, проблема не в сервисах, а в прокси.

## 5. Сбор логов контейнеров

Promtail обнаруживает контейнеры автоматически через docker socket, поэтому
новые контейнеры попадают в Loki без правки конфигурации:

```yaml
scrape_configs:
  - job_name: docker
    docker_sd_configs:
      - host: unix:///var/run/docker.sock
        refresh_interval: 15s
    relabel_configs:
      - source_labels: ['__meta_docker_container_name']
        regex: '/(.*)'
        target_label: container
      - source_labels: ['__meta_docker_container_label_com_docker_compose_service']
        target_label: compose_service
    pipeline_stages:
      - regex:
          expression: '(?i)(?P<level>panic|fatal|error|warn|info|debug)'
      - labels:
          level:
```

`pipeline_stages` вытаскивает уровень логирования в метку `level`, что
позволяет в Grafana отфильтровать только ошибки запросом
`{container=~".+", level="error"}`.

## 6. Дашборд Grafana

Дашборд и источники данных подключаются через provisioning — файлы
`datasources.yml`, `dashboards.yml` и `rental-overview.json` монтируются в
контейнер, поэтому дашборд не нужно настраивать руками после перезапуска и
он лежит в репозитории как код.

Дашборд разделён на три секции — ровно по пунктам задания.

### 6.1 Ресурсы ВМ

Четыре плитки с цветовыми порогами (CPU, RAM, диск, аптайм) и четыре
графика: загрузка CPU по режимам, память, сеть и дисковый ввод-вывод.

### 6.2 Доступность микросервисов

Плитки UP/DOWN по шести сервисам: `probe_success` со значениями,
переведёнными в текст через `mappings`, и фоном по порогу — зелёный при 1,
красный при 0. Рядом счётчик «сервисов доступно» (`sum(probe_success)`),
график истории доступности и график времени ответа `/health`.
Ниже — CPU и память по контейнерам приложения из cAdvisor.

### 6.3 Логи контейнеров

Панель логов по всем контейнерам ВМ и график скорости логирования.
Дашборд имеет две переменные:

- `container` — выбор контейнеров (значения подтягиваются из Loki,
  поддерживается множественный выбор и «All»);
- `search` — подстрока для полнотекстового поиска.

Запрос панели: `{container=~"$container"} |= "$search"`.

## 7. Развёртывание

Стек разворачивается плейбуком Ansible — в продолжение ЛР5:

```bash
cd lab6/ansible
ansible-playbook monitoring.yml --ask-pass
```

Роль `monitoring` копирует конфигурации в `/opt/rental-monitoring`,
генерирует `.env` с паролем администратора Grafana (`force: false` —
создаётся один раз), поднимает стек и дожидается ответа от
`/api/health` Grafana.

Роль `nginx` не дублируется, а переиспользуется из ЛР5 — в `ansible.cfg`
указан путь к её каталогу:

```ini
roles_path = roles:../../lab5/ansible/roles
```

Роли передаётся `grafana_enabled: true`, и в шаблоне конфигурации прокси
появляются две локации: `/grafana/` и `/grafana/api/live/` для websocket
(Grafana использует его для живого обновления панелей).

## 9. Заключение

Настроена система мониторинга на базе Grafana, закрывающая все три пункта
задания одним дашбордом:

1. **Ресурсы ВМ** — CPU, RAM, диск и сеть собираются node-exporter'ом и
   выводятся плитками с порогами и временными графиками;
2. **Healthcheck микросервисов** — blackbox-exporter опрашивает `/health`
   всех шести сервисов, дашборд показывает UP/DOWN по каждому, счётчик
   доступных сервисов, историю доступности и время ответа;
3. **Логи контейнеров** — Promtail собирает логи всех 20 контейнеров ВМ
   через docker-discovery, Loki хранит их неделю, панель логов в Grafana
   даёт фильтрацию по контейнеру и полнотекстовый поиск.

Весь стек описан как код: compose-файл, конфигурации экспортеров, дашборд
в JSON и provisioning источников данных лежат в репозитории, а
развёртывание выполняется плейбуком Ansible в продолжение ЛР5 — роль
`nginx` переиспользована из прошлой работы, а не скопирована.

### Принятые решения

- **Prometheus + Loki вместо одного инструмента.** Метрики и логи — разные
  по природе данные: метрики это числовые ряды, логи — текст с метками.
  Grafana объединяет их в одном интерфейсе, поэтому пользователю разделение
  незаметно.
- **Проверка содержимого ответа в healthcheck.** blackbox сверяет тело
  ответа с `"status":"ok"`, а не только код 200: сервис, отдающий 200 с
  телом об ошибке, будет честно показан как DOWN.
- **Внешняя проверка отдельным заданием.** `blackbox-public` ходит на
  приложение снаружи через nginx. Если внутренние проверки зелёные, а
  внешняя красная — проблема в прокси, а не в сервисах.
- **Ничего не опубликовано наружу.** Grafana слушает loopback и доступна
  только через nginx по `/grafana/`, Prometheus — тоже loopback (для
  отладки с сервера), Loki и экспортеры доступны лишь внутри docker-сети.
- **Provisioning вместо ручной настройки.** Дашборд и источники данных
  восстанавливаются из файлов при каждом старте: настройка не теряется
  при пересоздании контейнера и видна в истории git.

### Что можно улучшить

- **Алерты** (дополнительное задание): правило на `probe_success == 0` с
  отправкой почтовых уведомлений — требует SMTP-доступа, который пока не
  настроен.
- **Sentry** (дополнительное задание): self-hosted Sentry и `sentry-go`
  в сервисах дали бы трассировки ошибок с контекстом запроса.
- **Метрики самого приложения.** Сейчас доступность проверяется снаружи;
  экспорт метрик Gin (`/metrics`: RPS, задержки, коды ответов) дал бы
  картину по эндпоинтам, а не только «жив/не жив».
- **Хранение долгой истории.** Retention 15 дней для метрик и 7 для логов
  выбран под диск ВМ; для продакшена метрики обычно выносят в удалённое
  хранилище.
