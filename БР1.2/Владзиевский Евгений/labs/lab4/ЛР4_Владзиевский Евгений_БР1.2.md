## 1. Цель работы

Развернуть микросервисное приложение «Сервис для аренды недвижимости»,
реализованное в ЛР2–ЛР3, на удалённом сервере и обеспечить доступ к нему
извне. Задание состоит из трёх частей:

1. провести предварительную настройку удалённого сервера (установка необходимых зависимостей);
2. провести развёртывание приложения на удалённом сервере;
3. настроить nginx в режиме обратного прокси для обеспечения доступа к приложению извне.

Развёртываемое приложение — стек из 13 контейнеров: API Gateway, пять
микросервисов (auth, property, booking, payment, messaging), пять экземпляров
PostgreSQL (по базе на сервис) и Kafka + ZooKeeper для асинхронного
межсервисного взаимодействия.

```bash
sudo install -m 0755 -d /etc/apt/keyrings

sudo chmod a+r /etc/apt/keyrings/docker.asc

echo "deb [arch=$ARCH signed-by=/etc/apt/keyrings/docker.asc] \
https://download.docker.com/linux/ubuntu $CODENAME stable" \
    | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update -qq
sudo apt-get install -y docker-ce docker-ce-cli containerd.io \
                        docker-buildx-plugin docker-compose-plugin
```

Дополнительно скрипт:

- добавляет пользователя `ubuntu` в группу `docker`;
- включает автозапуск `docker` и `nginx` (`systemctl enable --now`);

## 4. Production-конфигурация приложения

Конфигурация из ЛР3 (`lab2/docker-compose.yml`) рассчитана на локальную
разработку: она публикует наружу порты всех баз данных, Kafka и каждого
микросервиса, а секреты хранит в значениях по умолчанию. Для сервера
подготовлен отдельный файл
[`deploy/docker-compose.prod.yml`](deploy/docker-compose.prod.yml).

| Аспект | Локальная конфигурация (ЛР3) | Production-конфигурация (ЛР4) |
|---|---|---|
| Публикация портов | 5432–5436, 9092, 2181, 8080–8085 на `0.0.0.0` | только `127.0.0.1:8080` (API Gateway) |
| Доступ извне | напрямую к каждому сервису | только через nginx на порту 80 |
| Секреты | значения по умолчанию в YAML | переменные из файла `.env` (режим `600`) |
| Пароли БД | фиксированные (`authpass` и т. п.) | случайные, `openssl rand -hex 16` |
| Политика перезапуска | нет | `restart: unless-stopped` у всех сервисов |
| Данные Kafka/ZooKeeper | в слое контейнера | именованные тома `kafka_data`, `zookeeper_data`, `zookeeper_log` |
| Heap JVM | без ограничений | `KAFKA_HEAP_OPTS` (512 МБ для Kafka, 256 МБ для ZooKeeper) |
| Kafka listeners | `PLAINTEXT` + `PLAINTEXT_HOST` (для хоста) | только внутренний `PLAINTEXT://kafka:9092` |

Ключевой фрагмент — публикация API Gateway только на loopback:

```yaml
  api-gateway:
    build:
      context: ./api-gateway
    restart: unless-stopped
    ports:
      # Порт слушается только на loopback: наружу приложение смотрит через nginx
      - "127.0.0.1:8080:8080"
```

Секреты генерируются на сервере при первом развёртывании и в репозиторий не
попадают; в git хранится только шаблон
[`deploy/.env.example`](deploy/.env.example):

```bash
echo "JWT_SECRET=$(openssl rand -hex 32)"      >  .env
echo "SERVICE_TOKEN=$(openssl rand -hex 32)"   >> .env
echo "AUTH_DB_PASSWORD=$(openssl rand -hex 16)" >> .env
# ... пароли остальных четырёх баз
chmod 600 .env
```

## 5. Развёртывание приложения

Второй пункт задания выполняется скриптом
[`deploy/deploy.sh`](deploy/deploy.sh) с локальной машины:

```bash
cd deploy && ./deploy.sh ubuntu@192.168.1.245
```

Шаги скрипта:

1. **Копирование исходников.** `rsync -az --delete` копирует каталог `lab2`
   в `/opt/rental-app`, исключая `.git`, `.env` и тестовые данные.
2. **Копирование production-конфигурации** — `docker-compose.prod.yml`,
   `.env.example` и конфиг nginx.
3. **Генерация `.env`** — при первом запуске создаются случайные секреты;
   при повторных запусках существующий файл сохраняется, чтобы не потерять
   доступ к уже созданным базам.
4. **Сборка и запуск стека:**

   ```bash
   sudo docker compose -f docker-compose.prod.yml --env-file .env build
   sudo docker compose -f docker-compose.prod.yml --env-file .env up -d
   ```

   Образы собираются непосредственно на сервере multi-stage-сборкой
   (`golang:1.24-alpine` → `alpine:latest`), поэтому итоговый образ каждого
   сервиса содержит только статически слинкованный бинарник.
5. **Подключение конфига nginx** и перезагрузка прокси.

Порядок запуска контейнеров задан через `depends_on` с условием
`service_healthy` для баз данных: микросервис стартует только после того, как
`pg_isready` в его базе отвечает успешно. Схема БД создаётся автоматически
через `AutoMigrate` GORM при старте сервиса.

## 6. Настройка nginx в режиме обратного прокси

Третий пункт задания. Конфигурация
[`deploy/nginx/rental-api.conf`](deploy/nginx/rental-api.conf) размещается в
`/etc/nginx/sites-available/` и линкуется в `/etc/nginx/sites-enabled/`,
стандартный сайт `default` отключается:

```nginx
upstream rental_api_gateway {
    # API Gateway опубликован docker-compose только на loopback-интерфейсе
    server 127.0.0.1:8080;
    keepalive 32;
}

server {
    listen 80;
    listen [::]:80;
    server_name 192.168.1.245 _;

    client_max_body_size 10m;
    server_tokens off;

    access_log /var/log/nginx/rental-api.access.log;
    error_log  /var/log/nginx/rental-api.error.log warn;

    location / {
        proxy_pass http://rental_api_gateway;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";

        proxy_connect_timeout 5s;
        proxy_send_timeout    60s;
        proxy_read_timeout    60s;
    }

    location = /health {
        proxy_pass http://rental_api_gateway/health;
        proxy_set_header Host $host;
        access_log off;
    }
}
```

Принятые решения:

- **`client_max_body_size 10m`** — согласовано с `MAX_UPLOAD_SIZE` в
  property-service (10 485 760 байт), иначе nginx отклонял бы загрузку фото
  объектов раньше приложения, возвращая 413.
- **`proxy_http_version 1.1` + `Connection ""` + `keepalive 32`** — включают
  keep-alive-соединения до API Gateway, что убирает установку нового TCP-соединения
  на каждый запрос.
- **`X-Real-IP` / `X-Forwarded-For`** — без них приложение видело бы в качестве
  клиента только `127.0.0.1`, и логирующий middleware API Gateway терял бы
  реальный адрес клиента.
- **`server_tokens off`** — nginx не раскрывает свою версию в заголовке
  `Server`.
- **Отдельная локация `/health`** с `access_log off` — проверки живости не
  засоряют access-лог.

Применение конфигурации:

```bash
sudo ln -sf /etc/nginx/sites-available/rental-api.conf /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

Проверка синтаксиса:

```
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

### 7.5 Проверка асинхронного контура (Kafka)

Регистрация пользователя через прокси должна порождать событие в Kafka по
паттерну Transactional Outbox (реализован в ДЗ5). Запись в outbox-таблице
auth-сервиса:

```console
$ psql -U auth -d auth_db -c \
    "select id, aggregate_type, event_type, status,
            published_at is not null as published from outbox_events;"
 id | aggregate_type |   event_type    |  status   | published
----+----------------+-----------------+-----------+-----------
  1 | user           | user.registered | published | t
```

Сообщение, фактически доехавшее в топик `user.events`:

```json
{"event_id":"274ef785-c46b-4ec6-b066-5e92ed18c600","event_type":"user.registered",
 "aggregate_type":"user","aggregate_id":1,"timestamp":"2026-11-15T15:17:24Z",
 "data":{"email":"deploy-check@example.com","id":1,"phone":null,
         "full_name":"Евгений Владзиевский","role":"owner"},
 "source":"auth-service"}
```

Созданные в Kafka топики: `user.events`, `property.events`, `rental.events`,
`payment.events` (плюс служебный `__consumer_offsets`).

Таким образом, на сервере работает вся цепочка:
`клиент → nginx → API Gateway → микросервис → PostgreSQL → outbox → Kafka`.

## 8. Эксплуатация и обновление

Обновление приложения — повторный запуск `deploy.sh`: исходники
синхронизируются, пересобираются только изменившиеся образы, контейнеры
перезапускаются, `.env` и тома с данными сохраняются.

Основные команды на сервере:

```bash
cd /opt/rental-app
# статус контейнеров
sudo docker compose -f docker-compose.prod.yml --env-file .env ps
# логи всех сервисов
sudo docker compose -f docker-compose.prod.yml --env-file .env logs -f
# перезапуск стека
sudo docker compose -f docker-compose.prod.yml --env-file .env restart
# запросы через прокси
sudo tail -f /var/log/nginx/rental-api.access.log
```

Благодаря `restart: unless-stopped` и `systemctl enable docker` стек
поднимается автоматически после перезагрузки сервера.

3. **nginx в режиме обратного прокси.** nginx принимает запросы на порту 80 и
   проксирует их в API Gateway на `127.0.0.1:8080`, пробрасывая реальный IP
   клиента, поднимая лимит тела запроса до 10 МБ под загрузку фотографий и
   удерживая keep-alive-соединения до апстрима. Проверки с внешней машины
   показали, что приложение полностью доступно извне через единственный
   порт 80, а порты API Gateway, баз данных и Kafka снаружи закрыты.

Работоспособность подтверждена сквозным сценарием: регистрация и вход
пользователя, авторизованный запрос профиля и каталога объектов, корректный
401 без токена, а также публикация события `user.registered` в Kafka через
Transactional Outbox.

### Что можно улучшить

- **HTTPS.** Сейчас прокси работает по HTTP. На сервере с публичным доменом
  следующий шаг — сертификат Let's Encrypt (`certbot --nginx`) и редирект
  с 80 на 443; заголовок `X-Forwarded-Proto` для этого уже проставляется.
- **Межсетевой экран.** Пакет `ufw` установлен, но правила не включены, так
  как сервер находится в локальной сети. На публичном сервере следует
  разрешить только порты 22, 80 и 443.
- **Автоматизация деплоя.** Развёртывание запускается вручную с локальной
  машины; следующая работа (ДЗ6) — перенос этих же шагов в пайплайн
  GitHub Actions с триггером на push в ветку.
