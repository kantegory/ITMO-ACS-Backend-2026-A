## 1. Цель работы

Разработать конфигурацию Ansible для автоматизации настройки виртуальных
машин и написать плейбуки для автоматической установки системных пакетов,
настройки окружения и запуска сервисов.

В ЛР4 сервер настраивался вручную: shell-скрипты `server-setup.sh` и
`deploy.sh` выполняли последовательность команд. У такого подхода есть
недостатки, которые и решает Ansible:

| Проблема shell-скриптов | Решение в Ansible |
|---|---|
| Скрипт не знает текущего состояния системы и выполняет команды всегда | Модули декларативны: задача меняет систему, только если состояние отличается от описанного |
| Повторный запуск может сломать уже настроенное | Идемпотентность: второй запуск завершается с `changed=0` |
| Нельзя заранее посмотреть, что изменится | Режим `--check --diff` показывает изменения, не применяя их |
| Конфигурация прибита гвоздями внутри команд | Переменные в `group_vars` и шаблоны Jinja2 |
| Применение к нескольким серверам — копирование скрипта руками | Инвентарь с группами хостов, выполнение параллельно (`forks`) |

Целевой сервер — тот же, что и в ЛР4: Ubuntu 24.04 по адресу
`192.168.1.245`, пользователь `ubuntu`.

## 2. Структура конфигурации

```
labs/lab5/ansible/
├── ansible.cfg                    # настройки проекта
├── inventory/hosts.yml            # описание хостов
├── group_vars/rental_servers.yml  # переменные группы
├── site.yml                       # главный плейбук
└── roles/
    ├── common/   tasks                      — пакеты, часовой пояс, каталоги
    ├── docker/   tasks                      — Docker Engine и Compose
    ├── nginx/    tasks + templates + handlers — обратный прокси
    └── app/      tasks + templates + handlers — доставка и запуск сервисов
```

Разбиение на роли выбрано по зонам ответственности: каждую роль можно
применить отдельно по тегу, а `nginx` и `app` переиспользуемы для другого
сервера без изменений — все различия вынесены в переменные.

Файл `ansible.cfg` фиксирует настройки проекта, чтобы запуск не зависел от
окружения разработчика:

```ini
[defaults]
inventory = inventory/hosts.yml
roles_path = roles
host_key_checking = False
result_format = yaml
callbacks_enabled = ansible.posix.profile_tasks
interpreter_python = auto_silent
forks = 10

[ssh_connection]
pipelining = True
```

`pipelining = True` ускоряет выполнение: модули передаются в одну SSH-сессию
без создания временных файлов на целевой машине.

## 3. Инвентарь и переменные

### 3.1 Инвентарь

```yaml
all:
  children:
    rental_servers:
      hosts:
        rental-server:
          ansible_host: 192.168.1.245
          ansible_user: ubuntu
          ansible_connection: paramiko
```

Группа `rental_servers` позволяет добавить второй сервер, не трогая роли.

Подключение выполняется плагином `paramiko`: он умеет парольную
аутентификацию без внешней утилиты `sshpass`, которой требует стандартный
плагин `ssh`. Пароль в репозитории не хранится — он запрашивается флагом
`--ask-pass` либо берётся из `ansible-vault`; при наличии SSH-ключа пароль
не нужен вовсе.

### 3.2 Переменные группы

В `group_vars/rental_servers.yml` вынесено всё, что может отличаться между
окружениями: каталог приложения, пользователь, списки пакетов, параметры
обратного прокси и описание баз данных сервисов:

```yaml
app_dir: /opt/rental-app
app_user: ubuntu

base_packages: [ca-certificates, curl, gnupg, git, rsync, openssl]
docker_packages: [docker-ce, docker-ce-cli, containerd.io,
                  docker-buildx-plugin, docker-compose-plugin]

nginx_site_name: rental-api
nginx_server_name: "192.168.1.245 _"
nginx_upstream_port: 8080
nginx_client_max_body_size: 10m

app_databases:
  - { prefix: AUTH, user: auth, name: auth_db }
  - { prefix: PROPERTY, user: property, name: property_catalog_db }
  - ...
```

Список `app_databases` используется шаблоном `.env`: добавление шестого
микросервиса с собственной БД сводится к одной строке в переменных.

## 4. Роли

### 4.1 common — системные пакеты и окружение

```yaml
- name: Обновить индекс пакетов apt (не чаще раза в час)
  ansible.builtin.apt:
    update_cache: true
    cache_valid_time: 3600
  become: true

- name: Установить базовые системные пакеты
  ansible.builtin.apt:
    name: "{{ base_packages }}"
    state: present
  become: true

- name: Задать часовой пояс
  community.general.timezone:
    name: Europe/Moscow
  become: true

- name: Создать каталог приложения
  ansible.builtin.file:
    path: "{{ app_dir }}"
    state: directory
    owner: "{{ app_user }}"
    mode: "0755"
  become: true
```

`cache_valid_time: 3600` не даёт обновлять индекс apt при каждом запуске —
это ускоряет повторные прогоны и не создаёт лишних `changed`.

### 4.2 docker — Docker Engine и Compose

Роль повторяет шаги ЛР4, но декларативно: каталог для ключей, загрузка
GPG-ключа, подключение репозитория, установка пакетов, добавление
пользователя в группу `docker`, включение службы.

```yaml
- name: Подключить репозиторий Docker
  ansible.builtin.apt_repository:
    repo: >-
      deb [arch={{ (ansible_architecture == 'aarch64') | ternary('arm64', 'amd64') }}
      signed-by=/etc/apt/keyrings/docker.asc]
      https://download.docker.com/linux/ubuntu {{ ansible_distribution_release }} stable
    filename: docker
    state: present
  become: true
```

Архитектура и кодовое имя релиза берутся из фактов, собранных Ansible, —
та же роль отработает на другой версии Ubuntu и на arm64.

### 4.3 nginx — обратный прокси из шаблона

Конфигурация прокси вынесена в Jinja2-шаблон, параметры подставляются из
переменных:

```nginx
upstream {{ nginx_site_name | replace('-', '_') }}_upstream {
    server {{ nginx_upstream_host }}:{{ nginx_upstream_port }};
    keepalive 32;
}

server {
    listen 80;
    server_name {{ nginx_server_name }};
    client_max_body_size {{ nginx_client_max_body_size }};
    ...
}
```

Перезагрузка nginx вынесена в handler — он срабатывает один раз в конце
плея и только если конфигурация действительно изменилась:

```yaml
- name: Перезагрузить nginx
  ansible.builtin.systemd_service:
    name: nginx
    state: reloaded
  become: true
```

Отдельная задача `nginx -t` проверяет синтаксис до того, как handler
выполнит reload. Проверять шаблон параметром `validate` модуля `template`
нельзя: файл сайта — не самостоятельный конфиг nginx, в отрыве от
`nginx.conf` он не проходит проверку.

### 4.4 app — доставка исходников и запуск сервисов

```yaml
- name: Упаковать исходники приложения на управляющей машине
  community.general.archive:
    path: "{{ app_src_dir }}/"
    dest: "...rental-app-src.tar.gz"
    exclude_path: ["{{ app_src_dir }}/test", "{{ app_src_dir }}/.env"]
  delegate_to: localhost
  changed_when: false

- name: Распаковать исходники в {{ app_dir }}
  ansible.builtin.unarchive:
    src: "...rental-app-src.tar.gz"
    dest: "{{ app_dir }}"
  become: true
  notify: Пересобрать и перезапустить стек

- name: Создать файл окружения с секретами (только при первом запуске)
  ansible.builtin.template:
    src: env.j2
    dest: "{{ app_dir }}/.env"
    mode: "0600"
    force: false
  become: true

- name: Собрать образы и поднять стек
  community.docker.docker_compose_v2:
    project_src: "{{ app_dir }}"
    files: ["{{ compose_file }}"]
    env_files: [.env]
    state: present
    build: policy
    remove_orphans: true
  become: true
```

Принятые решения:

- **Архив вместо `synchronize`.** Модуль `ansible.posix.synchronize`
  вызывает внешний `rsync` по SSH и при парольной аутентификации требует
  `sshpass`. Упаковка на управляющей машине и `unarchive` дают один
  перенос вместо 136 отдельных файлов и работают без лишних зависимостей.
- **`force: false` у `.env`.** Секреты генерируются ровно один раз.
  Перезапись меняла бы пароли БД и инвалидировала выданные JWT-токены.
  Сами значения получаются через `lookup('ansible.builtin.password', ...)`
  с `chars=['hexdigits']`.
- **`docker_compose_v2` вместо `command: docker compose up`.** Модуль сам
  определяет, что изменилось, и корректно сообщает `changed`, а не
  «выполнено всегда».
- **Smoke-тест внутри плейбука.** Модуль `uri` с `retries: 30` ждёт, пока
  приложение поднимется, и проверяет, что защищённый эндпоинт отвечает
  `401` без токена.

## 5. Главный плейбук

```yaml
- name: Настройка сервера и развёртывание rental-приложения
  hosts: rental_servers
  gather_facts: true

  pre_tasks:
    - name: Проверить, что ОС поддерживается ролями
      ansible.builtin.assert:
        that:
          - ansible_distribution == 'Ubuntu'
          - ansible_distribution_major_version | int >= 22

  roles:
    - role: common
      tags: [common, packages]
    - role: docker
      tags: [docker]
    - role: nginx
      tags: [nginx, proxy]
    - role: app
      tags: [app, deploy]
```

`pre_tasks` с `assert` останавливает выполнение на неподдерживаемой ОС до
того, как роли начнут что-то менять. Теги позволяют применить часть
конфигурации: `--tags nginx` обновит только прокси.

## 6. Результат применения

Плейбук применён к серверу, на котором приложение уже было развёрнуто
вручную в ЛР4 — то есть Ansible приводил к описанному состоянию реально
работающую систему, а не чистую ВМ.

```console
$ ansible-playbook site.yml --ask-pass
...
PLAY RECAP
rental-server : ok=28  changed=3  unreachable=0  failed=0  skipped=0
```

Изменения внесли три задачи:

| Задача | Что изменилось |
|---|---|
| `nginx : Развернуть конфигурацию сайта` | конфиг пересобран из шаблона: вместо файла, положенного вручную, появился параметризованный, с заголовком `Ansible managed` |
| `app : Распаковать исходники в /opt/rental-app` | права на файлы приведены к `ubuntu:ubuntu`, содержимое синхронизировано с репозиторием |
| `RUNNING HANDLER [nginx : Перезагрузить nginx]` | handler сработал, потому что конфигурация действительно изменилась |

Остальные 25 задач вернули `ok` — Docker, nginx и пакеты уже были в нужном
состоянии, и Ansible их не трогал. Это принципиальное отличие от
shell-скрипта, который переустанавливал бы всё заново.

Итоговое сообщение плейбука:

```
"msg": "Контейнеров запущено: 13, health-check: ok"
```

Приложение продолжает отвечать снаружи — проверка с другой машины:

```console
$ curl -o /dev/null -w "%{http_code}" http://192.168.1.245/health
200
```

Полный прогон занял 26 секунд.

## 7. Проверка идемпотентности

Главное свойство конфигурации — повторный запуск не должен ничего менять.

### 7.1 Повторное применение

```console
$ ansible-playbook site.yml --ask-pass
...
PLAY RECAP
rental-server : ok=26  changed=0  unreachable=0  failed=0  skipped=0
```

`changed=0` — ни одна задача не внесла изменений:

- конфиг nginx совпал с шаблоном, handler не запускался;
- архив исходников распакован, содержимое идентично — `unarchive` сравнил
  файлы и ничего не перезаписал;
- `.env` существует, `force: false` не дал его перегенерировать, пароли БД
  и выданные JWT остались валидными;
- `docker_compose_v2` увидел, что все 13 контейнеров уже запущены с
  актуальными образами, и не пересоздавал их.

Разница `ok=28` против `ok=26` — это два handler'а, которые в первом
прогоне были вызваны, а во втором не понадобились.

### 7.2 Режим проверки

```console
$ ansible-playbook site.yml --check --diff --ask-pass
...
PLAY RECAP
rental-server : ok=22  changed=0  unreachable=0  failed=0  skipped=4
```

`--check` выполняет «сухой прогон»: Ansible сообщает, что изменил бы, но
ничего не меняет. `skipped=4` — задачи, которые в check-режиме выполнить
нельзя (сборка образов и сетевые проверки запущенного приложения).

Такого режима у shell-скриптов из ЛР4 нет в принципе: единственный способ
узнать, что сделает скрипт, — запустить его.

## 8. Заключение

Разработана конфигурация Ansible, полностью автоматизирующая настройку
виртуальной машины под микросервисное приложение: четыре роли
(`common`, `docker`, `nginx`, `app`), инвентарь с группой хостов,
переменные окружения, Jinja2-шаблоны конфигурации nginx и файла секретов,
handlers для перезагрузки сервисов и главный плейбук `site.yml`.

Оба пункта задания закрыты:

1. **Конфигурация Ansible для автоматизации настройки ВМ** — проект с
   ролями, инвентарём, переменными и тегами, применяемый одной командой;
2. **Плейбуки для установки системных пакетов, настройки окружения и
   запуска сервисов** — `common` и `docker` ставят пакеты, `nginx`
   настраивает окружение из шаблона, `app` доставляет код, генерирует
   секреты, поднимает 13 контейнеров и проверяет работоспособность.

Конфигурация проверена на реальном сервере: первый прогон привёл систему
к описанному состоянию (`changed=3`), повторный не изменил ничего
(`changed=0`), режим `--check` отработал без внесения изменений.

### Что это дало по сравнению с ЛР4

- Вся настройка сервера описана декларативно, а не последовательностью
  команд; повторный запуск безопасен.
- Параметры вынесены в переменные: чтобы развернуть второй сервер,
  достаточно добавить хост в инвентарь.
- Появился режим предварительного просмотра изменений (`--check --diff`).
- Частичное применение по тегам: `--tags nginx` обновит только прокси.

### Что можно улучшить

- **Ansible Vault** для пароля подключения и чувствительных переменных:
  сейчас пароль вводится вручную при запуске.
- **Роль для self-hosted runner'а из ДЗ6** — его установка пока выполнена
  вручную и в плейбуке не описана.
- **Запуск плейбука из CI** вместо отдельного workflow с shell-командами:
  тогда и деплой, и настройка сервера будут описаны одним инструментом.
- **Molecule** для тестирования ролей в контейнерах до применения на
  реальном сервере.
