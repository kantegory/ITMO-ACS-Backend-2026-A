# ДЗ6 — GitHub Actions и автоматическое развёртывание

Workflow: `.github/workflows/deploy-rent.yml` в корне репозитория.
Триггер — push в существующую ветку **lab3** при изменении приложения или
его конфигурации. Для ручного запуска также предусмотрен `workflow_dispatch`.
Параллельные развёртывания сериализуются через `concurrency` в GitHub
и через `flock` на сервере.

## Этапы

1. `validate`: получение исходников, проверка синтаксиса shell, проверка
   объединённого Docker Compose и сборка общего образа приложения.
2. `deploy`: подключение по SSH с проверкой ключа сервера, передача SHA
   коммита, сборка и запуск этого коммита, проверки готовности и HTTP API.
3. Проверка, что публичный `/deployment.json` содержит SHA именно этого запуска.

Секреты приложения хранятся только на сервере. Workflow получает отдельный
SSH-ключ CI, который в `authorized_keys` ограничен командой
`/usr/local/sbin/rent-ci-dispatch`. Интерактивный терминал, перенаправление
портов и агент SSH для этого ключа запрещены.

## Первичная настройка

Ручное развёртывание из ЛР4 должно уже работать. В GitHub, в Settings → Secrets
and variables → Actions, требуются четыре секрета:

| Секрет | Содержимое |
|---|---|
| `DEPLOY_HOST` | IP сервера |
| `DEPLOY_PORT` | SSH-порт, здесь `22` |
| `DEPLOY_KEY` | Отдельный закрытый ключ SSH для CI |
| `DEPLOY_KNOWN_HOSTS` | Строка known_hosts с проверенным открытым ключом сервера |

Сверять отпечаток ключа сервера нужно через уже доверенное подключение
Termius и `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
`StrictHostKeyChecking` в workflow не отключается.
Открытые и закрытые ключи доступа не добавляются в репозиторий.

Скрипт `rent-ci-dispatch` устанавливается в `/usr/local/sbin/` с владельцем
root и правами `0755`. Он принимает только `deploy <SHA из 40 символов>`,
получает актуальную ветку lab3 и отклоняет SHA, который не совпадает с её
текущей вершиной. Исходники каждого релиза извлекаются в
`/opt/rent-lab4/releases/<SHA>`. Данные PostgreSQL остаются в томах одного
Compose-проекта `rent-lab4`.

После успешного обновления `/opt/rent-lab4/current` указывает на каталог
ЛР4 активного релиза, а `/var/lib/rent-lab4/deployment.json` содержит SHA,
название ветки и время развёртывания в UTC.

## Проверка результата

Отправить изменение приложения в lab3, открыть Actions и проверить успешное
завершение обоих jobs. Затем открыть:

- <http://77.239.127.10:8081/deployment.json>;
- <http://77.239.127.10:8081/api/v1/property-types/>.

SHA в первом ответе должен совпадать с коммитом запуска Actions.
Обновление документов исключено из триггера, чтобы добавление отчёта не
перезапускало приложение.
