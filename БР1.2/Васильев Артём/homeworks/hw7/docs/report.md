# ДЗ7. Технический дизайн облачной инфраструктуры Job Platform

Студент: Васильев Артём. Группа: БР1.2. Проект: сайт поиска работы.

## Задача

Разработать технический дизайн облачной инфраструктуры полного микросервисного приложения: размещение, ресурсы, сетевую связность и восстановление при отказах.

## Ход работы

## 1. Приложение и границы

Используется реализованный в ДЗ6 backend: семь независимых Express/TypeScript/TypeORM-сервисов. Auth/User отвечает за регистрацию и JWT, Company — за компании и работодателей, Dictionary — за справочники, Vacancy — за вакансии, Resume — за резюме, Application — за отклики, Interaction — за избранное и просмотры. Межсервисные запросы выполняются через REST с X-Service-Token; событие application.created передаётся через RabbitMQ.

Работа проектирует размещение полного приложения, а не одного демонстрационного сервиса. Старые лабораторные и мониторинг в родительском каталоге lab7 не изменяются. Новая облачная ЛР7 находится в labs/lab7/cloud.

## 2. Модель размещения и обоснование

Преподаватель разрешил использовать существующий VPS при выполнении требований. Выбран одноузловой K3s: один server/worker, Ubuntu 24.04 LTS, 3 vCPU, 5925 MiB RAM, виртуальный диск 90 GiB с ext4, IPv4 147.45.196.171 (Nuxt.Cloud, сервер 1591496). Managed Kubernetes, отдельный балансировщик, дополнительные VM и платный домен не используются из-за бюджета.

Control plane, SQLite-хранилище K3s, containerd, CoreDNS, metrics-server и local-path provisioner работают на том же узле. Встроенный Traefik и ServiceLB отключены; отдельный Traefik устанавливается закреплённым HelmChart вместе с matching CRD. Вход — NodePort Traefik 30080 → Ingress → приватный Nginx gateway. Собственный OCI registry доступен только на loopback через SSH-туннель. Образы собираются в GitHub Actions, а не на ограниченном VPS.

Это учебная инфраструктура, не production HA. Реплики на одном узле защищают от отказа процесса, но не от отказа VM, диска или площадки.

## 3. Карта ресурсов

- 7 Deployment + 7 ClusterIP Service — существующие микросервисы; по одной реплике в покое.
- Для каждого backend: начальные requests 25m CPU / 48Mi RAM, limits 300m / 112Mi; уточняются по измерениям ЛР8.
- PostgreSQL 16: один StatefulSet, PVC 3Gi, семь отдельных БД и семь отдельных LOGIN-ролей. CONNECT для PUBLIC отозван; роль каждого сервиса владеет только своей БД. Это экономит память семи процессов PostgreSQL без объединения моделей данных.
- RabbitMQ: один StatefulSet, PVC 1Gi, topic exchange, доступ только внутри namespace.
- Traefik: HelmChart/CRD и Deployment в kube-system, Service NodePort 30080, Ingress класса lab-ingress.
- Nginx gateway: один Deployment и ClusterIP Service :80 в job-platform; раздаёт также статическую документацию.
- Registry: Deployment с одной репликой и стратегией Recreate, hostNetwork; 127.0.0.1:5000 и hostPath. Не публикуется наружу, CI подключается через SSH.
- Мониторинг новых работ: Prometheus, Grafana, Loki и Alloy, host-метрики Node Exporter и TCP-проверки Blackbox Exporter; отдельные конфигурации в ЛР8. Существующие файлы ЛР6 не меняются.
- HPA: Auth/User Service, minReplicas=1, maxReplicas=2; CPU-цель задаётся относительно request. Metrics Server входит в K3s.

Полный мониторинг допускается только после проверки allocatable RAM ≥4 GiB; на новом узле gate пройден. Начальный запуск Grafana с загрузкой образа и миграциями занял 617 секунд, поэтому progressDeadlineSeconds и ожидание rollout установлены в 900 секунд. Размер реплик, retention и последовательность миграций/rollout остаются ограничены бюджетом. Не поддерживается одновременный запуск старого полного Compose и новой Kubernetes-копии. Ограничения контейнеров не являются резервированием дополнительной памяти: отсутствие OOM и Pending проверяется после реального запуска.

## 4. Сеть

Схема: diagram.svg.

```text
Пользователь → VPS:30080 → Traefik / Ingress → gateway:80 → ClusterIP микросервиса
                                    ├→ ClusterIP других сервисов
                                    ├→ PostgreSQL:5432 (своя БД/роль)
                                    └→ RabbitMQ:5672
CI runner → SSH:22 → localhost registry:5000 → containerd → Pod
Администратор → SSH port-forward → Grafana / API K3s
```

На интерфейсе ens3 назначен 147.45.196.171/32; маршрут по умолчанию — через 10.0.0.1 onlink. Адрес и маршрут прочитаны на целевой VM, подсеть /24 не предполагается. K3s использует Pod CIDR 10.42.0.0/16 и Service CIDR 10.43.0.0/16. Прикладные и monitoring workloads — namespace job-platform; ingress и registry — kube-system. Для единственного узла выделен Pod CIDR 10.42.0.0/24. БД и брокер не имеют NodePort. Входящие прикладные запросы проходят только через gateway; internal API маршруты наружу не проксируются.

Публичный адрес демонстрации — http://147.45.196.171:30080. При отсутствии домена HTTP не выдаётся за HTTPS: учётные данные только синтетические учебные, административный доступ и передача образов — по SSH. Для production нужны DNS/TLS и отказоустойчивые узлы.

## 5. Секреты, хранение и доступ

JWT, service-token, пароли БД/брокера генерируются на VPS и сохраняются в /opt/job-platform-cloud/secrets.env с правами 0600. Kubernetes Secret создаётся через CLI, реальные значения отсутствуют в Git. Kubeconfig 0600 остаётся на сервере; CI получает доступ через отдельный SSH Secret. Registry не требует публичного пароля, потому что слушает только loopback.

Данные PostgreSQL/RabbitMQ хранятся в PVC. Registry и локальные PVC переживают пересоздание Pod, но не потерю диска. Образы тегируются полным SHA commit; mutable latest не используется для приложения. Исходники сервисов берутся из homeworks/hw6. По согласованию исправлены только три внутренних batch DTO (профили работодателей, вакансии, резюме): явные camelCase-проекции вместо сериализации entity с публичными snake_case aliases. Публичный API, ownership/auth-проверки и исключение пароля сохраняются.

## 6. Отказы и восстановление

- Падение процесса: liveness/startup probes и Deployment/StatefulSet перезапускают контейнер. Для singleton возможен краткий перерыв; readiness убирает неготовые endpoints.
- Удаление Pod: контроллер создаёт замену; поведенческая проверка входит в ЛР7.
- Плохая версия: deployment rollout status с timeout; восстановление сохранённых spec.template всех семи приложений и gateway через release-rollback.sh с проверкой rollout. Снимок хранится до завершения Newman; отказ после деплоя также инициирует восстановление. Без полного предыдущего релиза сценарий явно завершается ошибкой, не удаляя новые приложения или данные. Общая конфигурация и данные этим механизмом не откатываются. Изменения схемы БД не откатываются автоматически: для разрушительных миграций нужна отдельная резервная копия.
- Отказ VM/диска/зоны: весь стенд недоступен; второго узла нет. Повторная установка + восстановление логических дампов.
- Удаление таблицы: восстановление из pg_dump; потеря последних данных зависит от возраста дампа.

Целевые, а не измеренные показатели: RTO backend после отказа процесса до 5 минут; RTO полного восстановления до 2 часов при наличии исправного VPS и копий; RPO до 24 часов при ежедневном дампе. Без отдельной off-host копии нет гарантии восстановления после потери диска. На новом VPS уже проверены логические дампы всех семи БД, восстановление в отдельные временные БД и совпадение количества строк; исходные БД/API сохранены. Это не проверка полного off-host disaster recovery и не доказательство RPO 24 часа: ежедневное off-host расписание пока не активировано.

## 7. План развёртывания и приёмка

1. Проверить SSH, Ubuntu, ресурсы и отсутствие конфликтующих приложений.
2. Установить закреплённый K3s, дождаться Ready; API и административные порты не использовать для публичных клиентов.
3. Поднять registry, namespace и Secret.
4. Выполнить CI: нормативная проверка контрактов и регрессии → настоящий serializer/guards → сборка и E2E во временном кластере → его очистка → SHA-образы и push в VPS registry по SSH-туннелю.
5. Создать PVC, ConfigMap и PostgreSQL/RabbitMQ; проверить Ready.
6. Применить 7 Deployment/Service, выполнить миграции init-контейнерами, проверить rollout.
7. Опубликовать Ingress/gateway, пройти Postman end-to-end, проверить удаление Pod и rollback на целевом VPS.
8. Подключить мониторинг ЛР8, выполнить baseline и нагрузку, показать HPA scale-out/scale-in и тюнинг.
9. Сохранить реальные логи приёмки, результаты восстановления и измерений, отчёты по новым работам. k6 работает на VPS; сборка образов — в CI, Docker на операторском ПК выключен.

Terraform не требуется для уже выделенного VPS; воспроизводимость обеспечивается bootstrap.sh, Kubernetes-манифестами и workflow ДЗ8. Новые платные ресурсы не создаются.
