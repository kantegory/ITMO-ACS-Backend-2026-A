## Задача

Подготовить сценарии нагрузки ключевых эндпоинтов микросервисов, базовые метрики RPS, latency p95/p99, error rate и целевые SLA/SLO.

## Ход работы

### Сценарий и данные

`load.js` использует k6 и существующий HTTP-контракт без изменения backend. В setup создаётся отдельный синтетический соискатель, выполняются вход и PATCH профиля. JWT и пароль не печатаются и не включаются в summary-файлы.

Обычная итерация имитирует поиск работы: GET `/vacancies?search=Backend&page=1&limit=20`, GET `/industries`, GET `/users/me` с JWT. Проверяются не только HTTP-коды, но и структура ответа. Это ключевые операции трёх сервисов; полный функциональный сценарий семи сервисов проверяется отдельно Postman-коллекцией, а не заменяется нагрузкой.

Профиль HPA выполняет POST `/auth/login` и GET `/users/me`: bcrypt-проверка пароля создаёт CPU-нагрузку на Auth/User. Повторная регистрация не выполняется в каждой итерации, поэтому тест не раздувает БД. У каждого запуска собственная синтетическая учётная запись.

## Профили

Используется открытая модель arrival-rate: интенсивность задаётся независимо от времени ответа. `RATE` — **итерации/с, не HTTP RPS**. Обычная итерация даёт 3 запроса, HPA-итерация — 2 при успешном входе.

- baseline: постоянная нагрузка; по умолчанию 5 итераций/с, 1 минута, ожидается около 15 запросов/с без учёта setup.
- stress: четыре стадии по 30 секунд: RATE → 2×RATE → 4×RATE → RATE. Определяет предел пропускной способности и восстановление.
- spike: обычная нагрузка → скачок до 10×RATE за 1 секунду → удержание → возврат. Продолжительность основных стадий по умолчанию 10 секунд.
- soak: постоянная нагрузка 20 минут для поиска накопления задержек/памяти; укороченный запуск явно отмечается как укороченный, не считается полным 20-минутным тестом.
- hpa: постоянная CPU-нагрузка на авторизацию, по умолчанию 5 минут. Начинать с RATE=1–2, чтобы не уничтожить очередь на малом VPS.

`VUS` ограничивает одновременно работающих виртуальных пользователей; автоматически растущий безграничный пул не используется. Недоставленная из-за занятого пула нагрузка фиксируется в `dropped_iterations` и не скрывается за низкой задержкой успешных запросов. Общая продолжительность ограничена 3000 секунд, потому что JWT стенда действует 3600 секунд.

## Метрики и целевые показатели

Метрики setup отделены меткой `phase=setup`; нагрузка имеет `phase=load`.

- RPS: фактическое число нагрузочных HTTP-запросов в секунду; summary k6 использует полное время запуска, поэтому начальный setup немного снижает агрегированную оценку. Для временного графика используется Prometheus rate по счётчику запросов.
- p95/p99: 95-й/99-й процентиль `http_req_duration`, в summary — миллисекунды. Это HTTP-время ответа через gateway, а не время всей трёхзапросной итерации.
- HTTP error rate: доля неуспешных HTTP-запросов.
- business_errors: доля ответов с неправильным кодом или структурой; предотвращает ложный успех при HTTP 200 с неверным JSON.
- dropped_iterations: число недоставленных итераций, обязательный показатель насыщения генератора/системы.

Целевой SLO базовой нагрузки: p95 < 500 мс; p99 < 1000 мс; HTTP error rate < 1%; business_errors < 1%; dropped_iterations = 0. Эти значения заданы как thresholds и приводят к ненулевому exit code при нарушении. Для stress/spike thresholds сохраняются: их нарушение — измеренный предел, а не повод переписать пороги после теста.

Учебный целевой SLA: доступность ключевых API не ниже 99% за 30 дней; без финансовых обязательств. Короткие лабораторные прогоны не доказывают месячную доступность и не являются production-гарантией. Одноузловой VPS не имеет защиты от отказа узла; для реального SLA нужны отказоустойчивость и длительный внешний мониторинг.

## Воспроизведение

Версия генератора: k6 v2.4.0, portable binary вне репозитория. В фактическом прогоне генератор работает на том же учебном VPS `147.45.196.171` (3 vCPU, 5925 MiB RAM), что и K3s: запросы идут через `127.0.0.1:30080 → Traefik/Ingress → gateway → сервис`. Это измерение приложения и локального ingress, не задержки внешнего WAN-клиента. Генератор делит CPU/RAM с системой; его влияние входит в host-графики. Операторский ПК не выполняет нагрузку и не запускает Docker.

Воспроизводимый набор запускается `homeworks/hw8/ci/load.sh` с `CHECK_CONFIG=homeworks/hw8/ci/vps.env`: baseline 60 с, stress 4×30 с, spike 32 с суммарно, soak 20 минут, HPA до настройки 180 с и после настройки 120 с. RATE=5 для обычных профилей, RATE=2 для HPA; пул не более 32 VU. Конфигурация содержит только несекретные параметры и пути.

```bash
# Запуск из отдельного каталога результатов: summary.json / summary.txt пишутся в cwd.
k6 run -e PROFILE=baseline -e RATE=5 -e VUS=32 -e DURATION=1m \
  -e BASE_URL=http://127.0.0.1:30080/api/v1 /path/to/hw10/load.js

k6 run -e PROFILE=stress -e RATE=5 -e DURATION=30s /path/to/hw10/load.js
k6 run -e PROFILE=spike -e RATE=2 -e DURATION=10s /path/to/hw10/load.js
k6 run -e PROFILE=soak -e RATE=2 -e DURATION=20m /path/to/hw10/load.js
k6 run -e PROFILE=hpa -e RATE=2 -e DURATION=5m /path/to/hw10/load.js
```

В серверном наборе включён `-o experimental-prometheus-rw`, `K6_PROMETHEUS_RW_SERVER_URL=http://127.0.0.1:9090/api/v1/write` и `K6_PROMETHEUS_RW_TREND_STATS=p(95),p(99),avg,max`. Процентили remote write имеют единицу секунд, поэтому запросы Grafana умножают их на 1000 перед выводом в миллисекундах. JSON-summary k6 уже содержит миллисекунды. Для просмотра приватной Grafana используется отдельный SSH-туннель; порт мониторинга наружу не открывается.
