# ДЗ8. CI/CD для облачной инфраструктуры

Студент: Васильев Артём. Группа: БР1.2.

## Задача

Реализовать автоматизированную интеграцию и доставку компонентов микросервисного приложения в целевую Kubernetes-инфраструктуру.

## Ход работы

### Запуск и порядок CI

Созданы два workflow; прежние workflows ДЗ6 и ЛР5 не используются для нового Kubernetes-стенда.

- `.github/workflows/cloud.yml`: push в `main` по заданным paths либо ручной запуск с `confirm_vps_recovery=true`. Push feature-ветки сам по себе не запускает VPS-деплой.
- `.github/workflows/cloud-validation.yml`: временный кластер на push в `main`/`feat/cloud-course-labs` по paths либо ручной запуск; изменения только Markdown/PDF исключены. Это проверка, не публикация на VPS.

Runner — Ubuntu 24.04, Node.js 22. Порядок основного workflow:

1. Checkout; unittest манифестов, renderer и CI, проверка фикстур, валидация восьми OpenAPI и Postman Collection v2.1, `mkdocs build --strict`.
2. `homeworks/hw8/ci/check-internal-contracts.sh`: реальные TypeScript, class-transformer и routing-controllers, сериализация DTO и проверки прав, а не только сравнение текстов.
3. `ci/setup.sh`, `ci/build-deploy.sh`: временный k3d и registry, сборка семи backend и gateway, общие облачные манифесты.
4. `ci/acceptance.sh`: Newman, документация и маршруты, пересоздание Pod, отрицательная readiness/откат, повторный Newman и логическое восстановление семи БД.
5. `ci/cleanup.sh`: удаление временного кластера и registry, в том числе при ошибке; порт 5000 освобождается перед SSH-туннелем.
6. Только после успешных проверок — `homeworks/hw8/scripts/build-deploy.sh`: сборка/отправка SHA-образов, обновление VPS и ограниченный Newman с JUnit-артефактом.

В preview после acceptance предусмотрены мониторинг, нагрузка/HPA и браузерные доказательства. Наличие шага в YAML не доказывает успешного выполнения.

### Доставка и откат

Цель — `147.45.196.171`, одноузловой K3s; настройки собраны в `labs/lab7/cloud/config.env`. Сборки идут на runner. Семь backend и gateway получают полный 40-символьный SHA без `latest`. Registry доступен только на `127.0.0.1:5000`, образы передаются через SSH-туннель. Host key проверяется через `known_hosts`; runtime-пароли и kubeconfig не выгружаются на runner.

Релиз доставляется в `/opt/job-platform-cloud/releases/<SHA>`. `labs/lab7/cloud/scripts/deploy.sh` сохраняет предыдущие Pod templates, применяет конфигурацию и хранилища, ждёт PostgreSQL/RabbitMQ, затем последовательно обновляет приложения и gateway. Миграции выполняются init-контейнерами; манифесты проверяются серверным dry-run.

Свежий JSON получается через `kubectl create --dry-run=client -o json`, а не apply-конвертацию существующего ресурса. `render.py` принимает JSON-поток, List или одиночный объект и заменяет image на полный SHA. После rollout читаются и сверяются реальные image всех восьми Deployment.

Перед Newman добавляются синтетические dictionary-фикстуры ДЗ9. Трафик идёт через SSH-туннель к Traefik NodePort и gateway. VPS-прогон ограничен: общий timeout 180000 мс, request 15000 мс, script 10000 мс, `--bail`.

При ошибке deploy работает серверный обработчик; после deploy и до успешного Newman — обработчик `build-deploy.sh`. `release-rollback.sh` восстанавливает восемь прежних `.spec.template` и ждёт rollout с timeout. Без полного снимка предыдущего релиза откат не объявляется успешным. **Откат ограничен Pod templates:** БД, SQL-миграции, ConfigMap, Service, Ingress, PVC и registry не возвращаются назад. Это не транзакционный откат всей системы; ошибка приёмки/отката остаётся ошибкой workflow.

После CD отдельно применён ресурсный overlay ЛР8 и выполнен 60-секундный baseline проверенного SHA: 900 запросов, без HTTP/business errors и dropped iterations. Для исходного нагрузочного SHA `2308635` сохранены все семь полных прогонов, HPA и JSON/CSV. Повторный базовый deploy может вернуть начальные requests/limits; для итогового состояния ЛР8 применяется `optimized-auth.json` после доставки.

Браузерная проверка больше не принимает пустые Grafana canvas и неоформленный HTML: проверяются отрисованные пиксели всех графиков и CSS navbar. Исправлены MIME-типы Nginx. API-проверки и фактические PNG рассматриваются отдельно; неудачные старые снимки в итоговые доказательства не включены.

## Вывод

Реализована и выполнена цепочка «контракты → временный Kubernetes → интеграция/восстановление → очистка → VPS», SHA-образы и ограниченный templates-only rollback. Ручная и автоматическая доставка от main-push, бизнес-E2E, ресурсный overlay и финальная визуальная проверка подтверждены реальным выполнением.
