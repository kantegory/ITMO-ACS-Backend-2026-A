# Тестирование

## Статические проверки

Из `homeworks/hw9`:

```bash
uv run --python 3.14 --with-requirements requirements.txt mkdocs build --strict
for spec in docs/contracts/openapi.yaml docs/contracts/services/*.yaml; do
  uv run --python 3.14 --with openapi-spec-validator==0.7.2 openapi-spec-validator "$spec" || exit 1
done
uv run --python 3.14 --with check-jsonschema==0.29.2 check-jsonschema \
  --schemafile https://schema.getpostman.com/json/collection/v2.1.0/collection.json \
  docs/contracts/job-platform-dz3.postman_collection.json
```

Сборка проверяет конфигурацию и локальные ссылки Markdown, OpenAPI validator —
структуру и ссылки контрактов, JSON Schema — формат Postman Collection v2.1.
Статическая валидация не проверяет доступность API, корректность серверных
ответов или актуальность контрактов относительно бизнес-логики.

## Регрессия UUID справочников (офлайн)

```bash
python -m unittest test_fixtures -v
```

Нужны Python и Node.js; HTTP/БД не используются. Тест исполняет настоящие
Postman-скрипты выбора справочников. В frozen HW6 `CreateVacancyDto` проверяет
`industry_id` и `experience_level_id` через `@IsUUID()`, но миграция справочников
создаёт ID `11111111-1111-1111-1111-111111111111` и
`22222222-2222-2222-2222-222222222222` (и аналогичные): их UUID variant — NCS,
а не RFC 4122. PostgreSQL хранит такие значения в колонке `uuid`, но это
не делает их совместимыми с DTO. Исходная HW3-коллекция берёт первый элемент;
эта новая копия выбирает существующий RFC UUID или явно проваливает assertion
на шагах 05/06. ID нельзя «исправлять» заменой символов: внешней записи с новым
ID может не существовать.

Если отдельная тестовая БД содержит только frozen seed, перед E2E оператор
должен применить [аддитивную фикстуру](contracts/e2e-dictionaries.sql) к БД
`dictionary-service`: она создаёт две опубликованные записи с DEFAULT
`gen_random_uuid()`, не изменяя старые ID, HW6 или бизнес-код. Фикстура применена
на отдельном учебном стенде перед успешным E2E. Публичный API справочников поддерживает только чтение, поэтому
сама Postman-коллекция не может подготовить эти записи. На production эту
фикстуру не применять; запускать только после согласования тестового стенда.

`FULL_TIME`, `HYBRID`, `PENDING`, `INVITED`, строковые `skills`/`education`
совпадают с исходными DTO/enums HW6; менять их не требуется. `hw10/load.js`
в setup создаёт только пользователя, логинится и обновляет имя; вакансий и
ссылок на справочники там нет. Несовместимость seed воспроизводится офлайн.
После применения фикстуры исправленная коллекция прошла на VPS; это не
доказывает, что UUID были единственной причиной прежнего HTTP 400 из CI.

## Postman: ручной E2E на отдельном тестовом стенде

1. Скачайте [коллекцию](contracts/job-platform-dz3.postman_collection.json)
   и импортируйте в Postman. Понадобится единый gateway, доступный клиенту.
2. Задайте `baseUrl` стенда с `/api/v1` без завершающего `/`. Проверьте,
   что environment-переменная с тем же именем не перекрывает collection variable.
3. Убедитесь, что отрасли и уровни опыта заполнены, и используйте только
   тестовую БД: запуск создаёт пользователей, компанию, вакансию, резюме,
   просмотры и отклик. Полного удаления этих данных в коллекции нет.
4. Выполните 23 запроса по порядку через Collection Runner: первый запрос
   генерирует уникальные email и очищает старые ID/JWT, login сохраняет токены.
   Не сохраняйте полученные токены в экспортируемый JSON.
5. Сценарий проверяет создание вакансии, поиск соискателем, резюме, избранное,
   отклик `PENDING`, смену на `INVITED`, чтение нового статуса и удаление
   избранного. Для проверки работы HTTP-ошибок нужны отдельные негативные
   сценарии: коллекция не заменяет полный набор тестов доступа.

Ожидаемый критерий — успешные assertions всей коллекции, не просто отсутствие
сетевых ошибок. При 401/403 проверьте роль, владельца, срок JWT и выполните
сценарий заново; при пустых справочниках подготовьте данные стенда.

## Подтверждённый прогон

27 ноября 2026 года на учебном VPS Newman выполнил 23 запроса без проваленных
проверок. После удаления pod он был пересоздан с новым UID и стал Ready.
Проверка с неверным портом readiness завершилась ожидаемым тайм-аутом;
`rollout undo` восстановил Ready. Повторный Newman также прошёл все 23 запроса.

Это проверка сценария найма и восстановления, не полный набор негативных тестов
или нагрузочное испытание. Отчёт Runner перед публикацией нужно очистить от
JWT, паролей и персональных данных.
