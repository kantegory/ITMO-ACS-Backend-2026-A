## Ход работы

### 1. Стенд и нагрузка

Испытания выполнены 27.11.2026, 08:40:05–09:12:15 UTC на VPS `147.45.196.171`: 3 vCPU, 5925 MiB RAM, один узел K3s. Версия образа приложения — `2308635cae6ebcdc272367a5c218e04b7da7c09f`. Нативный k6 v2.4.0 работал на той же VM и делил с приложением ресурсы. Маршрут: loopback:30080 → Traefik Ingress → gateway → семь сервисов. Это проверка стенда, а не скорости доступа через внешний интернет.

Использованы профили baseline, stress, spike, soak и отдельная нагрузка авторизации для HPA. Параметр RATE задаёт итерации в секунду, а не RPS: обычная итерация содержит три HTTP-запроса, HPA — два. Счётчики запросов и latency в таблице относятся только к `phase:load`, без setup. RPS использует полное время k6 summary (setup немного снижает агрегат); это средний показатель запуска, а не пиковая скорость spike.

| Запуск | HTTP-запросы | RPS | p95, мс | p99, мс |
|---|---:|---:|---:|---:|
| baseline_before | 903 | 14.99 | 6.82 | 12.09 |
| stress | 3600 | 29.95 | 6.08 | 11.02 |
| spike | 1962 | 60.94 | 7.39 | 47.38 |
| soak | 18003 | 15.00 | 5.16 | 7.58 |
| hpa_before | 722 | 4.01 | 31.42 | 82.73 |
| baseline_after | 903 | 14.97 | 4.98 | 6.33 |
| hpa_after | 480 | 4.00 | 31.17 | 37.38 |

Всего выполнено 26573 нагрузочных HTTP-запроса. Во всех семи запусках HTTP-ошибки и бизнес-ошибки составили 0%, `dropped_iterations` — 0, все пороги k6 пройдены. Soak длился полные 20 минут, с 08:43:38 до 09:03:38 UTC.

Критерии SLO: p95 < 500 мс, p99 < 1000 мс, доли HTTP- и бизнес-ошибок < 1%, отсутствие пропущенных итераций. Они выполнены в этих испытаниях. SLA 99% за 30 дней остаётся целевым значением: короткий эксперимент не измеряет месячную доступность.

### 2. Анализ графиков и узких мест

Для анализа использованы временные ряды Prometheus и показатели k6; отображение — в Grafana. Сводка ресурсов охватывает всё окно испытаний с шагом 15 секунд. Максимумы ниже относятся к полученным отсчётам, а не к гарантированным мгновенным пикам.

| Метрика | Результат |
|---|---:|
| CPU узла, максимум двухминутного rate | 24.00% |
| Занятая RAM узла, минимум–максимум | 2214.24–2376.05 MiB |
| I/O wait, максимум двухминутного rate | 4.21% |
| CPU auth, максимум на один pod по минутному rate | 73.59m |
| Working set auth, максимум на один pod | 47.51 MiB |

У spike хвост задержек выше, чем у baseline_before: p99 47.38 против 12.09 мс, но запас до SLO сохраняется. Самая большая p99 в таблице — 82.73 мс у hpa_before; это отдельный сценарий авторизации, поэтому напрямую сравнивать его с обычным профилем нельзя. Длительный soak также завершился без ошибок и пропущенных итераций.

В выбранных отсчётах нет признака исчерпания CPU или RAM узла. Предельная пропускная способность не найдена: название stress не означает, что достигнут отказ. По этим данным нельзя доказать отсутствие OOM, утечки памяти или кратковременного throttling; для таких выводов нужны отдельные события и метрики. Генератор на той же VM ограничивает независимость измерений.

Практическая проблема настройки — малый CPU request auth: HPA считал высокую относительную загрузку даже при небольшой абсолютной потребности. Признаков того, что старый CPU limit 300m был узким местом, не получено.

### 3. Проверка HPA

Для `auth-user-service` задан HPA: минимум одна, максимум две реплики, целевая загрузка CPU 70% от requests; окно стабилизации уменьшения — 90 секунд.

По `hpa.csv` при нагрузке желаемое число реплик стало равным двум в 09:04:09 UTC, фактическое число — в 09:04:30 UTC. В этом отсчёте относительная загрузка CPU достигала 244%. После окончания hpa_before в 09:06:39 UTC желаемое число снизилось до одного в 09:08:43 UTC, фактическое — в 09:09:04 UTC. Возврат занял 145 секунд и уложился в проверочный срок 240 секунд. Результат подтверждён маркером `HPA_SCALE_OUT_AND_IN_VERIFIED`.

Первые строки CSV содержат ещё не заполненный статус HPA; они не означают, что приложение работало без реплик. Для проверки масштабирования использован CSV с current/desired, а не число серий cAdvisor: серия контейнера сама по себе не доказывает Deployment Ready или desired replicas.

### 4. Requests/limits до и после

Изменены ресурсы контейнера приложения `auth-user-service` на одну реплику.

| Параметр | До | После |
|---|---:|---:|
| requests.cpu | 25m | 100m |
| requests.memory | 48Mi | 64Mi |
| limits.cpu | 300m | 500m |
| limits.memory | 112Mi | 128Mi |

Измеренный максимум working set 47.51 MiB близок к прежнему request 48Mi; request 64Mi даёт больший запас резервирования. Request не является пределом памяти: предел задаётся limit. CPU request 100m лучше соответствует измеренному максимуму 73.59m и меняет знаменатель расчёта HPA. Поэтому уменьшение относительной загрузки после настройки не следует принимать за уменьшение абсолютного потребления CPU.

Limits 500m/128Mi оставлены с запасом; необходимость CPU limit 500m для будущих всплесков этим экспериментом не доказана. Измеренный working set также не заменяет проверку всех видов учитываемой памяти контейнера.

После настройки baseline p95 составил 4.98 вместо 6.82 мс, p99 — 6.33 вместо 12.09 мс. Для HPA p95 составил 31.17 вместо 31.42 мс, p99 — 37.38 вместо 82.73 мс. Это наблюдение одного сравнения, а не доказательство ускорения: HPA-прогоны длились 180 и 120 секунд, окна метрик различаются, повторных серий эксперимента нет.

Исходные доказательства сохранены рядом с работами: `docs/evidence/results/` содержит HPA CSV, параметры ресурсов, анализ временных рядов и покрытие логов; `homeworks/hw10/docs/evidence/results/` (относительно каталога студента) — таблицу нагрузки и все семь summary k6. В `docs/evidence/` приложены читаемые фрагменты настоящей Grafana и отдельный график по `kubectl HPA status`; полный исходный снимок — в `docs/evidence/full/`. График CSV не выдаётся за снимок Grafana. CSV использует UTC, временная ось браузера — МСК.

На проверенном main-релизе `5772fc9a2b0f0a1acccfe8322aebe5ee2699aa58` автоматическая доставка `45973038963` прошла успешно; отдельно подтверждены восемь image/Ready. Ресурсный overlay ЛР8 повторно применён после базового deploy. Дополнительный baseline 60 секунд выполнил 900 запросов без HTTP/business errors и dropped iterations, все SLO пройдены. Это smoke нового релиза, не повтор исходных семи испытаний.

После публикации проверены все 14 запросов исправленного дашборда и реальные логи всех 32 запущенных regular/init/завершённых контейнеров за окно 24 часа: missing=0, silent=0. Отдельно проверены фактические пиксели отрисованных графиков. TCP-пробы не заменяют бизнес-E2E: функциональный Newman из 23 запросов выполнен отдельно. Пустые старые снимки не включены в доказательства. В панели cAdvisor учитываются недавние серии (<75 с), а не Ready/desired; при пересоздании контейнеров возможен временный двойной счёт, поэтому HPA доказывается CSV.

## Вывод

Все семь нагрузочных запусков прошли выбранные SLO без ошибок и пропущенных итераций. HPA выполнил переход 1 → 2 → 1. По измерениям увеличены requests/limits auth и устранён слишком малый CPU request. Предел мощности стенда и месячная доступность не установлены; гарантировать ускорение по одному сравнению нельзя.
